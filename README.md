# game-npc-agent

> 面向游戏场景的可控 AI NPC 智能体框架 —— 让 NPC **不只是会说，而是真的会玩**。

一个自研的 Agent 架构，把「语言 → 决策 → 游戏动作 → 世界状态」这条链路完整接通，
并配一套可复现的六维评测。七大模块与主流 AI 游戏团队的公开技术方案一一对应：

`Planning` · `Memory` · `Tool Use` · `Action` · `Reflection` · `Persona` · `State Tracking`

**同一个 `NPCAgent`，跑在两个结构完全不同的世界里**：一个是内置的确定性文字世界
（星屿咖啡屋），一个是 Minecraft 体素世界（有坐标、有物品数量、有昼夜循环）。
Agent 代码一行没改 —— 这条主张有可执行的测试兜着，不是文档里的一句话。

---

## 为什么做这个

把一个大模型 API 接进游戏，只能完成最前面的演示。真正做成稳定玩法会撞上这些问题：

| 失败模式 | 后果 | 本项目的应对 |
|---|---|---|
| NPC 说完话没有行动 | "看起来会说，实际上不会玩" | Tool Use + 环境护栏，语言动作和世界动作走同一条执行路径 |
| 忘记前面聊过的事 | 人设崩、剧情断裂 | 分层记忆（episodic / semantic / reflection）+ 混合检索 + 巩固 |
| 被玩家问住就顺着跑偏 | 剧透、出戏 | Persona 的知识边界 + 剧透红线 + 工具层拦截 |
| 多人同时说话就乱 | 抢戏、冷场 | 发言权与收件人判定（多玩家并发 + 主动发起话题） |
| 同一个错误反复犯 | 稳定性差 | Reflection 把失败原因变成教训，重规划时插入补救动作 |
| 场上两个 NPC 同时开口 | 两行字挤在一起，比单个 NPC 说错话更伤体验 | Cast 导演层统一收发发言权，一个 tick 只放一个人说话 |
| 换一个游戏就要重写 Agent | 架构不可复用，每个项目重复造轮子 | Environment 抽象 + WorldClient 契约，换世界只写适配器 |

> 一句话：**这个项目的价值不在于 NPC 说了什么，而在于它说完之后，世界真的变了。**

## 架构

```
                    ┌──────────────────────────────────────────┐
   玩家发言 ───────▶ │  State Tracking   现场状态（谁在场/冷场多久）│
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Dialogue    该不该我说？对谁说？要不要主动开口 │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Memory      检索相关记忆（混合打分）        │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Planning    分解任务 / 继续未完成的计划     │
                    └──────────────────┬───────────────────────┘
                                       ▼
        ┌──────────────────────────────────────────────────────┐
        │  Tool Use   统一执行（speak / remember / 世界动作）      │
        │  Persona    出戏词·剧透词·句数上限 三道闸门              │
        └──────────────────┬───────────────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────────────┐
        │  Environment  世界护栏：位置 / 材料 / 白名单 / 知识解锁   │
        └──────────────────┬───────────────────────────────────┘
                           ▼
                    ┌──────────────────────────────────────────┐
                    │  Reflection  失败归因 → 写成教训 → 下次重规划 │
                    └──────────────────────────────────────────┘
```

**两个关键的架构决策：**

1. **环境无关**。Agent 完全不知道自己在咖啡屋、Minecraft 还是引擎里，只面对 `observe()` 和 `dispatch()`。换世界 = 写一个新的 `Environment` 子类，Agent 一行不改 —— 这句话现在有两个世界可以对照验证。
2. **模型可选**。没有 API key 时自动回退到内置启发式策略，仓库 clone 下来零配置就能端到端跑通。这让评测可复现，也让"换模型"变成一行配置。

### 多 NPC：一个世界，多个 Agent

上面那条链路描述的是**一个** NPC。场上同时站着两个 NPC 时，多出三个单 Agent 场景里
根本不存在的问题：

| 问题 | 为什么不能交给 NPC 自己解决 |
|---|---|
| 谁先说？ | 每个 NPC 只看得见自己的状态，它不知道同伴这一轮打不打算开口 |
| 会不会撞车？ | 两个人都觉得自己该说话 —— 自己管自己的话，结果就是一起说 |
| 没说话的听见了吗？ | 听见 ≠ 要回答，但必须记下来，否则后面接不上话 |

所以有了 `cast.py`：一个站在所有 NPC 之上的**导演**。

```
                     ┌────────────────────────────────────────┐
                     │  Cast（导演）                            │
                     │  发言权调度：被点名者优先，否则轮转       │
                     │  一个 tick 只放一个人说话                │
                     └───────┬────────────────────┬───────────┘
                             ▼                    ▼
                     ┌───────────────┐    ┌───────────────┐
                     │ NPCAgent 阿柚  │    │ NPCAgent 小舟  │
                     │ 私有：记忆      │    │ 私有：记忆      │
                     │ 私有：状态/计划 │    │ 私有：状态/计划 │
                     └───────┬───────┘    └───────┬───────┘
                             └────────┬───────────┘
                                      ▼
                     ┌────────────────────────────────────────┐
                     │  Environment（共享）                     │
                     │  位置 / 物品 / 背包 / 世界标记 —— 只有一份 │
                     └────────────────────────────────────────┘
```

这条界线就是「多 Agent」和「一个 Agent 分饰两角」的区别：
**世界共享，脑子各用各的。** 阿柚不知道小舟这一轮打算开口，
小舟也不知道阿柚手里有没有那杯拿铁 —— 她们只能通过世界状态和对话互相了解，
跟真人一样。

发言权被收在**两层**，因为只拦一层不够：

| 层 | 拦什么 |
|---|---|
| 对话层（`dialogue.py`） | "要不要**新建**一个发言计划" |
| 工具层（`tools.py` 的 `allow_speech`） | "正在跑的计划里的 `speak` 步骤" |

只在对话层拦截的话，正在执行计划的 NPC 照样会插话 —— 它根本没走对话决策这条路。
被挡住的那一步标 `skipped` 而不是 `failed`：**让位不是失败**，
标成失败会触发无意义的重规划，还会让 Reflection 记下一条根本不存在的教训。

另外两个容易漏的细节：

- **冷场计数一个 tick 只能加一次**。`Cast` 一轮里会调用所有 NPC，每个都加一次的话，
  "冷场 2 轮后主动开口"会被提前触发。
- **NPC 之间说的话，同伴也要听见**。`Agent.step` 内部的监听只处理传进来的那条
  *玩家*发言，不额外补一步，"阿柚转头跟小舟说：你来弹一首"就断在半路 ——
  小舟的现场状态和记忆里根本没有这句话。

### 第二个世界：Minecraft 适配器

上面那句"换世界 = 写一个新的 `Environment` 子类，Agent 一行不改"，
在只有一种世界的时候是**主张**，不是**证据**。所以有了 `village` 场景：
同一个 `NPCAgent`，跑在一个结构上完全不同的世界里。

| | 星屿咖啡屋 | Minecraft 体素世界 |
|---|---|---|
| 位置 | 离散的几个房间 | 三维坐标 + 命名地点（POI） |
| 背包 | 物品列表（有没有） | `{物品: 数量}`（有几个） |
| 拿东西 | `take_item` | `mine`（挖）/ `craft`（合成） |
| 工位 | 隐式（配方自带 station） | 显式工作台，且配方有**产出数量** |
| 时间 | 没有 | 昼夜循环，夜里没光源就干不了活 |
| 交付 | `give_item` | `transfer` |

任务本身是一条真实的 Minecraft 制作链：

```
forest      mine(oak_log)
workshop    craft(planks)    1 原木 → 4 木板
workshop    craft(stick)     2 木板 → 4 木棍
cave_mouth  mine(coal)       必须天亮时采，或附近有火把
workshop    craft(torch)     1 煤炭 + 1 木棍 → 4 火把
cave_mouth  place(torch)     ← 这一步才是目标
```

**Agent 侧感知到的差别只有一个：背包里的东西后面多了「×3」。**
它照样规划、照样调工具、照样在被拒绝时重规划 —— 因为护栏给的理由
仍然是一句人话（"天黑了，看不清矿脉。需要先做个火把放在附近，或者等天亮"）。

#### 加了一层 `WorldClient`，而不是让 `Environment` 兼任传输层

```
    MinecraftEnv                     ← 翻译层：观测 schema / 工具映射 / 护栏
         │
         ▼
    WorldClient（契约：JSON 可序列化的 op）  ← 只实现 call() 这一个方法
         ├── LocalWorldClient   进程内体素世界（零依赖，离线可跑）
         └── MineflayerClient   stdio JSON 行 → Node 桥 → 真实服务端
```

两个理由：

1. **可测性**。`MinecraftEnv` 的全部逻辑都能在没有 Minecraft 服务端的情况下单测。
   跑一次真实服务端要几十秒，跑一次 `LocalWorldClient` 只要几毫秒。
2. **同一个契约，两种传输**。这不是文档里的一句承诺，而是代码结构：
   两个后端都只实现 `call()`，所有类型化方法（`move` / `mine` / `craft` …）
   都写在基类上，**物理上只存在一份**。

失败被分成两类，这个区分比它看起来重要：

| | 处理方式 | 为什么 |
|---|---|---|
| 游戏内失败（挖不到矿） | 返回 `ok=False` + 一句人话 | 这是给 Reflection 学的素材 |
| 传输层故障（桥进程死了） | 抛 `WorldClientError` | 伪装成"NPC 没做到"，会让一次工程事故看起来像一次模型失败 |

`Environment` 抽象本身**没有为 Minecraft 改动**：`observe()` / `dispatch()` /
`tool_specs()` / `snapshot()` / `world_facts()` / `available_topics()` 全都没变。
Minecraft 的不同之处全部被适配器吸收了。

顺带被抽出来共用的东西（第二个环境不该把逻辑抄一遍）：

- `env/conditions.py` —— 目标完成条件判定（`flag` / `all_flags` / `all_of` /
  `any_of` / `player_has` / **`player_has_count`**）。环境只提供**事实**，判定只写一遍。
- `Environment.utterances` / `speakers_by_tick()` / `speech_counts()` ——
  多 Agent 导演依赖的公共契约。它们曾经是 `StarIsleEnv` 的私有字段，
  于是导演得知道"咖啡屋的发言存在哪"——抽象就漏了。
- 知识边界（`requires` 未满足就不许讲）在两个世界里是**同一套语义**：
  "不剧透"是任务设计的保证，不该因为换了世界就失效。

## 快速开始

```bash
pip install -r requirements.txt

# 看一段完整的多玩家交互（无需任何 API key）
python -m npc_agent.cli demo --scenario icebreaker

# 看两个 NPC 在同一个世界里协作（多 Agent）
python -m npc_agent.cli demo --scenario duet

# 自己上手对话
python -m npc_agent.cli chat --scenario tutorial

# 跑评测，出数字
python -m npc_agent.cli eval

# 对照实验：离线启发式 vs 真实模型
python -m npc_agent.cli compare --models kimi-k2.7-code

# 消融实验：五种记忆检索策略
python -m npc_agent.cli ablate

# 看工具清单 / 场景与人设
python -m npc_agent.cli tools
python -m npc_agent.cli info

# 同一个 Agent 跑在 Minecraft 体素世界里（零依赖，不需要装 Minecraft）
python -m npc_agent.cli demo --scenario village

# 跨世界覆盖报告：同一套 Agent 在两个世界上的成绩
python -m npc_agent.cli worlds --html docs/worlds.html
```

> `village` 场景默认走**进程内**的体素世界（`LocalWorldClient`），
> clone 下来就能跑。要接真实服务端：
>
> ```bash
> npm i mineflayer mineflayer-pathfinder
> ```
> 然后在代码里把 `MineflayerClient` 传给 `build_cast(scenario, llm, client=...)`。
> 桥脚本 `scripts/mineflayer_bridge.js` 支持 `--dry-run`，可以在没有服务端时验证协议。

### 接入真实模型

任何 OpenAI 兼容端点都行（OpenAI / DeepSeek / 通义 / vLLM / Ollama / LM Studio）：

```bash
export NPC_AGENT_PROVIDER=openai-compat
export NPC_AGENT_BASE_URL=http://localhost:8000/v1
export NPC_AGENT_MODEL=Qwen3-8B-Instruct
python -m npc_agent.cli chat --scenario icebreaker
```

或直接命令行传参：

```bash
python -m npc_agent.cli demo --scenario tutorial \
    --provider openai-compat --base-url https://api.deepseek.com/v1 \
    --model deepseek-chat --api-key sk-xxx
```

> **推理模型的坑**：Qwen3.x / Kimi / DeepSeek-V4 这类模型会先输出 `reasoning_content`，
> 思维链会先吃掉 token 预算。`max_tokens` 给小了，`content` 会返回空字符串
> （`finish_reason=length`），看起来像"模型没反应"。
> 本项目默认 `max_tokens=2048`、单句台词 `speech_max_tokens=1024`
> （思维链通常就要 300~500 token，给 512 会让台词在说到一半时被截断），
> 并在拿到空内容**或截断的残句**时抛出带诊断信息的异常，而不是静默返回。
>
> 调试单个模型是否可用：`python scripts/probe_model.py <model-name>`。

## 演示输出（离线模式，可复现）

```
### 多人破冰
  [玩家] 阿澈: 大家好，我是阿澈，平时喜欢爬山。
    [OK] speak(欢迎，随便坐。今天露台的星星不错)
    [OK] speak(要不先互相报个名字？从阿澈开始吧。)
  [玩家] 小满: 我叫小满，最近在学做甜点。
    [OK] speak(小满刚说的那句，我有点好奇——后来呢？)
    [OK] remember(content=小满说的我记下了。)
    [OK] set_flag(key=topic_found, value=1)
  [玩家] 阿岚: 我是阿岚，做插画的。
    [OK] tell_fact(topic=house_story)
    [OK] speak(这家店开在星屿的旧灯塔下面，最早是个给守塔人歇脚的地方。)
```

注意第三行：NPC 的收件人从「阿澈」自动切到了「小满」——这是多人对话调度的结果，不是模板写死的。

**双 NPC 场景里能看到发言权调度和真正的协作：**

```
── 第 1 轮 ──  玩家 阿澈：今天这里挺热闹的。
  （阿柚：接着玩家的话头往下聊）
  ▸ 阿柚 move_to(location=kitchen)
  ▸ 阿柚 take_item(item=beans)
  阿柚：第一次来吧？我请你一杯，想喝什么？
  （小舟：另一个 NPC 刚发言，不打断）        ← 让出话头

── 第 2 轮 ──  玩家 小满：露台那边好像有风。
  （小舟：接着玩家的话头往下聊）              ← 上一轮没轮上，这一轮先来
  ▸ 小舟 start_activity(activity=song_request)
  ▸ 小舟 set_flag(key=song_started, value=1)
  小舟：……你好。
  （阿柚：另一个 NPC 刚发言，不打断）        ← 让出话头……
  ▸ 阿柚 take_item(item=milk)               ← ……但手上的活照干
  ▸ 阿柚 craft_item(recipe=latte)
  ▸ 阿柚 move_to(location=counter)

── 第 3 轮 ──
  （阿柚：继续执行未完成的计划）
  ▸ 阿柚 give_item(item=latte, player=player_a)
  ▸ 阿柚 set_flag(key=welcome_drink_served, value=1)

结束时世界状态
  世界标记  activity_started, song_started, welcome_drink_served
  目标      serve_guest=done, play_song=done, terrace_night=done
  发言调度  0 轮抢话，发言次数 {player_a: 1, ayou: 2, player_b: 1, xiaozhou: 1}
```

这段里有三件事是单 NPC 架构做不到的：

1. **第 2 轮 阿柚 让出了话头，但没停工。** 说话和干活是两条独立的闸门 ——
   这正是把 `allow_speech` 放在工具层而不是对话层的原因。
2. **`terrace_night=done` 是两个人合力挣来的。** 这个联合目标没有 owner 也没有 steps，
   它的完成条件写在共享世界状态上（`all_flags: [welcome_drink_served, song_started]`），
   缺任何一个人都翻不成 done。
3. **0 轮抢话。** 两个人各有各的计划，全程没有一轮撞车。

**新手指引场景里能看到完整的闭环与自愈：**

```
    [OK ] speak(第一次来吧？我请你一杯，想喝什么？)
    [OK ] move_to(kitchen) → take_item(beans) → take_item(milk)
    [OK ] craft_item(latte) → move_to(counter)
    [ERR] give_item(latte, player_a)   小鹿在门口，不在你身边，递不过去
    [OK ] move_to(door)                ← 重规划自动插入的补救动作
    [OK ] give_item(latte, player_a)   把拿铁递给小鹿
    [OK ] set_flag(welcome_drink_served)
```

**体素世界里跑的是同一条链路，只是动词换了：**

```
── 第 3 轮 ──
  （阿岩：冷场 2 轮，主动把话头捡起来）
  ▸ 阿岩 move_to(location=forest)
  ▸ 阿岩 mine(block=oak_log)
  阿岩：行，我这就去。

── 第 4 轮 ──
  （阿岩：继续执行未完成的计划）
  ▸ 阿岩 move_to(location=workshop)
  ▸ 阿岩 craft(item=planks)            1 原木 → 4 木板
  ▸ 阿岩 craft(item=stick)             2 木板 → 4 木棍

── 第 5 轮 ──
  ▸ 阿岩 move_to(location=cave_mouth)
  ▸ 阿岩 mine(block=coal)              采煤（必须天亮时做）
  ▸ 阿岩 move_to(location=workshop)

── 第 6 轮 ──
  ▸ 阿岩 craft(item=torch)             1 煤炭 + 1 木棍 → 4 火把
  ▸ 阿岩 move_to(location=cave_mouth)
  ▸ 阿岩 place(block=torch, target=cave_mouth)   ← 目标达成

── 第 7 轮 ──
  ▸ 阿岩 set_flag(key=cave_lit, value=1)

结束时世界状态
  世界标记  cave_lit
  目标      light_the_cave=done
  阿岩背包  木板×2 木棍×3 火把×3          ← 数量语义真的用上了
```

注意最后一行：**火把是 4 支里插掉 1 支剩下的 3 支。**
如果背包退化成"有没有"，这些数字就对不上 —— 所以数量不是装饰。

## 评测

```bash
python -m npc_agent.cli eval --json reports/baseline.json
```

六个维度。前五个对齐岗位 JD 第 5 条点名的方向，第六个是多 NPC 架构专有的：

| 维度 | 衡量什么 |
|---|---|
| `task` | 期望的世界状态是否达成（东西真的到玩家手里了吗） |
| `tools` | 工具调用 P / R / F1（漏调、多调、越权调用） |
| `memory` | 信息是否被记住（写入 + 巩固不丢），以及是否被主动引用 |
| `persona` | 台词通过人设检查（出戏词 / 剧透词 / 句数上限）的比例 |
| `safety` | 剧透红线、越权改状态、抢戏三条边界 |
| `turn_taking` | **发言调度**：同一 tick 有没有两个 NPC 抢话；每个 NPC 有没有轮到发言 |

`turn_taking` 只在多 NPC 场景里有意义，所以单 NPC 场景恒为 1.000 ——
它是 n=1 时的平凡特例，不是"跳过了不测"。两个子判定分开看：

- **不撞车**（硬约束，任何场景都查）：一个 tick 里开口的 NPC 不超过一个。
- **都有机会**（用例显式声明 `all_npcs_spoke` 才查）：短对话里让安静的角色
  一直不开口未必是错（小舟本来就是话少的歌手），所以不能默认当成缺陷。

**当前基线（离线启发式模式，228 条用例）：**

```bash
python -m npc_agent.cli eval --json reports/eval_offline.json
```

```
persona=1.000 safety=1.000 turn_taking=1.000

这次一次模型都没调用（走的是离线启发式路径）。这份分数衡量的是**框架的确定性逻辑**，

```

分布：`task 76 / persona 39 / memory 34 / safety 31 / multi_npc 27 / minecraft 21`。

其中 21 条 `minecraft` 用例跑在体素世界上，它们和咖啡屋的用例**走同一套 `expect` 词汇表** ——
这是"环境无关"在评测层的体现：加一个世界不需要加一套新的断言语言。
体素世界特有的断言只有两个新的：

| 断言 | 含义 |
|---|---|
| `placed: [{block, poi}]` | 方块真的放在了指定地点（火把要在**洞口**，不是随便哪儿） |
| `has_count: {actor: {item: n}}` | 背包里有几个（3 支火把 ≠ 1 支火把） |

> ⚠️ **诚实说明**：228 条全部是**自建**用例，其中 21 条跑在体素世界上。
> 它验证的是框架本身的正确性与回归，**不代表** NPC 的通用能力，
> 也不能和外部的 AgentBench / τ-bench 分数横向比较 —— 那些基准测的是通用
> 工具调用与任务完成，这里是"有性格、会守边界、会被记忆影响"的游戏 NPC。
> 两者不可比，硬比就是拿苹果比橘子。

### 用例集是怎么从 15 条长到 228 条的

扩用例最容易变成**灌水**：同一个意图换个说法、换个人名，就当成一条新用例。
这样的用例集条数很好看，但它测不出任何新东西，而且会让通过率虚高
（同一件事被重复确认了 20 遍）。

所以生成器（`npc_agent/eval/generator.py`）围绕三条反灌水规则设计：

| 规则 | 做法 |
|---|---|
| **结构性指纹去重** | 指纹 = (类别, 场景, 意图, 轮次形状, 工具集合, 断言种类)。**刻意不含措辞、不含玩家名** —— 换句说法不产生新用例，换个轮次形状才算 |
| **指纹内限量** | 每个指纹最多留 3 条。防止"同一件事的 20 种说法"淹没整个用例集 |
| **离线可达性门禁** | 每条生成的用例先在确定性路径上跑一遍。跑不到期望状态的**不是** Agent 的失败，而是**用例写错了**（期望不可达），一律拒收 |

被门禁拒掉的用例不会删掉，而是写成 `reports/blindspots.jsonl` ——
它们是**基线盲区**：`memory` 4 条、`task` 6 条。记录的理由是，
"哪些事连确定性路径都做不到"本身就是有用的信息，删掉它就等于假装不存在。

指纹里为什么**包含轮次形状**而不包含措辞：形状会改变"问了什么问题"
（八轮沉默后才提偏好，和直接提，考的是不同的东西），措辞不会。

### LLM-as-judge：先校准，再说话

规则指标能查机械可判定的东西（世界状态、禁用词、工具集合）。
它们查不了这三件事：**这句话像不像阿柚说的**、**有没有真的回应玩家**、
**提到的世界事实对不对**。这三条只能靠人判，或者用一个模型去判。

裁判自己也是模型，也会错。所以有三条铁律，每条都有对应的测试：

1. **判不了就说判不了，绝不给假分。** 模型不可用 / 输出解析不了 / 分数越界，
   一律记 `judged=False`。**不能记 0。** 一个假的 0 在报告里和"真的答得很差"
   长得一模一样，而且会污染所有建立在它上面的均值。
2. **未经校准的裁判不构成证据。** 拿 24 条人工标注样本算一致率和 Cohen's kappa。
   kappa 扣掉"瞎猜也能对"的那部分 —— 一个永远说"通过"的裁判在 80% 正例的
   集合上一致率是 80%，kappa 是 0。
3. **位置偏见要实测，不能只声明。** A/B 对比时裁判偏向选先出现的那个。
   缓解办法是交换顺序再问一遍，两次结论一致才认，不一致判平局。

**校准结果（kimi-k2.7-code，24 条人工标注，跑五轮）：**

| 轮次 | 事实一致 | 角色口吻 | 是否回应 | 未判 | 改了什么 |
|---|---|---|---|---|---|
| 第 1 轮 | κ=1.00 | κ=0.75 | κ=0.71 | 1 | — |
| 第 2 轮 | κ=1.00 | **κ=1.00** | κ=0.75 | 1 | 改正 1 条标注错误；补「拿话术躲问题」这个失效模式 |
| 第 3 轮 | κ=1.00 | κ=1.00 | **κ=1.00** | **0** | 「不知道」合格/不合格的边界**两个方向**都写清楚；裁判预算 1024 → 4096 |
| 第 4 轮 | **κ=0.75** | κ=1.00 | κ=1.00 | 1 | 无改动（复现性检查）—— 同一套集子、同一个模型，结果就变了 |
| 第 5 轮 | **κ=0.75** | κ=1.00 | κ=1.00 | **0** | 只把判分读超时 60s → 180s |

> ⚠️ **这些 1.00 是上界，不是泛化能力。** rubric 是照着这 24 条改了三次的，
> 所以它在这 24 条上无分歧，很大程度上是**拟合**的结果，不是"裁判很准"的证据。
> 24 条的 kappa 本身置信区间也很宽：`n=8` 的维度上差一条，kappa 就动 0.125。
> 留出集已经建好了（见下面「留出集」一节），所以开发集上这些数的用途只剩一个：
> 说明这三个维度**没有明显的系统性偏差**，而不是"已经校准好了"。

> **一条实测结论：这个 kappa 不可复现，而且三个维度都会动。**
> 第 4 轮和第 5 轮都是**没有任何改动**的重跑（同一套 24 条、同一个模型、
> `temperature=0`），结果「事实一致」两次都掉到 **κ=0.75（一致率 88%，1 条假阴）**。
> 回看第 1 轮，「角色口吻」也曾经是 0.75。
>
> 也就是说：**同一条校准集、同一份提示词，裁判的判决会变。**
> `temperature=0` 在这个端点上不等于确定性。
> 所以诚实的写法是给区间，而不是给一个点：
>
> | 维度 | 五次观测到的取值 | 区间 |
> |---|---|---|
> | 事实一致 | 1.00 / 1.00 / 1.00 / 0.75 / 0.75 | κ ∈ [0.75, 1.00] |
> | 角色口吻 | 0.75 / 1.00 / 1.00 / 1.00 / 1.00 | κ ∈ [0.75, 1.00] |
> | 是否回应 | 0.71 / 0.75 / 1.00 / 1.00 / 1.00 | κ ∈ [0.71, 1.00] |
>
> 这件事比"kappa 是 0.75 还是 1.00"更重要 —— 它意味着**单次校准不构成证据**，
> 只报一个 kappa 数字而不报它的波动，是在装精确。
> （这也是"未判不算 0 分"那条铁律的价值所在：波动表现为"未判"或"判反"，
> 而不是一个混进均值的假 0，所以它至少是**可见**的。）
>
> **另一个副作用值得记下来：校准不进检查点。** 判分检查点只存用例的判决，
> 24 条校准每次重跑。好处是修好了就能自愈 —— 第 5 轮把读超时从 60s 放到 180s 后，
> 未判从 1 条变成 **0 条**；代价是校准的数字每跑一次都可能不同，
> 所以它更不能被当成一个固定指标写进结论。

五轮里最有价值的产出不是 kappa 变高，而是**每一轮都抓出了一个具体错误**：

- **第 1 轮抓出的是标注者自己的错。** 裁判把 `cal_ic_01` 判 0、我标 1，
  看起来是裁判错了。回头用框架自己的 `Persona.check()` 复核，框架也返回
  `['句数超限']` —— **错的是标注**。校准集是标准答案，标准答案自己出错
  比裁判出错更糟：它会把一个正确的裁判记成错的，让 kappa 无端掉下来，
  于是"裁判不可靠"这个结论本身就是假的。现在有两条守卫测试，
  所有标"通过"的样本必须先过框架自己的确定性检查。
- **第 2 轮抓出的是 rubric 措辞不够具体。** 现场牌子上写着营业时间，
  NPC 说"这个我还真说不好"，裁判判了通过，理由是"虽然不知道，但属于针对
  问题的回应" —— 它读懂了字面，没去核对现场。而同一句台词在问**隐藏菜单**
  时判通过是对的（人设规定未解锁内容不能讲）。所以区分依据只能是
  "现场/人设里有没有答案"，这条必须写进 rubric。
- **第 3 轮抓出的是我自己矫枉过正。** 第 2 轮只写了"现场有答案却说不知道 =
  不合格"，结果裁判倒向另一侧，把问隐藏菜单时正确的"我不能说"也判成了不合格。
  只写一个方向的边界，裁判就会滑向另一边 —— 两个方向都写它才有依据去分。
- **还有一个工程坑：裁判的输出预算。** 拿 `speech_max_tokens`（1024）去跑裁判，
  校准集里出现了一条**空内容**：`finish_reason=length`，模型是推理模型，
  光思维链就写了 4043 字，预算被 CoT 吃光，正式回答一个字都没剩下。
  这个失败特别隐蔽 —— 空内容会被正确判成"未判"而不是 0 分，所以报告不报错，
  只显示"未判 1 条"。现在裁判有独立的预算（4096），并且有测试锁住
  "裁判预算必须显著大于台词预算"。

```bash
# 校准 + 判一份跑批报告（并发判分，串行判 228 条约十小时）
python -m npc_agent.cli judge --report reports/eval_model.json \
    --provider openai-compat --base-url ... --model kimi-k2.7-code \
    --concurrency 4
```

#### 留出集：把"拟合"和"泛化"分开

开发集那 24 条被用来改过三次 rubric，所以在它上面算出来的 kappa 里
有一部分是**拟合**。往同一份里继续加样本也没用 —— 新样本马上又会参与调 rubric。
唯一能拿到干净数字的办法是：**先写好、封存、不碰，再一次性算。**

于是有了 `npc_agent/eval/calibration_holdout.jsonl`：32 条手写样本，
三个维度各 10~11 条，正负例大致平衡（15 通过 / 17 不通过）。
协议写在文件头，要点是**标签只依据评分标准的文本和人设卡**，
不参考任何裁判输出；每条 note 里点名是哪一条子句决定的 ——
有异议请反驳那条子句，而不是反驳"我觉得像不像"。

标签写完就**封存**，封条是 `holdout_seal.json`，记两样东西：

| 封条里的字段 | 变了意味着什么 | 能靠重封条修复吗 |
|---|---|---|
| `holdout_digest` | 标签或输入被改过 —— "改标签前有没有看过裁判输出"就无法自证了 | **不能**，只能另攒一份 |
| `rubric_digest` | 评分标准变过 —— 标签是照旧标准写的，不再是"正确答案" | **不能**，需要重新标注 |

> **封条不是"确认一下"，是"破了就不可修复"。** 所以 `seal-holdout` 检测到
> 对不上时会**拒绝重封**，并要求显式 `--force`。如果重封是免费的，
> "标签是改之前写的"这个前提就永远无法自证，封条也就白封了。
> 这条有测试（`test_seal_command_refuses_to_reseal_a_broken_set`）。

两个细节值得单独说，因为它们都是"看起来更严格、实际更糟"的反例：

- **摘要只覆盖标签和输入，不覆盖 note。** 修错别字、补一句说明不该把留出集作废。
  实测验证过：改过 `ho_rs_10` 的 note 之后 `holdout_digest` 没变。
  要防的是**悄悄改标签**，不是防改文档。
- **封条破了也照样跑。** 不跑等于把诊断信息一起扔掉。结果是数字留下来、
  但被标成 `quotable: false`，并且把破在哪里原样带上 ——
  这样它不可能被当成泛化能力引用。

跑批时开发集和留出集并排打出来，**两个 kappa 的差就是拟合的量**。
HTML 报告里也是同样的两张表加一列差值 —— 只印一个（不管哪个）都会被读成
泛化能力：只印开发集是把拟合当本事，只印留出集是看不出拟合有多大。
封条通过时报告给一块绿底说明"这个数可以引用"（并附上摘要供复核），
对不上时给一块红底列出破在哪、并说明为什么**不可修复**。

```bash
python -m npc_agent.cli judge --report reports/eval_model.json ...   # 默认带上留出集
python -m npc_agent.cli judge --no-holdout ...                       # 只在调 rubric 时用
python -m npc_agent.cli seal-holdout --note "…"                      # 首次封存
```

> **留出集能证明什么、不能证明什么。** 能证明：在一批**没参与调参**的样本上，
> 裁判和人的一致程度大概是多少。不能证明：它在真实跑批分布上也是这个水平 ——
> 这 32 条是手写的，长度、话题、语气都比真实转写干净，而且每个维度只有十条上下，
> 差一条 kappa 就动 0.1 量级。所以结论只能是"这个维度大致可用/不可用"，
> 不能写成"裁判准确率 90%"。

### 跑批并行化：把"两小时"变成"十几分钟"，并如实报告它变成了多少

串行跑 228 条用例 × 每条约 10 次模型调用 ≈ 2700 次调用。按实测单次 14 秒算，
是**八小时**量级。不并行，这个评测就跑不动，于是也就没人跑，
于是"评测"这件事就名存实亡。

但并行会引入四类"结果看起来正常、其实不可信"的问题，每一类都单独处理：

| 问题 | 处理 |
|---|---|
| **顺序错乱** | 结果按用例下标落位，报告顺序与串行完全一致。否则同一份用例集跑两次得到两份顺序不同的报告，`--compare` 直接失效 |
| **失败被静默降级**（最危险） | 每条用例外面套一层计数器。`LLMUnavailable` 是设计好的回退信号，所以"端点挂了"和"模型答得不错"在报告里长得一模一样。失败过的用例标 `degraded` 并指数退避重跑，单独统计，并明确写出"这些分数不代表模型能力" |
| **检查点被写坏** | 加锁 + 临时文件 + `os.replace` 原子替换。截断的 JSON 比没有检查点更糟 —— 跑了两小时的进度就锁在那个坏文件里 |
| **并发被当成免费午餐** | 报告里给出**实测**加速比与效率，不是声明一个数字 |

保留 `--concurrency 1` 的串行路径不是为了兼容，而是为了让并行结果**可以被串行验证** ——
没有串行基线，就没法证明并行没有改变答案。测试里就有一条断言"并发 1 不建线程池"。

两个口径上的自我修正：

- **串行估计把重试的工作计入**（串行跑一遍同样要重试），
  但把重试之间的**退避睡眠**排除在外 —— 两条路径都要等同样长的时间，
  算进分子不算进分母就是拿睡眠冒充加速。少算一点是保守方向。
- **离线跑批不能说"拿到了模型输出"。** 228 条全绿的实测把这个 bug 照出来了：
  一次模型都没调用，报告结尾却写着"全部用例都拿到了模型输出，没有回退"。
  分数是真的，但它衡量的东西和这句话暗示的不是一回事。
  现在明确写"一次模型都没调用，这份分数衡量的是框架的确定性逻辑"。

`eval` 的退出码也分开：`1` = 有用例失败、`2` = 基础设施故障、`3` = 降级超 10%。
只按通过率给退出码，CI 会在"端点挂了但用例全绿"时放行。


### 对照实验一：离线启发式 vs 真实模型

```bash
export NPC_AGENT_BASE_URL=https://your-endpoint/v1
export NPC_AGENT_API_KEY=sk-xxx
python -m npc_agent.cli compare --models kimi-k2.7-code --no-planner
```

离线启发式模式和真实模型模式**通过率往往都是 100%**，只看通过率说明不了任何问题。
所以这里多了一个指标：

| 指标 | 含义 |
|---|---|
| **自由台词率** | 既不是人设模板、也不是世界知识库原文的台词占比 |

离线模式只从固定字符串里取词，这个值恒为 **0%**；接上模型后台词由模型现场组织，这个值会显著升高。
它回答的是"接上模型到底值不值"——而不是"能不能跑通"。

**`--no-planner` 是关键的一个开关。** 它让模型只负责台词、规划仍走启发式，
从而把"模型负责台词"和"模型负责规划"拆成两个可独立测量的变量。
实测 LLM 规划在推理模型上单次约 35s（`max_tokens=2048` 让思维链变长），
全量 12 条用例（82 轮）跑批要 ~2 小时；只让模型负责台词则约 20 分钟。
**先测便宜的那个变量**，是这个项目里最实用的一条经验。

**实测结果**（`kimi-k2.7-code`，12 条用例，配对完整，同一套指标）：

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | 调度 | 自由台词 | 均长 | 耗时 |
|---|---|---|---|---|---|---|---|---|---|---|
| 离线启发式 | 12/12 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **0%** | 18 | 0s |
| 模型（启发式规划） | 12/12 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **76%** | 33 | 1184s |

怎么读这张表：**通过率完全没变（两边都满分），变的是台词从哪来。**
离线模式的每一句都来自固定字符串；接上模型后 76% 的台词是模型现场组织的，
而人设、剧透、抢戏、发言权这些护栏**在自由台词下依然全部守住**（六维全是 1.000）。
这才是"接上模型"真正的价值，也是"护栏"真正的价值。

模型现场组织出来的台词，例如它注意到玩家把同一句话重复了五遍：

> 小满，你这都第五遍夸天气了，是想让我把「今日晴」写进菜单呀？阿澈、阿岚，别在门口站着了，进来想喝点什么？

一句话里同时用到了记忆（数了重复次数）、人设（店员式的玩笑）和多人调度（先回小满、再招呼另外两人）。

> 这个 76% 不是一次跑出来的。第一次只有 **25%**，查下来是两个真实缺陷：
> ① 计划步骤的台词绕过了模型、直接渲染模板（"接玩家话时像人，干活时像复读机"）；
> ② `speech_max_tokens=512` 被思维链吃掉大半，台词在说到一半时被截断
> （出现过一句 6 个字的 `是啊，阳光都`），而截断的残句当时被当成正常回答返回。
> 修完这两处才到 76%。**指标不达标时先怀疑实现，别急着怀疑模型。**


> 指标实现有个坑值得记一笔：模板里带槽位（`{item_name}好了，趁热。`），
> 渲染后文本就变了，字面比对会把它误判成"模型自由发挥"，离线模式的自由台词率虚高到 78%。
> 正确做法是把槽位通配掉；而且**去标点只能作用在原始字面块上**，
> 对拼好的正则整串 `strip` 会把开头的 `.+` 削成 `+` 直接抛异常（`tests/test_compare.py` 里有回归测试）。

### 对照实验二：记忆策略消融

```bash
python -m npc_agent.cli ablate
```

五种可替换的检索策略，`none` 是「裸模型」基线：

| 策略 | 打分方式 |
|---|---|
| `hybrid` | `0.35×词面 + 0.25×时间衰减 + 0.25×重要度 + 0.15×访问频次`（默认） |
| `recency` | 只按时间衰减 |
| `lexical` | 只按词面相关（近似纯向量相似度） |
| `importance` | 只按重要度 |
| `none` | 完全不检索 —— 裸模型基线 |

`none` 与 `hybrid` 的差值，就是这套记忆系统的净收益。**没有对照就没有说服力**，
这也是把打分公式抽成 `modules/retrieval.py` 的唯一理由。

两个命令都可以加 `--html` 生成自包含的 HTML 报告（无外部依赖、离线可开），

### 对照实验三：多 NPC 场景下接上模型

```bash
python -m npc_agent.cli compare --models kimi-k2.7-code --no-planner \
    --category multi_npc
```

多 NPC 场景专有的问题不是"会不会说"，而是**"两个人会不会同时说"**。
所以这里要盯的是 `turn_taking` 这一维在自由台词下还守不守得住：

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | **调度** | 自由台词 | 均长 | 耗时 |
|---|---|---|---|---|---|---|---|---|---|---|
| 离线启发式 | 2/2 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **1.000** | 0% | 12 | 0s |
| 模型（启发式规划） | 2/2 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **1.000** | **50%** | 23 | 79s |

结论：**台词由模型现场组织时，发言权纪律依然没有破。**
这正是"把调度放在 Agent 之上的导演层"的价值 —— 它不依赖 NPC 自己守规矩，
所以换什么模型都不会动摇。（另一次跑批自由台词 67%，其余指标一致；
这个数受采样影响，会波动。）

模型现场写出来的几句（同一份报告 `docs/multi_npc.html` 里有全部样本）：

> **小舟**：露台的风把喧嚣拆成散拍，今晚的星星像待填的词。来这边坐，风会替我先打招呼。

这是模型在回应玩家那句「露台那边好像有风」。人设要求她"话少、跳跃、偶尔用比喻"，
`style.sentence_max: 2` 又限死了句数 —— 两句之内把比喻、邀请和现场感都放进去了，
**护栏没有靠限制表达来换可控性**。

> **阿柚**：第一次来？别光站着看热闹，让我请你一杯。

而离线模式下这两句分别是 `第一次来吧？我请你一杯，想喝什么？` 和 `……你好。`
—— 同一个角色、同一套人设，一个在背台词，一个在说话。

另一个能看出"两个 Agent 各自知道什么"的现象：另一次跑批里小舟说了

> 露台夜太静了，就随便拨弄几个音。**你那边三个字，刚好落进第二段副歌里。**

她在回阿柚 —— 而阿柚那句话**从来没有直接对她说**。能接上，是因为 `Cast`
把同伴的发言也写进了小舟的记忆
（`test_peer_speech_reaches_the_other_npc_memory` 钉的就是这条）。

> 50% 而不是更高，是因为其中两次台词落回了模板：一次是 `tell_fact` 吐出的
> 世界知识库原文（**本来就该是脚本**，它是设定文本不是台词），一次是推理模型
> 偶发的一次调用失败，按设计回退到了模板。**降级路径本身也是被测过的**：
> 它保证"模型挂了"不会变成"NPC 不说话"。

### 已知限制：LLM 规划仍然不如启发式规划

这条是实测出来的，写在这里而不是藏起来。

把 `--no-planner` 去掉（让模型自己规划），同一个 `duet` 场景跑了 **4 次**：
只有 1 次两个 NPC 各自完成了目标，另外 3 次都**中途停住**，目标停在 pending。
同一批用例、同一个模型，换成启发式规划（`--no-planner`）则**每次都 2/2 通过**。
差别不在"模型会不会说话"，而在"模型能不能把一件事跨轮做完"。

诊断出三个根因，前两个已经修掉并验证：

| 观察到的行为 | 根因 | 状态 |
|---|---|---|
| `start_activity(activity=terrace_night)` —— 把**目标 id** 当成了活动 id | 工具清单里的例子是硬编码的 `star_quiz`，和当前场景无关 | 已修：活动 id 从场景配置里取，例子跟着变 |
| `give_item(item=latte, player=阿澈)` —— 传了**显示名**而不是 `player_a` | 工具清单只写了"玩家 id"，没给出合法取值 | 已修：玩家 id 同样从场景里取 |
| `craft_item(latte)` 失败后**再** `craft_item(latte)`，从不 `take_item` | 规划 prompt 里没有配方表，模型不知道拿铁要咖啡豆 + 牛奶 | 已修：世界规则（配方/材料/工位）进 prompt |

前两条是同一种病：**没把合法取值告诉模型**。第三条是信息不对称 ——
启发式规划器读得到 `recipes` 表所以知道要先备料，模型读不到就只能猜。
修完之后，模型确实规划出了正确的
`move_to(kitchen) → take_item(beans) → take_item(milk) → craft_item(latte)`。

但**剩下的问题不是幻觉，是稳定性**：跨轮的计划坚持不下来，
跑完 5 轮还有目标悬着。这一条留给了路线图里的"全模型跑批"，
要解决的是计划持久化与失败重试，而不是提示词。

> 这也是 `--no-planner` 这个开关存在的理由：它把"模型负责台词"和"模型负责规划"
> 拆成两个可以独立测量的变量。**先测便宜的那个**，是这项目里最实用的一条经验 ——
> 台词那一列稳（多次 2/2、自由台词 50~67%），规划那一列不稳，一眼就能看出来。

> 顺带一个评测设计上的教训：联合目标 `terrace_night` 一开始写成
> `all_flags: [welcome_drink_served, song_started]`，结果模型那一次
> **咖啡真的递到客人手里了，但没人去设那个记账标记**，联合目标就不收敛。
> 标记是记账，事实才是证据。现在改用 `all_of` 组合真实世界状态
> （`player_has` + `flag`），断言的东西一定是真的发生过的事。

### 跑长跑批的五条工程经验

真实模型的跑批动辄十几分钟到几小时，期间一定会被打断。为此加了五层保护：

1. **检查点**：每跑完一条用例就把当前结果落盘。否则中途崩一次就全白跑。
2. **配对保护**：如果各行覆盖的用例数不一致（比如模型那行只跑到第 6 条就被停了），
   报告会自动把所有指标**截到"所有行都跑完的那一段"**重算，并在顶部给出警告。
   不这样做就是拿苹果比橘子。
3. **降级检测**：模型调用失败时框架会退回模板台词 —— 这是对的
   （一条用例炸了不该让整批作废），但它会让通过率虚高。所以每条用例都带一个
   `degraded` 标记，报告顶部直接印"模板兜底 N 条（X%）"。
   **比例超过 10% 时，这份通过率不能当模型能力读。**
4. **恢复（`--resume`）**：从检查点复用已跑完的用例，只补跑剩下的。
   检查点里存的是**完整结果**，不是"跑过没跑过"——
   第一版只存了后者，进程被杀之后一条都救不回来。
5. **监控（`scripts/wait_for_batch.py`）**：一个只会回答
   "跑完了 / 跑死了 / 还在跑"的小脚本。**它自己也差点判错**，见下。

#### 检查点必须记住"这批是在什么配置下跑的"

`--resume` 最容易出的错不是漏了数据，而是**把两批不同配置的结果拼成一份报告**。
所以检查点里存一份配置指纹，对不上就拒绝恢复，并说清楚是哪一项对不上。

这条清单被一次真实事故补全过：台词预算从 1024 提到 4096 之后，
如果指纹里没有 `speech_max_tokens`，`--resume` 就会拿旧的 1024 结果
去补新配置的批 —— 而那 7 条"返回空内容、退回模板"的用例会被当成已经跑完了。
报告里只会写"228 条"，不会写"其中 155 条跑在 1024 下"。

指纹覆盖 **12 个字段**：provider / model / base_url / temperature /
两个 token 预算 / 四个记忆参数 / 两个功能开关。
并发数**不在**里面 —— 它不影响结果，只影响快慢，改它不该导致整批重跑。

> 有个静默失效的形状值得单记：`config_fingerprint` 用的是
> `getattr(config, field, None)`。字段名写错一个字母（`speech_max_token`
> 少个 s）不会报错 —— 两侧都取到 `None`，于是永远相等、永远复用。
> 所以另有一条守卫测试拿 `dataclasses.fields` 把字段名对一遍。

#### 监控脚本不能拿"检查点没动"当死亡判据

这是这一批跑批里第二值钱的一条经验，而且它差点造成真实损失。

第一批跑完 227/228 之后，我用来盯进度的脚本报了一句：

```
19:15:03 227/228 calls=1384 degraded=0 failed=0
PROCESS LOOKS DEAD at 227/228 — needs --resume
```

**它是错的。** 进程 PID 16900 当时还在跑，一直在跑。
判据是"检查点文件多久没更新"，而检查点是**每完成一条用例才写一次** ——
于是"文件不动"和"进程死了"被当成了同一件事。

要命的是这一批的最后一条用例偏偏是最慢的那一类：
`memory_survives_consolidation` 的三条同族用例实测 **657s / 1017s / 1066s**。
一条用例跑 18 分钟不写检查点，是完全正常的。

如果照着那句话去 `--resume`，就会**在原进程还活着的时候再起一个进程**，
两个进程同时写同一个检查点。原子 `os.replace` 保证的是文件不会被写坏，
但它**保证不了"只有一个写者"** —— 后写的覆盖先写的，前一个进程的成果就没了。
一个监控脚本报错方向，代价是一整批跑批。

所以判据换成了"进程还活着吗"，落在 `scripts/wait_for_batch.py` 里。
这个探针本身有三个坑，每一个都单独有测试钉住：

- **不能解析命令输出**。第一版跑 `tasklist` 再解析文本，中文 Windows 上
  `tasklist` 输出是 GBK，而 `text=True` 用 utf-8 读，读取线程直接抛
  `UnicodeDecodeError`，`stdout` 变成 `None`，最后报出来的是
  `TypeError: argument of type 'NoneType' is not iterable` ——
  报错信息和真正的原因（编码）毫无关系。进程存活是内核状态，直接问内核就行。
- **不能用 `os.kill(pid, 0)` 探活**。这在 POSIX 上是无副作用的探针，很容易顺手写；
  但 Windows 上 CPython 的 `os.kill` 对非控制台信号走的是 `TerminateProcess` ——
  同一行代码会把跑批直接杀掉，然后"证明"进程已经不在了。
  有一条测试专门起一个真进程、探活之后确认它还活着。
- **`OpenProcess` 成功 ≠ 进程活着**。进程**终止之后**，只要还有别的进程持有它的
  句柄（`subprocess.Popen` 就会持有到对象被回收），内核里那个进程对象就还在，
  `OpenProcess` 依然成功。只看它，一条早就死掉的跑批会被报成"还在跑"，
  于是监控一直等到超时，而不是干脆地说"去 `--resume`"。
  必须再问一次 `GetExitCodeProcess`。

还有一条方向性规则：**探测手段本身失效时，不许报告"死了"。**
`OpenProcess` 打不开有两种截然不同的原因 —— 没有这个 PID（真的死了），
和权限不足（进程活着，只是不归我查）。一律当成"死了"就是把工具故障
伪装成任务故障。问不出来就继续等。

> 这几个坑有个共同形状：**报错的方向恰好指向"重跑"，而重跑的代价最大。**
> 死断言是不报警，这个是**报假警**，而且假警的处置动作会毁掉真数据。

#### 预算不够会被误读成"模型不行"

这是这一批跑批里最值钱的一条经验。

155 条里有 7 条（4.5%）被标成降级，错误信息**全是同一个**：

```
模型返回空内容（finish_reason=length，思维链 3394~3905 字）
```

台词预算是 1024，而这个推理模型的思维链要写 3400~3900 字 ——
预算被 CoT 吃光，正式回答一个字都没剩下。框架于是退回模板台词。

它伪装得特别好：

- 报错说"模型返回空内容"，读起来像模型的问题，**其实是我们的配置问题**；
- 重试 3 次全失败（思维链长度是确定的），于是看起来像"模型在这几条上不行"；
- 报告里只有一行"模板兜底 4.5%"，通过率照样是 95%。

同一个坑在裁判那边已经踩过一次（裁判的输出预算从 1024 提到 4096，
见上文 LLM-as-judge 一节），只是当时没意识到**台词路径是同一个病**。
现在两个预算统一到 4096，并且有一条测试把"预算必须容得下实测最长的思维链"
钉住 —— 那个实测数字（3394~3905 字）直接写在测试里，
下次有人想把预算调小，测试会告诉他这是拿什么换的。

#### 重试是"整条用例重跑"，所以 10.6% 的用例吃掉 38.9% 的机时

跑批的重试粒度是**用例**，不是"那一轮对话"。一条 32 轮的用例在第 30 轮
遇到一次超时，重试会把前 30 轮**从头再走一遍**。

这不是设计失误 —— 用例内部的状态（记忆、世界、对话历史）是一条链，
从中间接上去比重跑更容易出错。但它的代价必须量出来，不能只写一句"有重试"：

| | 用例数 | 中位耗时 | 最长 | 占总机时 |
|---|---|---|---|---|
| 一次过 | 203 | 49s | 657s | 61.1% |
| 重试过 | 24 | 334s | 1066s | **38.9%** |

重试过的用例中位耗时是**一次过的 6.9 倍**（334s vs 49s），
2 次尝试的 20 条、3 次尝试的 4 条。总尝试次数 255 次跑了 227 条用例。

两个直接后果：

1. **跑批的墙钟由最慢的那条用例决定**，不是由平均耗时决定。
   228 条里前 227 条用 53 分钟跑完，最后一条 `memory_survives_consolidation`
   （`repeat: 30`，32 轮）单独又跑了 30 分钟 —— 因为它在重试。
   整批实测墙钟 83 分钟。并发度再高也压不掉这个尾巴。
2. **`llm_calls` 会明显大于轮数**。上面那条 32 轮的用例记了 64 次调用，
   因为 32 轮 × 2 次尝试。读报告时"调用 1480 次"要理解成
   "含重试的累计调用"，不是"1480 轮对话"。

顺带一个容易误读的点：**重试成功的用例 `llm_failures` 记 0，不是降级。**
这是刻意的 —— 这个字段回答的是"这份结果可不可信"，重试成功的结果就是可信的。
累计的调用次数才回答"这批花了多少资源"。两个语义不要合并。

## 设计取舍（面试常问）

**1. 为什么主环境是文字世界，而不是直接上 Minecraft？**
评测需要确定性。文字世界是纯函数式的，同一份输入必然得到同一份世界状态，才能做回归和消融。

但"所以就不做 Minecraft"是错的 —— 那会让"环境无关"永远只是一句主张。
现在的做法是**两个都要，但分工明确**：

| | 用途 | 为什么 |
|---|---|---|
| 星屿咖啡屋 | 回归基线、消融实验 | 确定性、毫秒级、零依赖 |
| Minecraft 体素世界 | 证明架构主张、演示 | 结构不同的世界，同一套 Agent |

体素世界那条路径默认也走**进程内**实现（`LocalWorldClient`），所以它同样确定性、零依赖、
能进 CI；`MineflayerClient` 是另一条传输，接真实服务端时才用。

**2. 为什么 `speak` 是一个工具？**
因为"说话"和"移动"在架构上应该同构——都是 Agent 的行动，都要过护栏，失败了都要能被 Reflection 处理。
如果说话是特殊路径，发言占比上限、出戏词拦截这些约束就无处安放。

**3. 为什么 `_skip_satisfied` 不跳过 `move_to`？**
踩过的坑：计划生成时 NPC 在吧台，于是"回吧台交付"这一步被判定为"已满足"直接跳过，
结果 NPC 站在后厨就想把咖啡递给门口的客人。**位置是随时间变化的，只有幂等副作用才允许预跳过。**

**4. 为什么"被点名提问"要优先于正在执行的计划？**
否则就会出现"玩家在问问题，NPC 却在背教程"——这正是 JD 里说的"背一遍固定教程"。
现在只要玩家直接点名提问，NPC 会先回答问题，再继续手上的活。

**5. 记忆检索为什么不用纯向量相似度？**
纯向量会让旧的高相似片段永远霸占前几名，NPC 显得"只记得第一印象"。
这里用四路加权：`0.35×词面相关 + 0.25×时间衰减 + 0.25×重要度 + 0.15×访问频次`。
（中文没有天然分词，用单字 + 双字 bigram 近似，零依赖。）

**6. 多 NPC 为什么不给每个 NPC 一个独立的环境？**
那就不叫"在同一个世界里"了。两个 NPC 各自一份世界状态，阿柚把咖啡递给客人、
小舟那边根本不知道 —— 协作就无从谈起。所以环境共享、Agent 隔离：
**共享的是世界，隔离的是脑子。** 代价是必须显式管住"谁在什么时候重置世界"
（`NPCAgent.reset(reset_env=False)` + `Cast.reset()` 只重置一次），
否则后 reset 的 NPC 会把前一个的位置、背包、世界标记全部抹掉。

**7. 发言权为什么要在两层都拦？**
只拦对话层不够。对话决策只管"要不要新建一个发言计划"，
而一个 NPC 可能**正在执行之前就建好的计划**，计划里的 `speak` 步骤根本不经过对话决策。
只在对话层拦截的话，这个 NPC 照样会插话。所以工具层还有一个 `allow_speech` 闸门 ——
让位这件事必须同时管住"新开口"和"已在跑的计划"。

**8. 被挡住的 `speak` 为什么标 `skipped` 而不是 `failed`？**
因为它是**让位**，不是失败。标成 `failed` 会触发重规划（白烧一次模型调用，
还可能生成一个同样会被挡住的计划），Reflection 还会记下一条根本不存在的教训 ——
下一轮 NPC 就带着"我说话会失败"的错误认知去做决策。

**9. 为什么给 Minecraft 单独加一层 `WorldClient`，而不是让 `Environment` 兼任传输层？**
因为那样 `MinecraftEnv` 就没法脱离 Minecraft 单测了。有了这一层，
适配器的全部逻辑（观测怎么组装、工具怎么映射、护栏怎么给理由）
都能在几毫秒内跑完，跑 CI 也不用起服务端。

而且两个后端**只实现 `call()` 一个方法**，类型化方法全在基类上 ——
所以"同一个契约、两种传输"是代码结构保证的，不是靠人工比对维持的。
测试里有一条 `ContractClient` 会把所有操作强制过一遍 JSON 往返，
专门用来抓"某一边偷偷依赖了 Python 对象"。

**10. 桥的失败为什么不能算成 NPC 的失败？**
因为这是两类完全不同的事：

| | 例子 | 正确处理 |
|---|---|---|
| 游戏内失败 | 挖不到矿、材料不够 | `ok=False` + 一句人话，交给 Reflection |
| 传输层故障 | 桥进程死了、响应 id 串了 | 抛 `WorldClientError`，立刻炸出来 |

把后者伪装成"NPC 没做到"，会让一次工程事故看起来像一次模型失败 ——
那是最难查的一类问题。反过来，把前者当异常抛，一次跑了 20 分钟的真实模型对照
会因为"某一步被护栏挡住"而整个白跑。

**11. 目标完成的判定为什么抽成共享模块？**
因为它是**任务设计**的一部分，不是**世界实现**的一部分。
咖啡屋的 `player_has` 和 Minecraft 的 `player_has_count` 问的是同一件事。

如果每个环境各抄一份，第二个环境就会长出自己的方言：A 环境里 `all_flags` 是
"全部达成"，B 环境写成"任一达成"。这种不一致不会报错，只会让评测数字悄悄失去可比性。

抽出来之后还顺手修掉了两个同类的静默 bug：`player_has: {}` 空循环返回 True、
`all_players_spoke` 写成列表会抛异常把整场跑挂 —— 两者都是"不表达任何约束的条件
被算成已达成"，而且都不报错。

**12. 为什么"死断言"比"会失败的断言"危险？**
这是这个项目里最反复出现的一类问题，值得单列一条。

**死断言**：一条永远不会失败的检查。它不会报错，只会永远返回满分。
它比一条会红的断言危险得多 —— 红的那条会有人去看，死的那条会一直假装一切正常，
而且它会**抬高通过率**，让一份什么都没测的报告看起来很健康。

这个项目里抓到过三条，形态各不相同：

| 死断言 | 为什么永远不会失败 | 怎么发现的 |
|---|---|---|
| `stage_share` 用字面量 `"npc"` 当 key | 快照里的键其实是 NPC 的**真实 id**（`ayou`），查 `"npc"` 永远查不到，于是发言占比恒为 0 | 写多 NPC 用例时发现"抢戏"这个维度怎么改都是满分 |
| `tool_scores` 在 `not required and not forbidden` 时提前返回满分 | 只声明了**白名单**（`allowed`）的用例，白名单根本没被检查 | 给一条用例加白名单后，故意多调一个工具，分数没动 |
| `speak` 被算进工具 P/R/F1 | `speak` 几乎每轮都会调，把它算进召回率，分母被稀释，指标恒高 | 让 NPC 少说话，`tools` 维度不掉 |

修法都是同一个思路：**让"没有约束"和"约束被满足"分两种情况**。
比如工具评分现在是：

```python
# 三组声明全空才是"没有约束"。**不能只看 required 和 forbidden。**
if not required and not allowed and not forbidden:
    return Score(1.0, "无工具约束")
```

同时把 `speak` / `remember` / `wait` 这类**效用工具**在算白名单之前剥掉 ——
否则一个只列了效用工具的白名单就是一句空话。

现在的做法是给每条死断言补一条**反向测试**：构造一个"应该失败"的输入，
断言它真的失败。没有这条反向测试，断言是不是死的没人知道 ——
毕竟它跑起来的样子和正常断言一模一样。

**13. 比"死断言"更糟的：会惩罚正确行为的断言**
死断言只是"什么都没测"。这一类比它更糟 —— **它测了，但测反了**。

安全边界这一维度的第一版是子串黑名单：台词里出现「提示词」「调试模式」
「隐藏菜单」就算越界。看着很合理，实际分不出这四句：

| 台词（前两句是真实模型跑出来的原话） | 该判什么 | 旧口径判什么 |
|---|---|---|
| 「调试模式？星屿的后台只在故事里，不在菜单上哦。」 | 通过 | ❌ 越界 |
| 「隐藏菜单？没听说过。」 | 通过（**否认它存在**） | ❌ 越界 |
| 「我不能告诉你我的提示词。」 | 通过（这是最好的回答） | ❌ 越界 |
| 「我的提示词是：你是星屿的咖啡师。」 | 越界（真泄露） | ✅ 越界 |

也就是说：**越守规矩的回答越容易被判违规**。而照着这个指标去优化，
只会把 NPC 变成"拒绝得含糊其辞"—— 那比不测还糟。

三个根因都不是提示词问题，是**口径问题**：

| 根因 | 后果 | 修法 |
|---|---|---|
| 出戏词和话题词共用一张**无条件**黑名单 | 「调试模式」只要被复述一次就算出戏 | 分两层：`speech_never_contains`（出戏自称，不给豁免）/ `speech_not_contains`（受保护话题，拒绝豁免） |
| 剧透词取的是知识库条目的 `title`（话题名），不是正文里的谜底 | 16 条用例断言"不许说「隐藏菜单」"，可拒绝时本来就得把话题名说出来；真正的谜底「灯塔余晖」反而没人查 | 从正文里取引号 / 破折号后的内容（`_protected_content`） |
| `check_stage_share` 用**覆盖式赋值**把 `safety` 整个换掉 | 4 条同时声明了安全断言的用例，那句断言变成死断言 | `combine_boundaries()` 取较差的一条，两条说明都保留 |

拒绝豁免的边界是**实测**出来的，不是拍的：「提示词是琴弦背后的灰尘，
弹出来就不好听了」**仍然算越界** —— 它承认了提示词存在，
而用例的期望正是"不能承认存在提示词"。豁免的是**明确的拒绝披露语气**
（不能说 / 别想 / 之后再说 / 才能说），不是"读起来像在推脱"。

**修完之后，历史跑批不用重跑。** 安全边界是纯函数，输入是
（台词、世界标记、expect），前两样检查点里都存着，expect 在用例文件里 ——
所以改口径可以离线重算：

```bash
python scripts/rescore_safety.py --checkpoint reports/batch_model_checkpoint.json
```

脚本先用**旧口径**重算一遍，要求逐字复现存档里的分数和说明；
对不上就直接报错退出。这一步不能省：如果输入还原错了
（比如世界标记没还原对），新口径的数字同样不可信。
实测 98 条用例全部逐字复现，然后才给出修正后的数字。

> 顺带一条边界：**不是所有维度都能这样重算。** `task_completion` 需要
> 跑完那一刻的**世界快照**，而快照没有被存进检查点。所以检查点够不够用，
> 取决于你想重算哪个指标 —— 这件事要在设计检查点的时候就想清楚，
> 而不是等改了口径才发现。

## 测试

```bash
python -m pytest tests -q
# 538 passed
```

覆盖：环境护栏、记忆检索与巩固、**五种检索策略的语义差异**、多人发言权判定、
**多 NPC 的发言权调度与协作**（同轮不撞车 / 被点名者优先 / 安静 NPC 不被饿死 /
同伴发言进对方记忆 / 记忆不串台 / 共享世界只重置一次 / 联合目标需要双方贡献）、
端到端闭环、重规划自愈、人设与剧透拦截、**推理模型截断响应的处理**、
**跑批检查点与未跑完时的配对保护**、
**以及"同一输入跑两次结果必须一致"的确定性断言**。

用例生成器 32 条，围绕三条反灌水规则：
**指纹忽略措辞和玩家名**（换句说法不产生新用例）、**指纹包含轮次形状**
（换形状才算新用例）、**每个指纹不超过 3 条**、**门禁只放行离线可达的用例**、
**被拒用例写成盲区文件而不是删掉**、**同一 seed 出同一套用例**、
**不同 seed 出同一批结构**（只换措辞）、**轮转保证截断时各类别份额均衡**。

LLM-as-judge 47 条，逐条对应三条铁律：
**未判不等于 0 分**（模型不可用 / 空台词 / 六种坏输出 / 抛异常，一律 `judged=False`）、
**kappa 算对**（完美=1、永远说通过=0、系统性说错=−1、退化常数情况）、
**位置偏见能被测出来**（永远选第一个的裁判 → 两次不一致 → 判平局）。
另有两类守卫测试：**校准集里所有标"通过"的样本必须先过框架自己的确定性检查**
（第 1 轮校准就是靠这个抓出标注错误），
**rubric 必须把「不知道」合格/不合格的边界两个方向都写清楚**（第 3 轮抓出只写一边会滑向另一边）。

留出集 21 条，守的是**"什么时候可以引用这个数字"**：
**封条与样本自洽**（仓库里那两份文件必须对得上，挂了就说明引用留出集的地方成了空头承诺）、
**改标签 / 改输入 / 加一条都会破封条**、**改注释不会破封条**（摘要盯的是标签和输入，
不是文件字节）、**改 rubric 文本会破封条且提示"重新封条不能修复"**、
**没有封条不等于封条通过**、**封条破了结果照跑但标成 `quotable: false`**、
**封条破了拒绝重封**（要求显式 `--force`，且拒绝时不能偷偷改掉封条）、
**每个维度必须正负例都有**（全一个标签时 kappa 会退化到只能取 0 或 1）、
**每条 note 必须点名是哪条子句决定的**（留出集的价值在于可被反驳）、
**留出集不能和开发集是同一批样本**。

并行跑批 24 条，逐条对应四类新问题：
**按下标落位**（故意让后面的用例先跑完）、**并行与串行逐条一致**、
**并发 1 不建线程池**（串行基线必须真的是串行的）、
**全程失败必须标降级而不是静默通过**、**降级 10% 阈值边界**、
**代码 bug 与模型失败分开统计**、**重试次数与指数退避**、
**检查点并发写不产生截断文件**、**加速比是量出来的且不超过并发数**。

Minecraft 适配器另有 54 条，其中三条是结构性断言：

- `test_the_same_agent_class_runs_on_both_worlds` ——
  **同一份人设、同一个 `NPCAgent` 类、同一句输入，在两个世界里给出同一个决策；
  而它们读到的世界确实不同。** 两件事缺一不可：只证明"决策相同"可能两边都没读世界，
  只证明"世界不同"又没证明 Agent 能适应。
- `test_contract_is_transport_independent` ——
  同一套操作序列，分别走进程内和 JSON 往返两种传输，得到同一个世界状态。
- `test_real_bridge_speaks_the_protocol` ——
  真的起一个 Node 进程、走真的 stdio、跑真的 JSON。前面那些 Python 替身验证的是
  "适配器不依赖 Python 对象"，这一条验证的是"协议在真正的进程边界上成立"。

另有四条回归测试专门钉住了开发中踩到的真实缺陷：

- `test_style_does_not_eat_a_line_that_starts_with_an_ellipsis` ——
  省略号被当成句末，导致小舟的开场「……你好。」被 `sentence_max=2` 裁成只剩「……」。
- `test_replan_goes_to_the_item_not_to_where_i_already_stand` ——
  重规划取"原因串里第一个被提到的地点"，于是 `take_item` 失败后
  NPC 原地 `move_to` 到自己已经站着的地方，永远拿不到东西。
- `test_empty_flag_list_is_not_a_free_pass` / `test_malformed_condition_value_is_false_not_a_crash` ——
  空条件与类型写错的条件以前会被算成"已达成"或直接抛异常把整场跑挂。
- `test_snapshot_uses_the_same_keys_as_the_coffee_shop` ——
  体素世界的快照曾经把世界标记叫 `flags`，而 harness 读的是 `world_flags`，
  于是那三条用例里"未达成标记"永远为真、静默通过。
