# ai-npc-agent

> 面向游戏场景的**可控** AI NPC 智能体框架 —— 让 NPC 不只是会说，而是真的会玩。

`Planning` · `Memory` · `Tool Use` · `Action` · `Reflection` · `Persona` · `State Tracking`

| | |
|---|---|
| **零配置可跑** | 没有 API key 时自动回退到内置启发式策略，clone 下来就能端到端跑通 |
| **换世界不用改 Agent** | 同一份 Agent 代码跑在自研文字世界和 Minecraft 体素世界上，一行没改 |
| **有评测，不只有演示** | 235 条自建用例、六个维度、可复现的离线基线；还有"注入缺陷必须掉分"的敏感性测试 |
| **有自测入口** | `python -m npc_agent.cli studio` 起一个本地网页，点着就能看 NPC 怎么想、做了什么 |

**本 README 的组织方式**：项目背景 → 方法框架 → 实现思路 → 实验结果 → 不足与总结。
想先看"到底有多好、哪里不行"，直接跳 **[五、不足与总结](#五不足与总结)**。

## 一、项目背景

### 1.1 问题：演示只要一天，做成玩法要过七道坎

把一个大模型 API 接进游戏，只能完成最前面的演示。真正做成稳定玩法会撞上这些问题：

| 失败模式 | 后果 | 本项目的应对 |
|---|---|---|
| NPC 说完话没有行动 | "看起来会说，实际上不会玩" | Tool Use + 环境护栏：语言动作和世界动作走同一条执行路径 |
| 忘记前面聊过的事 | 人设崩、剧情断裂 | 分层记忆（episodic / semantic / reflection）+ 混合检索 + 巩固 |
| 被玩家问住就顺着跑偏 | 剧透、出戏 | Persona 的知识边界 + 剧透红线 + 工具层拦截 |
| 多人同时说话就乱 | 抢戏、冷场 | 发言权与收件人判定（多玩家并发 + 主动发起话题） |
| 同一个错误反复犯 | 稳定性差 | Reflection 把失败原因变成教训，重规划时插入补救动作 |
| 两个 NPC 同时开口 | 两行字挤在一起，比单个 NPC 说错话更伤体验 | Cast 导演层统一收发发言权，一个 tick 只放一个人说话 |
| 换一个游戏就要重写 Agent | 架构不可复用，每个项目重复造轮子 | Environment 抽象 + WorldClient 契约，换世界只写适配器 |

### 1.2 为什么现成框架不够用

这不是"再包一层 LangChain"能解决的，原因有三条，每条都对应上面一个失败模式：

1. **要的是可控性，不是能力上限。** 什么时候**不说话**、什么话**不能说**、失败了怎么**归因** ——
   这类"边界"在通用框架里没有位置，而它们恰恰是 NPC 体验崩掉的地方。
2. **演示能跑 ≠ 可评测。** 只接模型的话，同一份输入两次跑出不同结果，
   "改了代码有没有变好"这个问题就永远答不上来。
3. **没有额度就复现不了。** 一个需要 API key 才能验证的项目，
   别人（和三个月后的自己）都只能选择相信文档。

### 1.3 本项目的定位（读数字前请先读这一段）

> 一句话：**这个项目的价值不在于 NPC 说了什么，而在于它说完之后，世界真的变了。**

三条边界声明，后面所有数字都带着它们：

- 这是一套**自建的小样本评测**（235 条用例），**不是公开基准**，不能把这里的数字说成公开基准成绩；
- **离线满分 ≠ 模型能力**。离线路径一次模型都没调用，它衡量的是框架逻辑自洽与护栏有效；
- 真实模型的读数**已经饱和**（99.6%），信息量在"框架能跑通完整跑批"这件事本身。

完整的边界清单见 [五、不足与总结](#五不足与总结)。

## 二、方法框架

### 2.1 一条链路

整个框架围绕一条链路组织，每个模块负责其中一环：

```
语言  ──▶  决策  ──▶  游戏动作  ──▶  世界状态
 ↑                                        │
 └──────────── 反馈：失败归因 → 教训 ──────┘
```

**关键点**：链路是**闭合**的。世界状态的变化会回到记忆与反思里，
所以下一轮决策看得见"我上次做了什么、结果如何"。

### 2.2 架构

```
                    ┌──────────────────────────────────────────┐
   玩家发言 ───────▶ │  State Tracking   现场状态（谁在场/冷场多久）│
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Dialogue    该不该我说？对谁说？要不要主动开口 │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Memory      检索相关记忆（混合打分）        │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Planning    分解任务 / 继续未完成的计划     │
                    └──────────────────┬───────────────────────┘
                                       ▼
        ┌──────────────────────────────────────────────────────┐
        │  Tool Use   统一执行（speak / remember / 世界动作）      │
        │  Persona    出戏词·剧透词·句数上限 三道闸门              │
        └──────────────────┬───────────────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────────────┐
        │  Environment  世界护栏：位置 / 材料 / 白名单 / 知识解锁   │
        └──────────────────┬───────────────────────────────────┘
                           ▼
                    ┌──────────────────────────────────────────┐
                    │  Reflection  失败归因 → 写成教训 → 下次重规划 │
                    └──────────────────────────────────────────┘
```

### 2.3 七个模块各自解决什么

| 模块 | 解决什么问题 | 你能看到什么 |
|---|---|---|
| **State Tracking** | 谁在场、谁说了话、冷场多久 | 控制台右侧实时状态；玩家与同伴 NPC 分开记账 |
| **Dialogue** | 该不该我说？对谁说？要不要主动开口 | 每轮都印出**决策理由**（"点名了我" / "冷场 2 轮，主动把话头捡起来"） |
| **Memory** | 检索相关记忆 | 分层记忆库计数 + 本轮**用到了哪几条记忆**（`m0001`…） |
| **Planning** | 分解任务、继续未完成的计划 | 工具调用序列，以及失败后的重规划 |
| **Tool Use** | 把决策落成世界动作 | 每个动作 `ok/失败原因`，被护栏挡下时会**明说** |
| **Persona** | 不出戏、不剧透、不啰嗦 | 句数上限、出戏词与剧透词三道闸门，违规会记进转写 |
| **Reflection** | 别在同一个坑里摔两次 | 失败归因写成教训，下一次规划时插入补救动作 |

多 NPC 场景下还有一个站在所有 NPC 之上的**导演**（`cast.py`）：
被点名者优先，否则轮转；一个 tick 只放一个人说话；没说话的人也会把同伴的话**记下来**。

### 2.4 两个架构决策

这两个决定是后面"可评测"和"可复用"的前提：

1. **环境无关**。Agent 完全不知道自己在咖啡屋、Minecraft 还是别的引擎里，只面对
   `observe()` 和 `dispatch()`。换世界 = 写一个新的 `Environment` 子类，Agent 一行不改 ——
   这句话有**两个结构完全不同的世界**可以对照验证，不是文档里的一句口号。
2. **模型可选**。没有 API key 时自动回退到内置启发式策略。这让评测**可复现**
   （同一份输入必然得到同一份输出），也让"换模型"变成一行配置。

## 三、实现思路

### 3.1 快速开始

需要 Python 3.11+。**不需要任何 API key**，也不需要联网。

**最直观的入口：自测控制台**

```bash
pip install -r requirements.txt
python -m npc_agent.cli studio
```

浏览器会自动打开一个本地网页（默认只绑 `127.0.0.1`），四个页签：

| 标签 | 能做什么 |
|---|---|
| ① 对话演示 | 选场景和身份说话；右边实时显示**世界状态 / 记忆库 / 发言统计**；「空转一轮」看 NPC 会不会自己找事做 |
| ② 跑评测 | 跑六维离线基线，看每个维度、每个类别的通过率，以及**没过的是哪几条、为什么** |
| ③ 变异测试 | 往 Agent 里**注入一个故意的缺陷**再重跑 —— 评测必须掉分 |
| ④ 报告门户 | `docs/` 里全部报告的入口，带**覆盖多少条**（12 条和 235 条不是一个量级） |

> 它**不重写任何逻辑**，只是把 `Cast` / `EvalHarness` / `run_sensitivity` 包了一层 HTTP，
> 所以网页上的数字和命令行**必然一致**（这件事有差分测试钉住）。
> 配了 `NPC_AGENT_PROVIDER=openai-compat` 会自动切成真实模型。

**命令行**

```bash
# 看一段完整的多玩家交互（无需任何 API key）
python -m npc_agent.cli demo --scenario icebreaker

# 看两个 NPC 在同一个世界里协作（多 Agent）
python -m npc_agent.cli demo --scenario duet

# 自己上手对话
python -m npc_agent.cli chat --scenario tutorial

# 跑评测，出数字
python -m npc_agent.cli eval

# 同一个 Agent 跑在 Minecraft 体素世界里（零依赖，不需要装 Minecraft）
python -m npc_agent.cli demo --scenario village

# 看工具清单 / 场景与人设
python -m npc_agent.cli tools
python -m npc_agent.cli info
```

场景（破冰 / 新手指引 / 游戏主持 / 双 NPC 协作 / 村庄）都是 YAML，**新增一个人设或场景不用改代码**。

**接上真实模型**

```bash
export NPC_AGENT_PROVIDER=openai-compat
export NPC_AGENT_BASE_URL=https://<你的端点>/v1
export NPC_AGENT_API_KEY=<你的 key>
export NPC_AGENT_MODEL=<模型名>
```

任何 OpenAI 兼容端点都可以。不配置时全部走离线启发式路径。

### 3.2 六个关键实现决策

**① 语言动作和世界动作走同一条执行路径。**
`speak` 和 `set_flag` / `give_item` 都是 `ToolRegistry` 里的工具，都要过同一套护栏
（人设边界、环境规则、发言权闸门）。所以"说了但没做"不会成为一类静默失败 ——
每个动作都带回 `ok` 与失败原因。

**② 离线确定性回退，让评测可复现。**
`RuntimeConfig.llm_provider` 默认 `"null"`。这不是"降级方案"，是**评测的地基**：
只有确定性的路径才能当回归基线。真实模型是**可插拔的上层**，不是前提。

**③ 人设三层闸门放在工具层，不在 prompt 里。**
出戏词、剧透词、句数上限都在 `Persona.check()` 里判定，`speak` 执行前拦截。
理由：prompt 是**请求**，工具层是**约束** —— 只有后者能被测试钉住。
违规会记进转写，所以"NPC 有没有出戏"是可观测的，不是靠人眼看。

**④ 发言权由导演层统一收放，不靠 NPC 自觉。**
多 NPC 场景里，`cast.py` 是唯一决定"这个 tick 谁能开口"的地方。
自己管自己的话，两个 NPC 都会觉得自己该说话 —— 这是多 Agent 最典型的翻车。

**⑤ 评测是可证伪的：六维 + 变异测试。**
六个维度（task / tools / memory / persona / safety / turn_taking）各自独立打分。
但"分数高"本身不是证据 —— 所以配了两层反向验证：
**注入已知缺陷必须掉分**（`sensitivity`），以及**量出评测的报警线画在哪**（`resolution`）。
一个从不失败的评测，和一个没有评测，在报告上长得一模一样。

**⑥ 报告分两类，这个分类被测试强制。**
「离线可复现」和「一次跑批的快照」**过期的方式完全不同**：
前者与代码不一致**就是说谎**（有逐字节新鲜度护栏）；
后者是历史读数，只作存档。分类写在 `npc_agent/eval/report_index.py`，
三处消费方（重生成脚本 / 过期护栏 / 报告门户）共用同一份清单，**能推导的别手抄**。

## 四、实验结果

> ⚠️ **先读这句**：下面第一份结果是**回归基线**，不是能力上限。
> 它证明的是"护栏在工作"，不是"NPC 很聪明"。每一份数字都标了**它的适用范围**。

### 4.1 离线基线：235 条自建用例，六个维度

```bash
python -m npc_agent.cli eval --json reports/eval_offline.json
```

```
通过率 235/235（100%）　各维度均值 task=1.000 tools=1.000 memory=1.000
persona=1.000 safety=1.000 turn_taking=1.000

跑批：235 条｜墙钟 <1s｜未调用模型（离线路径）
```

> 墙钟那一栏**故意不写死**（机器相关）。加配置解析缓存之前这里是 6s，
> 现在整个离线跑批的**串行估计**是 2s —— 见「诚实的局限」第 19 条。

用例分布：

分布：`task 80 / persona 39 / memory 37 / safety 31 / multi_npc 27 / minecraft 21`。

> ⚠️ **这份满分衡量的是框架的确定性逻辑，不是模型能力。**
> 离线路径一次模型都没调用 —— 它证明的是"护栏和评测彼此自洽"，
> 任何人 clone 下来都能复现。要测模型请加 `--provider` / `--model`。
> 这条数字**被测试钉住**：通过率、六个维度均值、用例分布都必须和实际跑出来的
> 逐字一致（墙钟那一栏除外 —— 它是机器相关的，钉它只会逼着文档写一个假值）。

**那这个满分有什么信息量？** 诚实的回答是：**在顶部几乎没有。** 三条独立证据：

| # | 实验 | 数字 | 说明 |
|---|---|---|---|
| 1 | 把**记忆整个模块**拿掉（消融 `none` 臂） | **229/235 = 97.4%** | 框架里最大的模块，只值 **6 条**用例 |
| 2 | 四种检索策略**互相比** | 全部 235/235，Δ=**0.000** | 评测**分辨不出**检索策略的差别 |
| 3 | 把计划按比例砍掉（剂量-反应） | 砍 **10%** → **223/235** | 报警线画在 **10%** |

第 2 条是一次**阴性结果**，我把它留在了报告里：一个分不清优劣的评测，
它的满分也不该被当成"优"。

### 4.2 四份对照实验

**① 记忆消融：记忆系统的净收益**

```bash
python -m npc_agent.cli ablate --html docs/ablation.html
```

五种检索策略（`hybrid` / `recency` / `lexical` / `importance` / `none`）。
前四种**完全一样**（235/235，Δ=0.000）；只有 `none`（等于没有记忆）掉到 229/235，
而且掉分**全部集中在 memory 维度**（−0.013 到 −0.026 通过率）。
另一个数：**自由台词只占 8%** —— 92% 的台词来自人设模板与世界知识。

**② 敏感性测试：满分不是"护栏从不报警"**

```bash
python -m npc_agent.cli sensitivity --html docs/sensitivity.html
```

往 Agent 里注入 6 个**故意的缺陷**（关掉记忆写入、关掉检索、关掉规划、
关掉发言权、让出戏词进转写……），评测**必须掉分**。**6 个全部被抓到。**

| 注入的缺陷 | 通过率 | 掉分 |
|---|---|---|
| 关掉记忆写入 | 85.1% | memory −0.147 |
| 关掉检索 | **97.4%** | memory **−0.013**（最弱的一处） |
| 关掉规划 | 59.1% | task −0.409 / tools −0.396 |
| 关掉发言权闸门 | 85.5% | turn_taking −0.145 |
| 出戏词进转写（×2 变体） | 0.0% | persona 全灭 |

这一测还真抓出一个覆盖缺口：**关掉检索只让 memory 维度动了 0.013**。
原因是那 37 条记忆用例里有 31 条断言的是"存储里有没有这条"，
只有 6 条断言"它有没有被说出来"—— 前者对检索是**结构性盲区**。

**③ 评测的分辨率：报警线画在哪**（`sensitivity` 回答不了的问题）

```bash
python -m npc_agent.cli resolution --html docs/resolution.html
```

`sensitivity` 是**二值**的（掉一个点就算抓到），所以它测不出灵敏度 ——
「只能发现整个模块被拔掉」和「能发现计划少走一步」在 **6/6** 上长得一模一样。
这里把剂量做成连续的：按比例 `k` 丢掉计划里的步骤。

| k | 0.0 | **0.1** | 0.3 | 0.5 | 0.7~1.0 |
|---|---|---|---|---|---|
| 通过率 | 1.0000 | **0.9489** | 0.7702 | 0.7064 | 0.5915（平台） |

**检出阈值 = 10%。** 两个自洽性检验：`k=1.0` 的 **0.5915** 与独立实现的
`planning_disabled` 变异 **0.591** 吻合（两条路径同一个口径）；
`k≥0.7` 出现平台（已无用例能完成目标）。

⭐ **最重要的发现**：整条曲线上 `memory` / `persona` / `safety` / `turn_taking`
**恒为 1.000** —— 哪怕把规划**整个拔掉**也不动，只有 `task` / `tools` 看得见。
所以**这 4 个维度的分数不能拿来当"规划没问题"的证据**。

**④ 换一个世界，Agent 一行不改**

同一套 `NPCAgent` 跑在两个结构完全不同的环境上：

- **星屿咖啡屋**（自研文字世界）：确定性、零依赖，用来做可复现评测
- **Minecraft 体素世界**：有坐标、有物品数量、有昼夜循环，靠 `minecraft_env.py` 适配

```bash
python -m npc_agent.cli worlds --html docs/worlds.html
```

跨世界报告答的是**覆盖面**，不是"A 比 B 好多少"—— 两个世界的用例集不同，相减没有意义。
要接**真实 Minecraft 服务端**（`mineflayer` 桥，协议已用 `--dry-run` 验证）：
`npm i mineflayer mineflayer-pathfinder vec3` → 起服务端 → `python scripts/e2e_minecraft.py`。

### 4.4 两个"数字掉下来了但其实是修好了"的案例

这两个案例比上面的分数更能说明这个项目在做什么。

**案例 A：对话复读 —— 用户实测发现的问题**

在自测控制台里聊天，NPC 会反复重复同一个话题，对话推不动。量下来是**两类**缺陷：

**(A) 复读** —— 10 轮对话里 **62% 的台词是逐字重复**（44 句里 27 句）。
四个成因：陈述句一律落到同一个意图、模板只有一个写法、记忆被反复回引同一条、问句只认问号。

**(B) 推不动** —— 更直接：NPC 在跑自己的计划时**完全听不见玩家**。
玩家连问三个问题，NPC 一声不吭去后厨拿牛奶。根因是优先级倒置 ——
`decide()` 里"继续执行未完成的计划"排在"被点名""有人提问"**前面**，
而 `step()` 里那段"回答优先于计划"的闸门写的是 `decision.urgency >= 0.9`，
计划那一支只给 0.55，所以那段代码**从来没执行过**（死代码）。

```bash
python scripts/measure_repetition.py --html docs/repetition.html
```

| 场景 | 修复前（10 轮） | 修复后（10 轮） | 修复后（20 轮，离线） |
|---|---|---|---|
| duet | 50.0% | 0.0% | 0.0% |
| hosting | 60.0% | 0.0% | 20.0% |
| icebreaker | 70.0% | 0.0% | 25.0% |
| tutorial | 62.5% | 0.0% | 25.0% |
| village | 66.7% | 0.0% | 40.0% |
| **合计** | **61.4%** | **0.0%** | **22.0%** |

> ⚠️ **10 轮是演示对话的真实长度，20 轮那个数是已知局限，不是目标。**
> 离线启发式的词汇量是**固定的**（每人设约 12 条低信息台词 + 3~4 个话题），
> 复读率的下界就是 `(轮数 − 词汇量) / 轮数` —— village 20 轮实测 40%，
> 正好等于 `(20 − 12) / 20`。**长对话要接模型**：台词 prompt 里带了【你最近说过】，
> 模型能自己换话题，不受模板池大小限制。
>
> 顺带说明：这个数比上一版（18%）**高**，但不是变差了 —— 修好"听得见玩家"之后
> NPC 每轮都开口（20 轮 20 句），多出来的正是那些低信息量的应声；
> 上一版有 2~4 轮是静默的，那些轮次把复读率的分母缩小了。**同一件事现在算得更准。**

**案例 B：模型自己规划时，也真的能把一件事做完**

"让模型规划"曾经明显不稳：同一个 `duet` 场景跑 4 次，只有 **1 次**两个 NPC 各自完成了目标。

**根因不是"模型不会规划"，是 prompt 里少了一条判据。**
规划 prompt 只喂了目标的**文字**，**没给 `success_when`**（"世界标记 `song_started` 被置上"）。
于是模型规划出的是 `speak → emote(play_guitar) → start_activity(song_request)`
—— 全都是"像在起歌"的动作，**唯独没有人去 `set_flag(song_started)`**。

| | 完成目标次数 | 备注 |
|---|---|---|
| 修复前（模型规划） | **1 / 4** | 3 次都悬着同一对目标 |
| 修复后（模型规划） | **10 / 10** | 4 次 + 补跑的 6 次 |
| 对照组（离线规划） | 2 / 2 | 秒级，本来就没问题 |

> ⚠️ **适用范围**：只有一个场景（`duet`）、一个模型（kimi-k2.7-code），
> 修复后 n=10、修复前 n=4（样本偏小）。它是"这个根因确实存在、修掉之后确实好了"的
> **定向验证**，不是"LLM 规划已经全面可靠"的结论。
>
> **补做的批量配对对比（60 条）结论是「这批测不出修复」** —— 这个结果也写在这里，
> 因为它比一个好看的数字更有用：翻转的 7 条用例**全部**落在"规划回落"里，
> 而两边都没回落的 19 条上修复前后都是满分（说明它们**结构上不经过那个缺陷**）。
> 详见 [`docs/planner_batch.html`](docs/planner_batch.html)。

## 五、不足与总结

### 5.1 诚实的局限

这个项目是**自建的小样本评测**，不是通用能力证明。以下每一条都请在读数字时带上：

1. **用例集是自己写的，235 条，不是 LongMemEval 之类的公开基准。**
   没有跑过官方 LOCOMO/LongMemEval（当时环境拿不到数据集），
   仓库里只有适配器和 6 条内置样例。**不能把这里的数字说成"公开基准上的成绩"。**
2. **离线满分不等于模型能力。** 它衡量的是框架逻辑的自洽与可复现，
   以及"护栏确实在工作"。真正的模型能力看第 4.3 节，而那一节是饱和的。
3. **真实模型跑批停在 228 条版本上**，且已经饱和 —— 它的信息量主要在"框架能跑通
   完整跑批 + 裁判 + 留出集"这件事本身，而不是那个通过率。
4. **LLM 规划的修复只做过**定向**验证，不是全面结论**：见「效果 6」——
   一个场景、一个模型、修复后 n=10（修复前 n=4，样本偏小）。
   补做的批量配对对比（60 条）**测不出修复前后**：翻转的用例全部落在
   "规划回落"里，两边都没回落的 19 条上修复前后都是满分。
   **`docs/batch_planner.html` 里"模型规划比启发式差"的结论描述的是旧代码**，
   不能拿来评价现在。
5. **⭐ 端点稳定性是目前测"LLM 规划"的最大障碍**：规划调用超时后框架会
   **回落到启发式规划器**，于是网络抖动被记成"规划失败"。
      配对子集（60 条）里两条臂都是 **48%**；修复后那一臂整臂是 **112/231（48%）**
      （跑批时用例集是 231 条）。
   在端点稳定下来之前，这个仓库里任何"LLM 规划"的批量读数都带着这层污染。
   （**没有一条是「模型给出了读不懂的计划」**：修复前 29 条全是传输层故障，
   修复后 112 条里 109 条传输层 + 3 条 `max_tokens` 截断 —— 后者是预算问题。）
   **回落现在不再是静默的**（2026-09-20）：每个计划带 `Plan.source`，
   跑批报告有「规划来源」一节、控制台在回合上打红色「⚠ 回落」标签，
   所以**污染可以被看见、被排除** —— 但端点本身仍然不稳，这一点没变。
   **传输层重试补上了**（2026-09-20，默认 3 次、退避 1s / 2s，只重试传输层故障）——
   但它只吃得掉**抖动**：`retries=1` 时 5 次调用失败 1 次，`retries=3` 时 6 次调用
   失败 0 次（HTTP 尝试 7 次 = 6 + **1 次重试，而且成功了**）。
   ⚠️ **样本只有 1 次重试事件**，所以这证明的是"这条路走得通"，**不是**改善幅度。
   端点**持续**不可用时，重试只是把同一份失败多试两遍。
6. **评测对"规划"的敏感度有限**：235 条用例里只有 **122 条**断言了世界状态
   （34 条 `flags`、20 条 `objectives_done`）—— 一半的用例**结构上**看不见规划对不对。
   `icebreaker` 的两个目标原来一条都没被验收，2026-09-20 补上了
   （`tests/test_eval_coverage.py` 里那份已知缺口清单现在是**空的**）。
   但**覆盖率不足不会报错，只会一直给你高分** —— 这个性质没有变。
   另外：**"断言了世界状态"是按 `expect` 里有哪些键数的**，
   所以它是个**代理量** —— 空的 `flags: []` 也会被数进去。
   2026-09-20 清掉了 35 处这种**永远不会失败**的断言
   （详见 `docs/ENGINEERING.md` 附七，护栏在 `tests/test_eval_assertions.py`）。
   ⭐ **比覆盖率更硬的一处证据**（2026-09-26）：六个维度里 **4 个对规划恒为 1.000**
   —— 把规划整个拔掉也不动（`docs/resolution.html`）。覆盖率不足说的是
   「**可能**没测到」，恒为 1.000 说的是「**确实**没测到」。
7. **真实 Minecraft 服务端未接入仓库的默认路径**：桥脚本和协议验证都在，
   缺的是服务端环境；默认走进程内的 `LocalWorldClient`。
8. **六个维度里有两个的覆盖仍然偏薄**（`memory` 的检索侧、`turn_taking` 的部分场景），
   敏感性报告会标出来。覆盖率不足的维度**不会报错，只会一直给你 1.000**。
9. **离线启发式撑不住长对话**：模板池是固定的，20 轮之后复读率会爬到 20%~40%
   （下界是 `(轮数 − 词汇量) / 轮数`）。10 轮以内是干净的（实测 0%）。
   要长对话就接模型 —— 同一个 20 轮对话，离线 25% → 真实模型 **0%**。
10. **六维评测看不见"复读"这类序列缺陷**：它每一维都只看单句。
    所以复读 62% 和"六维全 1.000"曾经同时成立。现在由
    `tests/test_repetition.py` 单独守着 —— 加评测维度时请先问一句
    "这一维看的是**一个点**还是一个**区间**"。
11. **裁判的判决不可复现，所以裁判数字只能当参考信号。** 实测：
    `JUDGE_TEMPERATURE = 0.0`、prompt 逐字节相同，**同一条台词判两次，
    `grounded` 有 22.2%（2/9）的概率给出相反的结论**。
    后果是任何"某条判决翻转了"的观察都**不能单独归因**（先测噪声底），
    而且**已有的裁判数字都自带这层噪声** —— 包括那个 kappa。
    它是"某一次判分"的读数，不是"裁判的水平"。
    `--judge-samples N` 取多数票是**缓解**：七票实测仍有 4/9 对
    （`grounded`）票型分裂，也就是说**被压住的那部分仍然存在**，
    只是多数票把它藏了起来。噪声大是模型的属性，换不了。
12. **⭐ 反思曾经把"守规矩"记成"有毛病"，而且这件事不会报错、也不会掉分。**
    `ok=False` 原来混着两类完全不同的东西 —— 动作**真的**没做成，
    和动作**按策略主动让出**（发言占比到顶让出话头）。只有前者该反思。
    量出来（`scripts/probe_advice_coverage.py`，离线 235 条、0 次模型调用）：
    写进记忆的 457 条反思里有 **139 条（30.4%）** 是假教训，
    而全语料**最高频**的那条就是它（出现 **122** 次）——
    「我说话太多了」，配在一个**主动**让出话头的动作上。
    它以 `importance=0.85` 进记忆、被规划 prompt 以【想起的事】取走，
    所以配真实模型时，**模型会读到一句假的自我评价**。
    修法是把"让出"变成产出方声明的结构化字段（`ActionResult.outcome`），
    不在消费方按文案猜（见 `docs/ENGINEERING.md` 附十二）。
    修后：457 → **336** 条反思，假教训 **139 → 0**，**离线基线仍是 235/235**
    —— 这条缺陷污染的不是分数，是**写进记忆的东西**。
    顺带删掉了一条零调用点的 `reflect_with_llm`（实测它**不会**更准：
    关键词表在真实失败上覆盖率 100%、通用档 0.0%）。
13. **同一个假象有三个出口，修了一处不等于修完。** 上面那条缺陷的假象
    （"主动让出话头长得像失败"）不止写在记忆里：
    ① 记忆（规划 prompt 的【想起的事】）—— 修了；
    ② **评测转写** —— `harness` 自己写了一份 `"ok" if result.ok else "!!"`，
    而 `ActionResult.render()` 也算一份 ⇒ **同一件事两个产出点**，
    加了 `declined` 之后两份分家，转写印 `[!!]`，**而裁判读的就是这段转写**；
    ③ **控制台动作列表** —— 把让出印成红色并配一个 ✗。
    现在标记只有 `ActionResult.mark` 一个产出点，另配护栏禁止再出现
    "只读 `.ok` 就下结论"的写法。**判据：这件事有几个产出点？多于一个就会分家。**
14. **⭐ 第四个出口：自测平台网页。** 前三个出口都在命令行侧，这一个在
    `python -m npc_agent.cli studio` 打开的页面上 —— 而它恰好是**演示时
    唯一会被看到的界面**。`_turn_payload` 从前只发一个布尔 `ok`，
    页面据此写死 `a.ok ? "ok" : "no"`，于是"主动让出话头"在网页上
    是一个红色的 `✗`。修法与上同（只发 `mark` / `declined`，页面只管印），
    并新增 `.act.yield`（灰、符号 `↷`）与失败的红色 `✗` 区分开。
    同一段代码里还挖出**第四处**同类判据：`_turn_payload` 过滤成功 `speak`
    时写的是 `not result.ok`，而让出的 `ok` 也是 `False` ⇒
    **让出的 speak 照样被列进动作列表**，与那段注释写的"会被过滤掉"正好相反
    （注释描述了一个没被实现的意图）。实测三种结果：
    成功→略去、让出→**旧判据保留（错）/ 新判据略去（对）**、真失败→保留（不变）。
    护栏把页面里那个表达式抽出来**交给 node 真的跑一遍**，
    断言三种 `mark` 映出的 CSS 类两两不同（做过反向测试：合流即红）。
    详见 `docs/ENGINEERING.md` 附十三。
15. **⭐⭐ 第五个出口，也是规模最大的一处：规划状态机。** 同一个假象
    （"让出长得像失败"）还藏在 `_run_plan()` 里 —— 它判的是
    `if result.ok: done else: 重规划 → failed`，而**让出的 `ok` 也是 `False`**。
    离线 235 条 A/B 实测：**228 个** step 被误标成 `failed`
    （其中 **228 个的 note 就是那句让出文案 —— 没有一个是真失败**），
    `replan` 调用 **309 → 93**（**−216 次**是为让出触发的）。
    危害有两条，都可观测：① 计划记录里写着"某步失败"，而它其实是发言权上限
    在正常工作；② 每次重规划都**重建整份计划**，插入一条
    「…（重试）」步骤（实测插了 **121 条**）并把理由写成
    「重规划：发言占比 67% 已超上限」。
    ⚠️ **但不是"白烧模型调用"** —— `Planner.replan()` 是纯启发式
    （`_corrective_steps`，体内没有 `self.llm`），**不花 token**；
    （代码里那句"重规划会白烧一次模型调用"的注释本身就是错的 ——
    只有 `plan_with_llm` 调模型。）
    修法：`result.declined` → `skipped`。**关键线索**：同一个函数里
    另外两处让位（"话头给了同伴"、"本轮已经说过一句"）**本来就写的 `skipped`**
    —— 三处让位里漏了一处，三处说法不一致。
    而漏掉的那种（"占比超上限"）只有**执行之后**才知道，
    前面的 `not ctx.allow_speech` 闸门**结构上拦不住**。
    详见 `docs/ENGINEERING.md` 附十四。
16. **⭐ 「无害」可能是借来的 —— 借据是两份实现的巧合一致。** `_proactive_share()`
    把候选话题记进 `_shared_topics`（**永久**黑名单）**先于**执行 `tell_fact`，
    失败也不撤销 ⇒ 失败一次，那个话题这一局就再也不会被分享。
    量下来**目前无害**：`available_topics()` 说能聊的话题，`tell_fact` 一定说能讲 ——
    但那是因为**两份各自实现的检查恰好等价**（穷举 flag 组合 **16/16** 一致）。
    只让其中一份漏掉一条检查（模拟"将来有人只改一处"）：
    `tell_fact` 失败 **0 → 25** 次、**25** 个话题被永久拉黑 ——
    而**分数仍是 235/235（满分）**，235 条用例**一条都抓不到**。
    修法：**不改产品代码、只把不变量变成契约** —— 新增护栏穷举 flag 组合，
    断言 `topic in available_topics()` **当且仅当** `tell_fact(topic).ok`。
    ⚠️ 而这条护栏的**第一版是永远绿的**：场景用了 `icebreaker`，
    它的 `knowledge_unlocked` 恰好覆盖全部"无 requires"话题 ⇒ 那条检查恒为空转，
    注入缺陷照样全绿。换 `village`（锁住 3 个）并**加一条前提断言**后才真的会红。
    详见 `docs/ENGINEERING.md` 附十五。

17. **⭐ 修好一处「度量」之后，别处那个同名计数会悄悄变得偏低。** 2026-09-20
    给解析层补上重试（见路线图那条）之后，**裁判那层的 `judge_parse_retries`
    从此刻起会偏低** —— 大部分解析失败在模型客户端那一层就被救回了，
    根本传不到裁判自己的重试循环里。这不是 bug，是**口径变了**：
    "重试了多少次"现在有两个产出点，报告只印了其中一个。
    处置：在报告里把这件事**写出来**（"这个数偏低"），而不是让它看起来像
    "解析失败只发生过这么多次"。**同一类的教训此前出现过 5 次**（附一~附九），
    这是第 6 次 —— 修一层重试，就要重新数一遍"谁在数重试"。
18. **⭐ 「天花板」和「收益」要分开报，而且要看分布。** 2026-09-20
    给判分材料补上世界知识表，修的是一个真 bug（NPC 照着自己的知识库说话
    被判成编造）。但**不要**顺手说"这能修好 17% 的 `grounded` 失败"：
    那个 87/502 是**内容级匹配出来的上限** —— 它只说明"这些句子的原文
    以前不在材料里"，不说明裁判改口。更关键的是**分布极不均**：
    village 23/23、icebreaker **0/308**。同一句"可救回上限 17.3%"
    在 icebreaker 上等于零，在 village 上等于全部。
    **一个总比率会把一个局部修复说成全局修复。**
19. **⭐ 「先量再优化」的反面同样成立：不量就动手，你会先做那个最小的。** 2026-09-21
    一次性能清扫里量出三处，**收益差了 50 倍**：
    ① 未使用 import 5 处（清理，0 收益）；
    ② `load_persona` / `load_scenario` 没缓存 —— 一次离线 eval 里
    `load_yaml` 被调 **510 次**、只涉及 **8 个文件**（去重率 1.6%），
    单次 2.9ms ⇒ 约 **1.5s** 花在反复解析同一批 YAML；
    ③ **测试套件里约 90 秒纯粹在 `time.sleep`** ——
    `LLMJudge` 的退避是 `3.0 × (1+2) = 9s`，而"喂坏输出 / 让模型抛异常"
    那类用例**每条都会走完重试**，实测 7 条这样，白等 63 秒。
    三处做完：套件 **343s → 66s**，离线跑批**串行估计 9s → 2s**。
    ⇒ **③ 是最大的那处，而它藏在 `--durations` 里，不在代码里。**
    靠读代码猜"哪里慢"，猜到的会是 ①（`import` 冗余最显眼、收益为零）。
20. **⭐ 「靠人记得」的约定迟早会漏 —— 要么把它变成默认值，要么配一条会红的护栏。** 2026-09-20
    上一条的 ③ 有个现成的开关：`LLMJudge(sleep=...)`，注释里也写着
    "注入 sleep 是为了让测试不用真的等 3 秒、6 秒"。**但实测有 7 处忘了传** ——
    约定本身是对的，只是它要求每个人每次都记得。
    处置：抽出 `judge.DEFAULT_SLEEP`（唯一的默认等待函数），
    由 `tests/conftest.py` 的 autouse fixture 换成 no-op ⇒ **忘了也不会真的等**；
    再配一条护栏钉住"开关真的被关掉了"（谁删了 fixture 立刻变红）。
    ⚠️ 不要顺手 patch 全局的 `time.sleep`：同文件里有一条用例
    **故意用 `time.sleep` 模拟模型延迟**来测并发加速比，
    全局 patch 会把它的语义一起改掉 —— **"顺手关掉太多"会静默削弱别的测试。**

### 5.2 没量过的（明确标注，不装懂）

| 没量过的事 | 为什么没量 |
|---|---|
| 公开基准（LongMemEval / LOCOMO） | 当时拿不到数据集。适配器已在，缺数据集 + 一次跑批 |
| **真人玩家体验** | 没有真人被试。需要用户研究，不是工程能替代的 |
| **裁判与人工标注的一致性** | 没有人工标注集。在那之前，"多数票更准"没被验证 |
| `grounded` 裁判的噪声底 | 只测了 9 条重复采样 |
| **规划敏感度 10% 是不是通用** | 只测了"均匀丢步"这一种退化路径 |
| 长对话（>20 轮）的表现 | 离线模板池撑不住，模型跑批又贵 |
| 多 NPC 场景的规模上限 | 最多只有 **2 个 NPC**（`duet`）。⚠️ 别把 `icebreaker` 的 **3 个玩家**记成 3 个 NPC |
| 端到端延迟 / 成本 | 只记了总耗时（4999s / 228 条），没分阶段打点 |

完整的证据单（每条边界的实测数字 + 出处 + 追问怎么答）见
**[`docs/BOUNDARY.md`](docs/BOUNDARY.md)**。

### 5.3 总结

**做了什么**：一套环境无关、模型可选、**可评测**的 AI NPC 框架 ——
七个模块 + 多 NPC 导演层 + 六维评测 + 四份离线对照实验 + 一份自测控制台。

**最值钱的地方不是功能，是"每个数字都能被质疑"**：

- 满分不是靠演示撑的 —— 有变异测试证明护栏在工作，还有分辨率曲线量出报警线画在哪；
- 阴性结果留在报告里 —— 四种检索策略 Δ=0.000、批量配对测不出修复、跨世界不做优劣比较；
- 局限写在文档里、**并且有护栏守着** —— README 的测试数、离线基线、报告覆盖数、
  每条被文档化的命令，都真的跑一遍去核对。

**如果只记一句话**：

> 一个从不失败的评测，和一个没有评测，在报告上长得一模一样。
> 所以这个项目里，"我怎么知道我的评测有用"和"我的评测得了多少分"是同等重要的问题。
