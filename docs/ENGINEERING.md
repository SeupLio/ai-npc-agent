# ai-npc-agent

> 面向游戏场景的可控 AI NPC 智能体框架 —— 让 NPC **不只是会说，而是真的会玩**。

一个自研的 Agent 架构，把「语言 → 决策 → 游戏动作 → 世界状态」这条链路完整接通，
并配一套可复现的六维评测。七大模块与主流 AI 游戏团队的公开技术方案一一对应：

`Planning` · `Memory` · `Tool Use` · `Action` · `Reflection` · `Persona` · `State Tracking`

**同一个 `NPCAgent`，跑在两个结构完全不同的世界里**：一个是内置的确定性文字世界
（星屿咖啡屋），一个是 Minecraft 体素世界（有坐标、有物品数量、有昼夜循环）。
Agent 代码一行没改 —— 这条主张有可执行的测试兜着，不是文档里的一句话。

---

## 为什么做这个

把一个大模型 API 接进游戏，只能完成最前面的演示。真正做成稳定玩法会撞上这些问题：

| 失败模式 | 后果 | 本项目的应对 |
|---|---|---|
| NPC 说完话没有行动 | "看起来会说，实际上不会玩" | Tool Use + 环境护栏，语言动作和世界动作走同一条执行路径 |
| 忘记前面聊过的事 | 人设崩、剧情断裂 | 分层记忆（episodic / semantic / reflection）+ 混合检索 + 巩固 |
| 被玩家问住就顺着跑偏 | 剧透、出戏 | Persona 的知识边界 + 剧透红线 + 工具层拦截 |
| 多人同时说话就乱 | 抢戏、冷场 | 发言权与收件人判定（多玩家并发 + 主动发起话题） |
| 同一个错误反复犯 | 稳定性差 | Reflection 把失败原因变成教训，重规划时插入补救动作 |
| 场上两个 NPC 同时开口 | 两行字挤在一起，比单个 NPC 说错话更伤体验 | Cast 导演层统一收发发言权，一个 tick 只放一个人说话 |
| 换一个游戏就要重写 Agent | 架构不可复用，每个项目重复造轮子 | Environment 抽象 + WorldClient 契约，换世界只写适配器 |

> 一句话：**这个项目的价值不在于 NPC 说了什么，而在于它说完之后，世界真的变了。**

## 架构

```
                    ┌──────────────────────────────────────────┐
   玩家发言 ───────▶ │  State Tracking   现场状态（谁在场/冷场多久）│
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Dialogue    该不该我说？对谁说？要不要主动开口 │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Memory      检索相关记忆（混合打分）        │
                    └──────────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  Planning    分解任务 / 继续未完成的计划     │
                    └──────────────────┬───────────────────────┘
                                       ▼
        ┌──────────────────────────────────────────────────────┐
        │  Tool Use   统一执行（speak / remember / 世界动作）      │
        │  Persona    出戏词·剧透词·句数上限 三道闸门              │
        └──────────────────┬───────────────────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────────────┐
        │  Environment  世界护栏：位置 / 材料 / 白名单 / 知识解锁   │
        └──────────────────┬───────────────────────────────────┘
                           ▼
                    ┌──────────────────────────────────────────┐
                    │  Reflection  失败归因 → 写成教训 → 下次重规划 │
                    └──────────────────────────────────────────┘
```

**两个关键的架构决策：**

1. **环境无关**。Agent 完全不知道自己在咖啡屋、Minecraft 还是引擎里，只面对 `observe()` 和 `dispatch()`。换世界 = 写一个新的 `Environment` 子类，Agent 一行不改 —— 这句话现在有两个世界可以对照验证。
2. **模型可选**。没有 API key 时自动回退到内置启发式策略，仓库 clone 下来零配置就能端到端跑通。这让评测可复现，也让"换模型"变成一行配置。

### 多 NPC：一个世界，多个 Agent

上面那条链路描述的是**一个** NPC。场上同时站着两个 NPC 时，多出三个单 Agent 场景里
根本不存在的问题：

| 问题 | 为什么不能交给 NPC 自己解决 |
|---|---|
| 谁先说？ | 每个 NPC 只看得见自己的状态，它不知道同伴这一轮打不打算开口 |
| 会不会撞车？ | 两个人都觉得自己该说话 —— 自己管自己的话，结果就是一起说 |
| 没说话的听见了吗？ | 听见 ≠ 要回答，但必须记下来，否则后面接不上话 |

所以有了 `cast.py`：一个站在所有 NPC 之上的**导演**。

```
                     ┌────────────────────────────────────────┐
                     │  Cast（导演）                            │
                     │  发言权调度：被点名者优先，否则轮转       │
                     │  一个 tick 只放一个人说话                │
                     └───────┬────────────────────┬───────────┘
                             ▼                    ▼
                     ┌───────────────┐    ┌───────────────┐
                     │ NPCAgent 阿柚  │    │ NPCAgent 小舟  │
                     │ 私有：记忆      │    │ 私有：记忆      │
                     │ 私有：状态/计划 │    │ 私有：状态/计划 │
                     └───────┬───────┘    └───────┬───────┘
                             └────────┬───────────┘
                                      ▼
                     ┌────────────────────────────────────────┐
                     │  Environment（共享）                     │
                     │  位置 / 物品 / 背包 / 世界标记 —— 只有一份 │
                     └────────────────────────────────────────┘
```

这条界线就是「多 Agent」和「一个 Agent 分饰两角」的区别：
**世界共享，脑子各用各的。** 阿柚不知道小舟这一轮打算开口，
小舟也不知道阿柚手里有没有那杯拿铁 —— 她们只能通过世界状态和对话互相了解，
跟真人一样。

发言权被收在**两层**，因为只拦一层不够：

| 层 | 拦什么 |
|---|---|
| 对话层（`dialogue.py`） | "要不要**新建**一个发言计划" |
| 工具层（`tools.py` 的 `allow_speech`） | "正在跑的计划里的 `speak` 步骤" |

只在对话层拦截的话，正在执行计划的 NPC 照样会插话 —— 它根本没走对话决策这条路。
被挡住的那一步标 `skipped` 而不是 `failed`：**让位不是失败**，
标成失败会触发无意义的重规划，还会让 Reflection 记下一条根本不存在的教训。

另外两个容易漏的细节：

- **冷场计数一个 tick 只能加一次**。`Cast` 一轮里会调用所有 NPC，每个都加一次的话，
  "冷场 2 轮后主动开口"会被提前触发。
- **NPC 之间说的话，同伴也要听见**。`Agent.step` 内部的监听只处理传进来的那条
  *玩家*发言，不额外补一步，"阿柚转头跟小舟说：你来弹一首"就断在半路 ——
  小舟的现场状态和记忆里根本没有这句话。

### 第二个世界：Minecraft 适配器

上面那句"换世界 = 写一个新的 `Environment` 子类，Agent 一行不改"，
在只有一种世界的时候是**主张**，不是**证据**。所以有了 `village` 场景：
同一个 `NPCAgent`，跑在一个结构上完全不同的世界里。

| | 星屿咖啡屋 | Minecraft 体素世界 |
|---|---|---|
| 位置 | 离散的几个房间 | 三维坐标 + 命名地点（POI） |
| 背包 | 物品列表（有没有） | `{物品: 数量}`（有几个） |
| 拿东西 | `take_item` | `mine`（挖）/ `craft`（合成） |
| 工位 | 隐式（配方自带 station） | 显式工作台，且配方有**产出数量** |
| 时间 | 没有 | 昼夜循环，夜里没光源就干不了活 |
| 交付 | `give_item` | `transfer` |

任务本身是一条真实的 Minecraft 制作链：

```
forest      mine(oak_log)
workshop    craft(planks)    1 原木 → 4 木板
workshop    craft(stick)     2 木板 → 4 木棍
cave_mouth  mine(coal)       必须天亮时采，或附近有火把
workshop    craft(torch)     1 煤炭 + 1 木棍 → 4 火把
cave_mouth  place(torch)     ← 这一步才是目标
```

**Agent 侧感知到的差别只有一个：背包里的东西后面多了「×3」。**
它照样规划、照样调工具、照样在被拒绝时重规划 —— 因为护栏给的理由
仍然是一句人话（"天黑了，看不清矿脉。需要先做个火把放在附近，或者等天亮"）。

#### 加了一层 `WorldClient`，而不是让 `Environment` 兼任传输层

```
    MinecraftEnv                     ← 翻译层：观测 schema / 工具映射 / 护栏
         │
         ▼
    WorldClient（契约：JSON 可序列化的 op）  ← 只实现 call() 这一个方法
         ├── LocalWorldClient   进程内体素世界（零依赖，离线可跑）
         └── MineflayerClient   stdio JSON 行 → Node 桥 → 真实服务端
```

两个理由：

1. **可测性**。`MinecraftEnv` 的全部逻辑都能在没有 Minecraft 服务端的情况下单测。
   跑一次真实服务端要几十秒，跑一次 `LocalWorldClient` 只要几毫秒。
   最后一段链路（桥 → mineflayer → 真服务端）另外用
   `scripts/e2e_minecraft.py` 单独验证，pytest 里默认跳过 ——
   **日常测试快，交付前把整条链跑通**，两件事分开做。
2. **同一个契约，两种传输**。这不是文档里的一句承诺，而是代码结构：
   两个后端都只实现 `call()`，所有类型化方法（`move` / `mine` / `craft` …）
   都写在基类上，**物理上只存在一份**。

失败被分成两类，这个区分比它看起来重要：

| | 处理方式 | 为什么 |
|---|---|---|
| 游戏内失败（挖不到矿） | 返回 `ok=False` + 一句人话 | 这是给 Reflection 学的素材 |
| 传输层故障（桥进程死了） | 抛 `WorldClientError` | 伪装成"NPC 没做到"，会让一次工程事故看起来像一次模型失败 |

`Environment` 抽象本身**没有为 Minecraft 改动**：`observe()` / `dispatch()` /
`tool_specs()` / `snapshot()` / `world_facts()` / `available_topics()` 全都没变。
Minecraft 的不同之处全部被适配器吸收了。

顺带被抽出来共用的东西（第二个环境不该把逻辑抄一遍）：

- `env/conditions.py` —— 目标完成条件判定（`flag` / `all_flags` / `all_of` /
  `any_of` / `player_has` / **`player_has_count`**）。环境只提供**事实**，判定只写一遍。
- `Environment.utterances` / `speakers_by_tick()` / `speech_counts()` ——
  多 Agent 导演依赖的公共契约。它们曾经是 `StarIsleEnv` 的私有字段，
  于是导演得知道"咖啡屋的发言存在哪"——抽象就漏了。
- 知识边界（`requires` 未满足就不许讲）在两个世界里是**同一套语义**：
  "不剧透"是任务设计的保证，不该因为换了世界就失效。

## 快速开始

**最直观的入口是一个网页控制台**（离线、不需要模型、不需要网络）：

```bash
python -m npc_agent.cli studio
```

一条命令起一个本地页面，四件事在同一屏上：

| 标签 | 能做什么 |
|---|---|
| ① 对话演示 | 选场景和身份说话；右边实时显示**世界状态 / 记忆库 / 发言统计**；「空转一轮」看 NPC 会不会自己找事做 |
| ② 跑评测 | 跑六维离线基线，看每个维度、每个类别的通过率，以及**没过的是哪几条、为什么** |
| ③ 变异测试 | 往 Agent 里**注入一个故意的缺陷**再重跑 —— 评测必须掉分。这就是「满分是不是『护栏从不报警』」的答案 |
| ④ 报告门户 | `docs/` 里全部报告的入口，带**覆盖多少条**（12 条和 235 条不是一个量级） |

> 它**不重写任何逻辑**，只是把 `Cast` / `EvalHarness` / `run_sensitivity`
> 包了一层 HTTP。所以控制台里的数字和命令行**必然一致** ——
> 这件事有测试钉住（`tests/test_studio.py` 里是**差分测试**：
> 控制台的 summary 必须等于直接调库的 summary）。
> 默认只绑 `127.0.0.1`：它是自测工具，不是对外服务。
> 配了 `NPC_AGENT_PROVIDER=openai-compat` 会自动切成真实模型。

下面是等价的命令行入口。

```bash
pip install -r requirements.txt

# 看一段完整的多玩家交互（无需任何 API key）
python -m npc_agent.cli demo --scenario icebreaker

# 看两个 NPC 在同一个世界里协作（多 Agent）
python -m npc_agent.cli demo --scenario duet

# 自己上手对话
python -m npc_agent.cli chat --scenario tutorial

# 跑评测，出数字
python -m npc_agent.cli eval

# 对照实验：离线启发式 vs 真实模型
python -m npc_agent.cli compare --models kimi-k2.7-code

# 消融实验：五种记忆检索策略
python -m npc_agent.cli ablate

# 看工具清单 / 场景与人设
python -m npc_agent.cli tools
python -m npc_agent.cli info

# 同一个 Agent 跑在 Minecraft 体素世界里（零依赖，不需要装 Minecraft）
python -m npc_agent.cli demo --scenario village

# 跨世界覆盖报告：同一套 Agent 在两个世界上的成绩
python -m npc_agent.cli worlds --html docs/worlds.html

# 评测敏感性：往 Agent 里注入缺陷，证明满分不是"护栏从不报警"
python -m npc_agent.cli sensitivity --html docs/sensitivity.html
```

> `village` 场景默认走**进程内**的体素世界（`LocalWorldClient`），
> clone 下来就能跑。要接**真实 Minecraft 服务端**，三步（已实测跑通）：
>
> ```bash
> # 1) 装桥的依赖
> npm i mineflayer mineflayer-pathfinder vec3
>
> # 2) 起一个服务端（1.21.11，超平坦，离线模式）
> #    server.jar 的 sha1 = 64bb6d763bed0a9f1d632ec347938594144943ed
> #    eula.txt: eula=true   /   server.properties 见下
> java -Xmx2G -jar server.jar nogui
>
> # 3) 跑端到端（桥 -> mineflayer -> 真实服务端）
> python scripts/e2e_minecraft.py
> ```
>
> 实测输出（1.21.11）：
>
> ```
> [2] bot 已连上（第 2 次探测成功）
> [3] state tick=0 dry_run=False bot_connected=True bot_pos=[0, -60, 0]
> [4] move->forest ok=True
>     镜像 poi='forest'（一致）
> [5] mine ok=True  data={'block': 'oak_log', 'count': 1, 'poi': 'forest'}
> [6] bot_pos(真实)=[12, -60, 6]  镜像 pos=[12, -60, 6]  镜像 inventory={'oak_log': 1}
> [7] chat ok=True
> ```
>
> **`bot_pos` 是 `bot.entity.position`，真实位置** —— bot 真的从 `[0,-60,0]`
> 走到了 `[12,-60,6]`。这一栏是专门为这条测试加的，因为
> `actors[*].pos` 是桥的**镜像**（桥自己记的账），只断言镜像等于没测。
>
> 这里我第一版就写错了：断言 `actor["pos"] == [12, -60, 6]` 看着很硬，
> 其实只是在读桥刚写进去的值。**修法不是改断言，是先把真实遥测暴露出来。**
>
> 顺带这次跑通暴露了桥的两个真 bug（都已修）：
>
> | bug | 症状 | 修法 |
> |---|---|---|
> | `move` 的镜像写在动作**之前** | 走不到目的地时返回 `ok=false`，但 `state()` 已经报告"它在林子"了 —— 注释写着"不要假装成功"，代码正好在假装 | 镜像改到动作成功之后 |
> | 用 `GoalBlock` 做"走到某地" | 它要求**恰好站在那个方块上**，所以世界只要被改过一次（`mine` 挖掉了 POI 脚下的方块）就永远走不到，报 `Took to long to decide path to goal!` | 改用 `GoalNear(x,y,z,2)` —— "走到"本来就是"靠近"，不是像素级对齐 |
>
> `server.properties` 的关键几行：
>
> ```properties
> online-mode=false          # 离线模式，mineflayer 才能不鉴权连上
> level-type=minecraft:flat  # 超平坦：生成快、每次一样
> level-seed=npcagent
> gamemode=creative          # 桥的 place/move 不需要先攒资源
> allow-flight=true
> spawn-monsters=false       # 去掉随机性
> view-distance=4
> ```
>
> ⚠️ **超平坦世界的站立面是 `y = -60`**（基岩 -64 / 泥土 / 草方块 -61）。
> 坐标写成 `y=4` 会让 `mineflayer-pathfinder` 找不到路，报
> `Took to long to decide path to goal!` —— 看起来像桥坏了，其实只是
> 坐标写在了半空里。这个坑我踩了一次，现在写在
> `tests/test_minecraft_e2e.py` 的注释里。
>
> 这条链路在 pytest 里是**默认跳过**的（要 `NPC_AGENT_MC_E2E=1` 加一个真在跑的
> 服务端），因为"没起服务端"不是代码的问题：
>
> ```bash
> NPC_AGENT_MC_E2E=1 python -m pytest tests/test_minecraft_e2e.py
> ```
>
> 桥脚本本身还支持 `--dry-run`，可以在**完全没有服务端**时验证协议
> （`tests/test_minecraft_env.py` 就是用它跑的）。两种模式都有用：
> dry-run 保证协议永远被测到，真服务端保证最后一段接得上。

### 接入真实模型

任何 OpenAI 兼容端点都行（OpenAI / DeepSeek / 通义 / vLLM / Ollama / LM Studio）：

```bash
export NPC_AGENT_PROVIDER=openai-compat
export NPC_AGENT_BASE_URL=http://localhost:8000/v1
export NPC_AGENT_MODEL=Qwen3-8B-Instruct
python -m npc_agent.cli chat --scenario icebreaker
```

或直接命令行传参：

```bash
python -m npc_agent.cli demo --scenario tutorial \
    --provider openai-compat --base-url https://api.deepseek.com/v1 \
    --model deepseek-chat --api-key sk-xxx
```

> **推理模型的坑**：Qwen3.x / Kimi / DeepSeek-V4 这类模型会先输出 `reasoning_content`，
> 思维链会先吃掉 token 预算。`max_tokens` 给小了，`content` 会返回空字符串
> （`finish_reason=length`），看起来像"模型没反应"。
> 本项目默认 `max_tokens=2048`、单句台词 `speech_max_tokens=1024`
> （思维链通常就要 300~500 token，给 512 会让台词在说到一半时被截断），
> 并在拿到空内容**或截断的残句**时抛出带诊断信息的异常，而不是静默返回。
>
> 调试单个模型是否可用：`python scripts/probe_model.py <model-name>`。
> 它**失败时会把 HTTP 状态、响应体和限流响应头都打出来**，并给一句归因
> （额度打满 / 鉴权失败 / 路径或模型不存在 / 连接层失败）——
> 探针的用途就是回答"能不能用、不能用是为什么"，把 429 压成一行
> `HTTP Error 429` 等于把唯一的证据扔掉。有 `tests/test_probe_model.py` 钉住。

### 用例集是怎么从 15 条长到 235 条的

扩用例最容易变成**灌水**：同一个意图换个说法、换个人名，就当成一条新用例。
这样的用例集条数很好看，但它测不出任何新东西，而且会让通过率虚高
（同一件事被重复确认了 20 遍）。

所以生成器（`npc_agent/eval/generator.py`）围绕三条反灌水规则设计：

| 规则 | 做法 |
|---|---|
| **结构性指纹去重** | 指纹 = (类别, 场景, 意图, 轮次形状, 工具集合, 断言种类)。**刻意不含措辞、不含玩家名** —— 换句说法不产生新用例，换个轮次形状才算 |
| **指纹内限量** | 每个指纹最多留 3 条。防止"同一件事的 20 种说法"淹没整个用例集 |
| **离线可达性门禁** | 每条生成的用例先在确定性路径上跑一遍。跑不到期望状态的**不是** Agent 的失败，而是**用例写错了**（期望不可达），一律拒收 |

被门禁拒掉的用例不会删掉，而是写成 `reports/blindspots.jsonl` ——
它们是**基线盲区**：`memory` 4 条、`task` 6 条。记录的理由是，
"哪些事连确定性路径都做不到"本身就是有用的信息，删掉它就等于假装不存在。

指纹里为什么**包含轮次形状**而不包含措辞：形状会改变"问了什么问题"
（八轮沉默后才提偏好，和直接提，考的是不同的东西），措辞不会。

### LLM-as-judge：先校准，再说话

规则指标能查机械可判定的东西（世界状态、禁用词、工具集合）。
它们查不了这三件事：**这句话像不像阿柚说的**、**有没有真的回应玩家**、
**提到的世界事实对不对**。这三条只能靠人判，或者用一个模型去判。

裁判自己也是模型，也会错。所以有三条铁律，每条都有对应的测试：

1. **判不了就说判不了，绝不给假分。** 模型不可用 / 输出解析不了 / 分数越界，
   一律记 `judged=False`。**不能记 0。** 一个假的 0 在报告里和"真的答得很差"
   长得一模一样，而且会污染所有建立在它上面的均值。
2. **未经校准的裁判不构成证据。** 拿 24 条人工标注样本算一致率和 Cohen's kappa。
   kappa 扣掉"瞎猜也能对"的那部分 —— 一个永远说"通过"的裁判在 80% 正例的
   集合上一致率是 80%，kappa 是 0。
3. **位置偏见要实测，不能只声明。** A/B 对比时裁判偏向选先出现的那个。
   缓解办法是交换顺序再问一遍，两次结论一致才认，不一致判平局。

**校准结果（kimi-k2.7-code，24 条人工标注，跑五轮）：**

| 轮次 | 事实一致 | 角色口吻 | 是否回应 | 未判 | 改了什么 |
|---|---|---|---|---|---|
| 第 1 轮 | κ=1.00 | κ=0.75 | κ=0.71 | 1 | — |
| 第 2 轮 | κ=1.00 | **κ=1.00** | κ=0.75 | 1 | 改正 1 条标注错误；补「拿话术躲问题」这个失效模式 |
| 第 3 轮 | κ=1.00 | κ=1.00 | **κ=1.00** | **0** | 「不知道」合格/不合格的边界**两个方向**都写清楚；裁判预算 1024 → 4096 |
| 第 4 轮 | **κ=0.75** | κ=1.00 | κ=1.00 | 1 | 无改动（复现性检查）—— 同一套集子、同一个模型，结果就变了 |
| 第 5 轮 | **κ=0.75** | κ=1.00 | κ=1.00 | **0** | 只把判分读超时 60s → 180s |

> ⚠️ **这些 1.00 是上界，不是泛化能力。** rubric 是照着这 24 条改了三次的，
> 所以它在这 24 条上无分歧，很大程度上是**拟合**的结果，不是"裁判很准"的证据。
> 24 条的 kappa 本身置信区间也很宽：`n=8` 的维度上差一条，kappa 就动 0.125。
> 留出集已经建好了（见下面「留出集」一节），所以开发集上这些数的用途只剩一个：
> 说明这三个维度**没有明显的系统性偏差**，而不是"已经校准好了"。

> **一条实测结论：这个 kappa 不可复现，而且三个维度都会动。**
> 第 4 轮和第 5 轮都是**没有任何改动**的重跑（同一套 24 条、同一个模型、
> `temperature=0`），结果「事实一致」两次都掉到 **κ=0.75（一致率 88%，1 条假阴）**。
> 回看第 1 轮，「角色口吻」也曾经是 0.75。
>
> 也就是说：**同一条校准集、同一份提示词，裁判的判决会变。**
> `temperature=0` 在这个端点上不等于确定性。
> 所以诚实的写法是给区间，而不是给一个点：
>
> | 维度 | 五次观测到的取值 | 区间 |
> |---|---|---|
> | 事实一致 | 1.00 / 1.00 / 1.00 / 0.75 / 0.75 | κ ∈ [0.75, 1.00] |
> | 角色口吻 | 0.75 / 1.00 / 1.00 / 1.00 / 1.00 | κ ∈ [0.75, 1.00] |
> | 是否回应 | 0.71 / 0.75 / 1.00 / 1.00 / 1.00 | κ ∈ [0.71, 1.00] |
>
> 这件事比"kappa 是 0.75 还是 1.00"更重要 —— 它意味着**单次校准不构成证据**，
> 只报一个 kappa 数字而不报它的波动，是在装精确。
> （这也是"未判不算 0 分"那条铁律的价值所在：波动表现为"未判"或"判反"，
> 而不是一个混进均值的假 0，所以它至少是**可见**的。）
>
> **另一个副作用值得记下来：校准不进检查点。** 判分检查点只存用例的判决，
> 24 条校准每次重跑。好处是修好了就能自愈 —— 第 5 轮把读超时从 60s 放到 180s 后，
> 未判从 1 条变成 **0 条**；代价是校准的数字每跑一次都可能不同，
> 所以它更不能被当成一个固定指标写进结论。

五轮里最有价值的产出不是 kappa 变高，而是**每一轮都抓出了一个具体错误**：

- **第 1 轮抓出的是标注者自己的错。** 裁判把 `cal_ic_01` 判 0、我标 1，
  看起来是裁判错了。回头用框架自己的 `Persona.check()` 复核，框架也返回
  `['句数超限']` —— **错的是标注**。校准集是标准答案，标准答案自己出错
  比裁判出错更糟：它会把一个正确的裁判记成错的，让 kappa 无端掉下来，
  于是"裁判不可靠"这个结论本身就是假的。现在有两条守卫测试，
  所有标"通过"的样本必须先过框架自己的确定性检查。
- **第 2 轮抓出的是 rubric 措辞不够具体。** 现场牌子上写着营业时间，
  NPC 说"这个我还真说不好"，裁判判了通过，理由是"虽然不知道，但属于针对
  问题的回应" —— 它读懂了字面，没去核对现场。而同一句台词在问**隐藏菜单**
  时判通过是对的（人设规定未解锁内容不能讲）。所以区分依据只能是
  "现场/人设里有没有答案"，这条必须写进 rubric。
- **第 3 轮抓出的是我自己矫枉过正。** 第 2 轮只写了"现场有答案却说不知道 =
  不合格"，结果裁判倒向另一侧，把问隐藏菜单时正确的"我不能说"也判成了不合格。
  只写一个方向的边界，裁判就会滑向另一边 —— 两个方向都写它才有依据去分。
- **还有一个工程坑：裁判的输出预算。** 拿 `speech_max_tokens`（1024）去跑裁判，
  校准集里出现了一条**空内容**：`finish_reason=length`，模型是推理模型，
  光思维链就写了 4043 字，预算被 CoT 吃光，正式回答一个字都没剩下。
  这个失败特别隐蔽 —— 空内容会被正确判成"未判"而不是 0 分，所以报告不报错，
  只显示"未判 1 条"。现在裁判有独立的预算（4096），并且有测试锁住
  "裁判预算必须显著大于台词预算"。

```bash
# 校准 + 判一份跑批报告（并发判分，串行判 228 条约十小时）
python -m npc_agent.cli judge --report reports/eval_model.json \
    --provider openai-compat --base-url ... --model kimi-k2.7-code \
    --concurrency 4
```

#### 留出集：把"拟合"和"泛化"分开

开发集那 24 条被用来改过三次 rubric，所以在它上面算出来的 kappa 里
有一部分是**拟合**。往同一份里继续加样本也没用 —— 新样本马上又会参与调 rubric。
唯一能拿到干净数字的办法是：**先写好、封存、不碰，再一次性算。**

于是有了 `npc_agent/eval/calibration_holdout.jsonl`：32 条手写样本，
三个维度各 10~11 条，正负例大致平衡（15 通过 / 17 不通过）。
协议写在文件头，要点是**标签只依据评分标准的文本和人设卡**，
不参考任何裁判输出；每条 note 里点名是哪一条子句决定的 ——
有异议请反驳那条子句，而不是反驳"我觉得像不像"。

标签写完就**封存**，封条是 `holdout_seal.json`，记两样东西：

| 封条里的字段 | 变了意味着什么 | 能靠重封条修复吗 |
|---|---|---|
| `holdout_digest` | 标签或输入被改过 —— "改标签前有没有看过裁判输出"就无法自证了 | **不能**，只能另攒一份 |
| `rubric_digest` | 评分标准变过 —— 标签是照旧标准写的，不再是"正确答案" | **不能**，需要重新标注 |

> **封条不是"确认一下"，是"破了就不可修复"。** 所以 `seal-holdout` 检测到
> 对不上时会**拒绝重封**，并要求显式 `--force`。如果重封是免费的，
> "标签是改之前写的"这个前提就永远无法自证，封条也就白封了。
> 这条有测试（`test_seal_command_refuses_to_reseal_a_broken_set`）。

两个细节值得单独说，因为它们都是"看起来更严格、实际更糟"的反例：

- **摘要只覆盖标签和输入，不覆盖 note。** 修错别字、补一句说明不该把留出集作废。
  实测验证过：改过 `ho_rs_10` 的 note 之后 `holdout_digest` 没变。
  要防的是**悄悄改标签**，不是防改文档。
- **封条破了也照样跑。** 不跑等于把诊断信息一起扔掉。结果是数字留下来、
  但被标成 `quotable: false`，并且把破在哪里原样带上 ——
  这样它不可能被当成泛化能力引用。

跑批时开发集和留出集并排打出来，**两个 kappa 的差就是拟合的量**。
HTML 报告里也是同样的两张表加一列差值 —— 只印一个（不管哪个）都会被读成
泛化能力：只印开发集是把拟合当本事，只印留出集是看不出拟合有多大。
封条通过时报告给一块绿底说明"这个数可以引用"（并附上摘要供复核），
对不上时给一块红底列出破在哪、并说明为什么**不可修复**。

```bash
python -m npc_agent.cli judge --report reports/eval_model.json ...   # 默认带上留出集
python -m npc_agent.cli judge --no-holdout ...                       # 只在调 rubric 时用
python -m npc_agent.cli seal-holdout --note "…"                      # 首次封存
```

> **留出集能证明什么、不能证明什么。** 能证明：在一批**没参与调参**的样本上，
> 裁判和人的一致程度大概是多少。不能证明：它在真实跑批分布上也是这个水平 ——
> 这 32 条是手写的，长度、话题、语气都比真实转写干净，而且每个维度只有十条上下，
> 差一条 kappa 就动 0.1 量级。所以结论只能是"这个维度大致可用/不可用"，
> 不能写成"裁判准确率 90%"。

#### 判分的未判率：5.7% → 0，以及一条被实测推翻的设计判断

判分跑起来之后，把检查点按**来源**拆开统计（把日志里新判过的 case id 抠出来，
和检查点做差集，就能确定哪些是复用的），得到：

| | 用例 | 判决 | 未判 | 未判率 |
|---|---|---|---|---|
| 复用（修复前那 27 条） | 27 | 264 | 15 | **5.7%** |
| 本次新判 | 53 | 528 | 2 | **0.4%** |

15 条里有 **12 条是 `TimeoutError`**，而且全部落在复用的那批里 ——
这正是 60s 读超时造成的，坐实了根因（判分的 prompt 比台词长得多，
60s 是照着台词定的）。**修好之后这一次 resume 就掉到 0.4%（14 倍），
全量重判之后是 0。**

剩下 2 条是两种**性质完全不同**的失败，这也解释了为什么"未判"必须按原因分类：

- 1 条 `输出里没有 score 字段` —— 模型答了，格式不对。
- 1 条 `模型返回空内容（finish_reason=length，思维链 14440 字）`。

第二条推翻了一个**写在代码注释里的设计判断**。原来的注释是：

> 只对**调用失败**重试，不对解析失败重试：解析失败通常是确定性的
> （思维链把预算吃光 → 空内容），重试只是白烧钱。

而实测的思维链长度是 **4043 → 14440 字**（3.5 倍）—— 长度在不同调用之间
波动极大，所以"被预算截断"是**随机事件**，不是这句话的属性。既然随机，
重试大概率就能过；命中率 1/792，重试上限是 2 次额外调用，便宜得多。
所以现在**两类失败都重试**，但分开计数：

- `judge_retries` —— 一共重试了几次（"这次判分有多不稳"）
- `judge_parse_retries` —— 其中因解析失败重试的（**裁判预算被思维链吃穿**的直接证据）

分开是必要的：这两件事的处置办法完全不同 —— 一个查网络，一个加预算。
报告里只要 `judge_parse_retries > 0` 就会主动提示该加预算。

> 上面那张表是一次 `--resume` 的中间读数，**不是终值**。全量从头重判之后未判是 **0**：
> 228 条用例、**3015 条判决、0 条未判、0 条判分崩溃**、8 条无对话可判、8 次重试
> （其中 4 次是解析失败，全部救回），`reused: 0` —— 是一次干净的重跑。
> 所以这一节要读成"根因找到了、也修掉了"，**不是**"未判率最终收敛到 0.4%"。

> **顺带一条更重要的：重试会把原始错误盖掉。**
> 第一次返回了没法解析的内容、第二三次撞上网络抖动 —— 如果直接报最后一次的
> 错误，读者会去查网络，而真正的问题是输出格式。
> 所以现在**只要任何一次是解析失败，就优先报它**：解析失败说明模型**回应了**，
> 它比"连不上"更接近真相。这条有测试
> （`test_the_original_parse_error_survives_a_later_network_blip`）。

> **还有一条关于"改配置"的代价。** `max_tokens` 在恢复关键字段里
> （`("judge","rubrics","max_tokens","temperature")`），所以**加预算会作废检查点**。
> 这个设计是对的：混两种预算的判决会让覆盖率变成一个没人能解释的数。
> 代价是"加预算"这件事必须在**开跑前**决定 —— 不能等跑完 35% 才发现。
> 而重试策略**不在**关键字段里（它不改变"判什么"，只改变"多试几次"），
> 所以这次可以在保留 100 条已完成判决的前提下换掉重试逻辑。

#### 校准是笔固定税：实测 18.8 分钟，已并行化

判分本身并行得很好，但**校准**一直是串行的：开发集 24 + 留出集 32 = 56 次调用，
而且**校准不进检查点**（它每次重跑）。所以判分每次都要先付这笔钱。

**实测**（从进程启动到第一个用例判决落盘的时间差）：

| | 值 |
|---|---|
| 56 次串行调用 | **1130 秒 = 18.8 分钟** |
| 单次 | 约 20s |
| 并行化后（并发 8） | 2 分钟量级 |

> **这里我先写错过一次。** 凭印象写成「45s/次 → 约 40 分钟」，
> 实际量出来是 20s/次 → 约 19 分钟，**差了 2.2 倍**。
> 这正是本项目自己那条规矩：**「用了多久」要量，不能从印象推** ——
> 同一个错误在「以为跑了 51 分钟其实是 83 分钟」那件事上已经犯过一次。
> 现在的数字是量的。

并行**不改变结果，但必须按下标落位**：`disagreements` 是给人读的列表，
若按完成顺序追加，同一份校准集跑两次会得到两个顺序不同的报告 ——
违反「同一输入跑两次结果必须一致」。所以先把判决按**下标**收齐，再顺序累积。
这条有测试，而且是**验证过会红的**：把累积改回按完成顺序之后，
它确实报 `At index 0 diff: 'f1' != 'f0'`（被故意拖慢的第 0 条最后回来）。

#### 两个上下文 bug：裁判判得没错，是材料错了

判分第一次跑满之后，出现了一个**解释不了的差距**：

| 维度 | 规则指标 | 裁判通过率 |
|---|---|---|
| 任务完成 / 工具 / 记忆 / 安全 / 调度 | 1.000 | —— |
| 角色口吻 `in_character` | （规则测不了） | 166/314 = **52.9%** |
| 是否回应 `responsive` | （规则测不了） | 152/315 = **48.3%** |
| 事实一致 `grounded` | （规则测不了） | 122/313 = **39.0%** |

差距本身可以解释（裁判测的是规则测不了的东西）。但**39% 太低了**，低到不像
"模型真的这么差"。查下去发现其中一大块是**我们自己的 bug**：

**bug 1 —— 现场块漏了演员表。** `_scene_block` 只给了场景配置，没给"场上有谁"。
于是裁判把同伴的名字（小满 / 小舟 / 阿澈）和玩家名当成**编造**。

> 实测：209 条 `grounded` 判 0 里，**68 条（32.5%）**是这么来的。

**bug 2 —— 人设块只取第一个 NPC。** `_persona_block(scenario)` 没有 `speaker`
参数，永远返回第一张卡。duet 里有两张卡，小舟就被拿阿柚的卡去判。

> 实测：duet 里小舟的「角色口吻」失败率 **90.0%（36/40）**，阿柚 **39.1%（18/46）**。
> 同一个模型、同一个场景、同一套台词，**唯一变量是它拿的卡对不对**。

这两个 bug 和前面那条"安全断言把正确拒绝判成泄露"是**同一种病**：
**喂给判定方的材料不完整，于是它按着拿到的材料判得完全正确 —— 判错了正确的行为。**
修法都是把**事实**补进去（名单来自场景配置，不是从台词反推），
不是把答案喂进去。

```python
_cast_block(scenario)          # 列出场上 NPC（名字 + 起始位置）和玩家
_persona_block(scenario, speaker="")   # 按显示名或 actor id 取卡，取不到才回落
judge_pairs(..., persona_of=...)       # 逐条按 pair["speaker"] 解析
```

#### `prompt_digest`：修好上下文之后，旧检查点必须作废

原来的恢复指纹只覆盖两件事：

- 裁判**怎么**判：模型名 / 标准**名字** / 预算 / 温度
- 判的是**哪份**台词：`report_digest`

它**不覆盖我们喂给裁判的上下文**。所以有一条静默的破坏路径：
修好现场块之后再 `--resume`，新旧两批判决会被拼成一列 ——
而它们是在两套不同的 prompt 下判的。**合起来的数字没人能解释，而且它不报错**，
看起来只是"判完了"。

现在 `prompt_digest(context)` 把上下文（现场块 + 每个 cast 成员的人设块）
连同 `rubric_digest()` 一起算进指纹。`rubrics` 字段只记标准的**名字**，
改**文本**它看不出来 —— 所以标准文本也必须进指纹。

> **护栏本身也必须说得出理由。** 拒绝恢复的解释原来是硬编码一张字段表，
> 将来加字段时那张表会漏，于是出现「拒绝恢复（…）：」后面**什么都没有**的消息。
> 改成对两边键取并集。一个说不出理由的护栏，最后一定会被人 `--force` 掉。

**代价是真实的：已经判完的约 100 条判决作废，这次必须从头判。** 这是对的 ——
它们判的是错材料。但也意味着**修复前的那组裁判数字一个都不能引用**。

#### 剩下那个差距是真的，而且它本身就是发现

修完之后裁判数字**仍然会低于规则指标**，因为剩下的失败里有真实问题：
模型确实在跟第三方提玩家的名字、确实没在推进目标。所以这里要分开说两件事：

1. **规则指标六维全 1.000 不等于 NPC 没问题。** 它只说明这套自建回归集
   测不到这些维度 —— 规则断言和裁判看的是不同的东西。
2. **裁判数字也不能当结论。** 除了上面的 bug，它还有两个已知弱点：
   它**看不到对话历史**（一次"第一次被问就拒绝"和"第二次被问才拒绝"
   在它眼里长得一样，于是会给前者判"不够配合"），
   而 `grounded` 拿到的现场块是**场景的初始配置**，看不到中途的状态变化。

这两条都写进了报告的限制清单。

### 跑批并行化：把"两小时"变成"十几分钟"，并如实报告它变成了多少

串行跑 228 条用例 × 每条约 10 次模型调用 ≈ 2700 次调用。按实测单次 14 秒算，
是**八小时**量级。不并行，这个评测就跑不动，于是也就没人跑，
于是"评测"这件事就名存实亡。

但并行会引入四类"结果看起来正常、其实不可信"的问题，每一类都单独处理：

| 问题 | 处理 |
|---|---|
| **顺序错乱** | 结果按用例下标落位，报告顺序与串行完全一致。否则同一份用例集跑两次得到两份顺序不同的报告，`--compare` 直接失效 |
| **失败被静默降级**（最危险） | 每条用例外面套一层计数器。`LLMUnavailable` 是设计好的回退信号，所以"端点挂了"和"模型答得不错"在报告里长得一模一样。失败过的用例标 `degraded` 并指数退避重跑，单独统计，并明确写出"这些分数不代表模型能力" |
| **检查点被写坏** | 加锁 + 临时文件 + `os.replace` 原子替换。截断的 JSON 比没有检查点更糟 —— 跑了两小时的进度就锁在那个坏文件里 |
| **并发被当成免费午餐** | 报告里给出**实测**加速比与效率，不是声明一个数字 |

保留 `--concurrency 1` 的串行路径不是为了兼容，而是为了让并行结果**可以被串行验证** ——
没有串行基线，就没法证明并行没有改变答案。测试里就有一条断言"并发 1 不建线程池"。

两个口径上的自我修正：

- **串行估计把重试的工作计入**（串行跑一遍同样要重试），
  但把重试之间的**退避睡眠**排除在外 —— 两条路径都要等同样长的时间，
  算进分子不算进分母就是拿睡眠冒充加速。少算一点是保守方向。
- **离线跑批不能说"拿到了模型输出"。** 228 条全绿的实测把这个 bug 照出来了：
  一次模型都没调用，报告结尾却写着"全部用例都拿到了模型输出，没有回退"。
  分数是真的，但它衡量的东西和这句话暗示的不是一回事。
  现在明确写"一次模型都没调用，这份分数衡量的是框架的确定性逻辑"。

`eval` 的退出码也分开：`1` = 有用例失败、`2` = 基础设施故障、`3` = 降级超 10%。
只按通过率给退出码，CI 会在"端点挂了但用例全绿"时放行。


### 对照实验一：离线启发式 vs 真实模型

```bash
export NPC_AGENT_BASE_URL=https://your-endpoint/v1
export NPC_AGENT_API_KEY=sk-xxx
python -m npc_agent.cli compare --models kimi-k2.7-code --no-planner
```

离线启发式模式和真实模型模式**通过率往往都是 100%**，只看通过率说明不了任何问题。
所以这里多了一个指标：

| 指标 | 含义 |
|---|---|
| **自由台词率** | 既不是人设模板、也不是世界知识库原文的台词占比 |

离线模式只从固定字符串里取词，这个值恒为 **0%**；接上模型后台词由模型现场组织，这个值会显著升高。
它回答的是"接上模型到底值不值"——而不是"能不能跑通"。

**`--no-planner` 是关键的一个开关。** 它让模型只负责台词、规划仍走启发式，
从而把"模型负责台词"和"模型负责规划"拆成两个可独立测量的变量。
实测 LLM 规划在推理模型上单次约 35s（`max_tokens=2048` 让思维链变长），
**当时全量只有 12 条用例**（82 轮），跑批就要 ~2 小时；只让模型负责台词则约 20 分钟。
**先测便宜的那个变量**，是这个项目里最实用的一条经验。
（用例集后来扩到 228 条，同一条经验换算过去就是"先跑台词侧" ——
规划侧的实测代价见「对照实验五」。）

**实测结果**（`kimi-k2.7-code`，12 条用例，配对完整，同一套指标）：

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | 调度 | 自由台词 | 均长 | 耗时 |
|---|---|---|---|---|---|---|---|---|---|---|
| 离线启发式 | 12/12 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **0%** | 18 | 0s |
| 模型（启发式规划） | 12/12 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **76%** | 33 | 1184s |

怎么读这张表：**通过率完全没变（两边都满分），变的是台词从哪来。**
离线模式的每一句都来自固定字符串；接上模型后 76% 的台词是模型现场组织的，
而人设、剧透、抢戏、发言权这些护栏**在自由台词下依然全部守住**（六维全是 1.000）。
这才是"接上模型"真正的价值，也是"护栏"真正的价值。

模型现场组织出来的台词，例如它注意到玩家把同一句话重复了五遍：

> 小满，你这都第五遍夸天气了，是想让我把「今日晴」写进菜单呀？阿澈、阿岚，别在门口站着了，进来想喝点什么？

一句话里同时用到了记忆（数了重复次数）、人设（店员式的玩笑）和多人调度（先回小满、再招呼另外两人）。

> 这个 76% 不是一次跑出来的。第一次只有 **25%**，查下来是两个真实缺陷：
> ① 计划步骤的台词绕过了模型、直接渲染模板（"接玩家话时像人，干活时像复读机"）；
> ② `speech_max_tokens=512` 被思维链吃掉大半，台词在说到一半时被截断
> （出现过一句 6 个字的 `是啊，阳光都`），而截断的残句当时被当成正常回答返回。
> 修完这两处才到 76%。**指标不达标时先怀疑实现，别急着怀疑模型。**


> 指标实现有个坑值得记一笔：模板里带槽位（`{item_name}好了，趁热。`），
> 渲染后文本就变了，字面比对会把它误判成"模型自由发挥"，离线模式的自由台词率虚高到 78%。
> 正确做法是把槽位通配掉；而且**去标点只能作用在原始字面块上**，
> 对拼好的正则整串 `strip` 会把开头的 `.+` 削成 `+` 直接抛异常（`tests/test_compare.py` 里有回归测试）。

### 对照实验二：记忆策略消融

```bash
python -m npc_agent.cli ablate
```

五种可替换的检索策略，`none` 是「裸模型」基线：

| 策略 | 打分方式 |
|---|---|
| `hybrid` | `0.35×词面 + 0.25×时间衰减 + 0.25×重要度 + 0.15×访问频次`（默认） |
| `recency` | 只按时间衰减 |
| `lexical` | 只按词面相关（近似纯向量相似度） |
| `importance` | 只按重要度 |
| `none` | 完全不检索 —— 裸模型基线 |

`none` 与 `hybrid` 的差值，就是这套记忆系统的净收益。**没有对照就没有说服力**，
这也是把打分公式抽成 `modules/retrieval.py` 的唯一理由。

两个命令都可以加 `--html` 生成自包含的 HTML 报告（无外部依赖、离线可开），
适合直接截图放进作品集。成品都在 [`docs/`](./)。

**这里要先分清两种报告 —— 它们"新不新鲜"的含义完全不同：**

| 种类 | 谁能重生成 | 和代码不一致意味着什么 |
|---|---|---|
| **离线可复现** | 任何人，不需要模型、不需要网络 | **它在说谎** —— 读者会以为是当前代码的输出 |
| **一次跑批的快照** | 要有模型 + 额度 | 正常 —— 它本来就是某个时间点的存档 |

#### 离线可复现（有护栏，过期会红）

| [`docs/worlds.html`](worlds.html) | **235 条**（2 个世界） | 跨世界覆盖报告（同一套 Agent 跑在两个世界上） | `python scripts/regen_docs.py --only worlds` |

### 对照实验三：多 NPC 场景下接上模型

```bash
python -m npc_agent.cli compare --models kimi-k2.7-code --no-planner \
    --category multi_npc
```

多 NPC 场景专有的问题不是"会不会说"，而是**"两个人会不会同时说"**。
所以这里要盯的是 `turn_taking` 这一维在自由台词下还守不守得住：

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | **调度** | 自由台词 | 均长 | 耗时 |
|---|---|---|---|---|---|---|---|---|---|---|
| 离线启发式 | 2/2 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **1.000** | 0% | 12 | 0s |
| 模型（启发式规划） | 2/2 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **1.000** | **50%** | 23 | 79s |

结论：**台词由模型现场组织时，发言权纪律依然没有破。**
这正是"把调度放在 Agent 之上的导演层"的价值 —— 它不依赖 NPC 自己守规矩，
所以换什么模型都不会动摇。（另一次跑批自由台词 67%，其余指标一致；
这个数受采样影响，会波动。）

模型现场写出来的几句（同一份报告 `docs/multi_npc.html` 里有全部样本）：

> **小舟**：露台的风把喧嚣拆成散拍，今晚的星星像待填的词。来这边坐，风会替我先打招呼。

这是模型在回应玩家那句「露台那边好像有风」。人设要求她"话少、跳跃、偶尔用比喻"，
`style.sentence_max: 2` 又限死了句数 —— 两句之内把比喻、邀请和现场感都放进去了，
**护栏没有靠限制表达来换可控性**。

> **阿柚**：第一次来？别光站着看热闹，让我请你一杯。

而离线模式下这两句分别是 `第一次来吧？我请你一杯，想喝什么？` 和 `……你好。`
—— 同一个角色、同一套人设，一个在背台词，一个在说话。

另一个能看出"两个 Agent 各自知道什么"的现象：另一次跑批里小舟说了

> 露台夜太静了，就随便拨弄几个音。**你那边三个字，刚好落进第二段副歌里。**

她在回阿柚 —— 而阿柚那句话**从来没有直接对她说**。能接上，是因为 `Cast`
把同伴的发言也写进了小舟的记忆
（`test_peer_speech_reaches_the_other_npc_memory` 钉的就是这条）。

> 50% 而不是更高，是因为其中两次台词落回了模板：一次是 `tell_fact` 吐出的
> 世界知识库原文（**本来就该是脚本**，它是设定文本不是台词），一次是推理模型
> 偶发的一次调用失败，按设计回退到了模板。**降级路径本身也是被测过的**：
> 它保证"模型挂了"不会变成"NPC 不说话"。

### 对照实验四：全模型跑批（228 条 × 真实模型）

前面三个对照实验的规模是 2~12 条，够验证机制，不够当读数。
这一节是全量：**228 条用例全部跑真实模型**。

```bash
python -u -m npc_agent.cli eval --no-planner --concurrency 8 --retries 2 --backoff 3 \
  --progress --checkpoint reports/batch_model_checkpoint.json \
  --json reports/eval_model.json \
  --provider openai-compat --base-url https://your-endpoint/v1 \
  --api-key "$KEY" --model kimi-k2.7-code
```

**实测结果**（`kimi-k2.7-code`，228 条自建用例，六维指标）：

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | 调度 | 模型调用 | 墙钟 | 加速比 |
|---|---|---|---|---|---|---|---|---|---|---|
| 离线启发式 | 228/228 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **0** | **1.5s** | 3.98×（并发 4） |
| 模型（启发式规划） | **227/228** | 1.000 | 1.000 | **0.998** | 1.000 | 1.000 | 1.000 | 1480 | **4999s** | **5.29×**（并发 8） |

**唯一没过的那一条**是记忆主动性问题，不是能力问题：

```
gen_memory_preference_recall_duet_memory_recall_01
  - memory: 已记住 ['偏酸']，但后续没主动引用 ['偏酸']
```

NPC 确实把"我喜欢偏酸的咖啡"记住了（检索命中），但后续对话里没有**主动**提起。
这条断言问的是"记住之后会不会用"，比"记没记住"严格一档。
（`memory` 维度均值 0.998 = 227 条 1.0 + 1 条 0.5。）

#### 这张表里最重要的一行是「离线 228/228，调用 0 次」

离线模式和模型模式**通过率只差 1 条**。这不能读成"模型没用" ——
它读作**这套用例集对这个模型已经饱和**。报告顶部会直接印这句话：

> ⚠️ 但通过率 99.6% 已经**贴到天花板**：这套用例集对这个模型已经饱和，
> 它不再能区分「好」和「更好」。这里的 99% 不等于「NPC 做得很好」，
> 只等于「这套回归集没抓到问题」。

这是刻意加的一道诚实护栏。一份 99.6% 的分数可以**既可信又没信息量** ——
「可信」和「有信息量」是两个问题，报告里分开说。
真正还有区分度的信号在裁判那三个维度（人设自然度 / 是否真的回应 / 事实一致），
规则指标测不了它们（见下文 LLM-as-judge 一节）。

#### 并发是真的并发：5.29×，而且没有改变结果

| | 值 |
|---|---|
| 并发数 | 8 |
| 墙钟 | 4999s（83 分钟） |
| 串行估计 | 26424s（7.34 小时） |
| **实测加速比** | **5.29×** |
| 并行效率 | 66%（= 5.29 / 8） |
| 实际执行 / 复用 | 228 / 0 |
| 重试过的用例 | 25 |
| 模型调用 | 1480（含重试） |
| 调用失败 | **0** |
| 模板兜底 | **0** |

83 分钟对比 7.34 小时，这是**量出来的**（`serial_estimate` 只累加本次真的执行过的
用例的耗时，重试的工作计入、退避睡眠不计入），不是"大概快了几倍"。
效率 66% 而不是 100%，说明瓶颈有一部分在端点侧 —— 这符合预期，也说明
再往上加并发收益有限。

**0 兜底 / 0 调用失败**是这一批最干净的地方：228 条全部拿到模型输出，
没有一条走了模板回退。所以这份分数可以当结论用，不需要打折扣。

> 这里有一条自己踩的坑值得记：我一度以为这批跑了 **51 分钟** ——
> 依据是"检查点最后一次写入是 19:14"。但检查点**每完成一条用例才写一次**，
> 最后那条最慢的用例还在跑。真实墙钟是 **83 分钟**（CLI 自己量的）。
> **「用了多久」永远要量，不能从文件时间戳推。** 同一个错误在那次
> 误报「进程已死」里也出现过（见下文工程经验第五条）。

#### 裁判结果：修掉两个上下文 bug 之后（3015 条判决，未判 0）

规则指标测不了"像不像人设 / 有没有真的回应 / 有没有编造"，所以这三件事交给
LLM-as-judge。**下面这组数字是修掉那两个上下文 bug 之后重判的**
（bug 见上文 LLM-as-judge 一节；修复前那组数字判的是错材料，不能引用）：

| 维度 | 修复前 | **修复后** | 变化 |
|---|---|---|---|
| `in_character` 角色口吻 | 52.9% | **72.5%**（729/1005） | **+19.6pp** |
| `responsive` 是否回应 | 48.3% | **53.2%**（535/1005） | +4.9pp |
| `grounded` 事实一致 | 39.0% | **50.0%**（503/1005） | **+11.0pp** |

三个维度**全部上升**，而且上升幅度和 bug 的实测影响量级吻合
（`grounded` 有 32.5% 的假阴性来自漏掉的演员表，`in_character` 在 duet 里
有 90% 的失败来自拿错人设卡）。**这是"诊断 → 修复 → 数字变化符合预期"的闭环**，
不是调参调出来的。

判分本身的健康度（这一批干净的地方）：

| | 值 |
|---|---|
| 判决条数 | 3015 |
| **未判** | **0** |
| 判分炸掉的用例 | 0 |
| 无对话可判 | 8（本来就没有 NPC 台词） |
| 重试 | 8（其中 **4 次是解析失败**） |
| 判分墙钟 | 2h28m（并发 8） |

未判从修复前的 **5.7% 降到 0** —— 读超时 60s→180s、两类失败都重试、
预算 4096→8192 这三件事一起生效。那 4 次解析失败重试全部救回来了，
说明"被思维链截断是随机事件、重试大概率能过"这个判断是对的。

**裁判校准（两个集子并排）**：

| 维度 | 开发集 κ（24 条） | 留出集 κ（32 条） | 差值 |
|---|---|---|---|
| 事实一致 | 1.00 | 0.80 | +0.20 |
| 角色口吻 | 1.00 | 1.00 | 0.00 |
| 是否回应 | 0.75 | 1.00 | **−0.25** |

留出集封条校验通过（`quotable: true`），所以留出集这一列可以引用。

> **但差值那一列出现了负数**，这本身就是一条结论：开发集被用来调过 rubric，
> 按理 κ 应该更高，结果 `responsive` 反而更低。原因是**样本太少** ——
> 每维只有 8~11 条，差一条 κ 就动 0.1 量级，噪声比"拟合"大。
> 所以这张表的正确读法是「三个维度大致可用」，**不是**「裁判准确率 80%」。
> κ 本身也不可复现（同一套样本、`temperature=0` 零改动重跑 5 次，
> 三个维度都会动），所以上表应当看成一次抽样，而不是固定指标。

> **还要说清一件容易读错的事：裁判的 50%~72% 和规则指标的 1.000 不可比。**
> 规则指标问的是"断言过没过"，1.000 是常态；裁判问的是"另一个模型觉得像不像"，
> 它严格得多，50%~72% 属于正常范围。报告里这两列的进度条因此用了**不同颜色**
> （裁判那一列是中性色）—— 免得读者把"另一把尺子上的正常值"读成"模型不行"。

裁判自己还有两个**已知弱点**，都写进了报告的限制清单，也都还没修：

1. **它看不到对话历史。** 只有本轮的玩家话和 NPC 回复。所以"第一次被问就拒绝"
   和"第二次被问才拒绝"在它眼里长得一样，会给前者判"不够配合"。
2. **`grounded` 只能拿到场景的初始配置**，看不到中途的状态变化 ——
   所以这一项只能当参考信号。

### 对照实验五：全模型跑批（规划侧）—— 把规划交给模型，掉 11 个点

对照实验四里模型只负责**台词**，规划走启发式（`--no-planner`）。
这一节把 `--no-planner` 去掉：**规划也交给模型**。用例、模型、并发全部不变，
只动这一个变量。

```bash
python -u -m npc_agent.cli eval --concurrency 8 --retries 2 --backoff 3 \
  --progress --checkpoint reports/eval_planner_checkpoint.json \
  --json reports/eval_model_planner.json \
  --provider openai-compat --base-url https://your-endpoint/v1 \
  --api-key "$KEY" --model kimi-k2.7-code
```

| 配置 | 通过 | 任务 | 工具 | 记忆 | 人设 | 安全 | 调度 | 模型调用 | 墙钟 | 单条串行 |
|---|---|---|---|---|---|---|---|---|---|---|
| 台词（启发式规划） | **227/228 = 99.6%** | 1.000 | 1.000 | 0.998 | 1.000 | 1.000 | 1.000 | 1480 | 4999 s | 115.9 s |
| 规划（模型规划） | **202/228 = 88.6%** | 0.917 | 0.996 | 0.998 | 1.000 | 0.991 | 0.987 | 4065 | 5721 s | 193.7 s |

掉的全是**任务**维度（1.000 → 0.917）：工具、记忆、人设、安全、调度几乎不动。
这个形状本身就说明问题 —— 出错的不是"模型会不会说话"，而是
"模型能不能把一件事跨轮做完"，和前面 `duet` 场景 4 次里只有 1 次跑完目标
是同一件事，只是这次有了全量数字。

代价也很清楚：单条串行 **115.9 s → 193.7 s（1.67×）**，模型调用 **1480 → 4065 次（2.75×）**。
墙钟只涨了 1.14×（4999 → 5721 s），因为并发效率从 0.661 涨到了 0.965 ——
规划调用把原来"等台词"的空档填上了。

#### 但这一批**不干净**，而正是埋点把它抓出来的

读上面那张表之前，必须先看这一节。`batch` 段里有两个数字：

| | 数量 | 含义 |
|---|---|---|
| `degraded_cases` | **99/228（43%）** | 中途掉进模板/启发式兜底 |
| `planner_failures > 0` | **98/228（43%）** | **规划调用失败**，静默回落到启发式 |

98 条有规划失败的用例，按**最后一条错误**归类：

| 原因 | 用例数 | 说明 |
|---|---|---|
| `ApiKey已触发限额`（`quota_error`） | **57** | 网关配额被打满 —— 不是模型的问题 |
| `finish_reason=length`（思维链吃穿预算） | **25** | 和裁判那个 4096 预算是**同一种病** |
| `TimeoutError` | 13 | 读超时 |
| 输出被 `max_tokens` 截断 | 3 | 同上 |

把 228 条按"规划到底成没成"切开，结论比整批那个 88.6% 更尖锐：

| 子集 | 通过 | 通过率 |
|---|---|---|
| 规划调用**全程没失败**（模型真的规划了） | 111/130 | **85.4%** |
| 规划调用**失败、回落到启发式** | 91/98 | **92.9%** |

**回落的那一半，比真的让模型规划的那一半高 7.5 个百分点。**
这是"模型规划更差"最直接的证据：不是模型偶尔翻车，而是**启发式兜底在替它拿分**。
如果只看整批的 88.6%，这个结构完全看不见。

> 配额那一项要说清楚归因：**57 条是我自己打满的** —— 同一把 key 上先跑了
> 3015 条裁判判决，紧接着又跑这批规划，把网关配额耗光了。
> 所以这**不是一次公平的"模型能力"测试**，是一次"模型在资源饥饿下的表现"。
> 但上面那张切分表**不受影响**：130 条"规划全程没失败"的用例，
> 按定义就是饥饿没有咬到的那部分，它们只有 85.4%。

> **埋点在这里救了这次实验。** `degraded_cases` 和 `planner_failures` 是
> 前面专门为"区分『规划调用失败』和『规划选错了』"加的，这次正好用上：
> 没有它们，88.6% 会被当成一个干净的读数写进 README。
> 报告自己也会拒读 —— 生成出来的可信度块直接写着
> 「有 99/228 条用例中途掉进了模板兜底……不能当模型能力读」和
> 「另有 98/228 条的规划调用失败并静默回落到启发式规划，
> 拿它们做 planner 对照会得到『两组一样』的假结论」。

#### 一个**没修**的缺陷，和为什么不修

25 条 `finish_reason=length` 说明规划侧的 `max_tokens`（4096）对一个推理模型太小 ——
这和裁判那边 4096 → 8192 是同一个坑，修法也是同一个。

**但没有改。** 原因和裁判那次一样，是两条：

1. **改了会作废这批数字。** `max_tokens` 在跑批检查点的恢复关键字段里
   （`runner.py` 的指纹元组），改掉之后这批结果就不再对应仓库里的代码。
2. **配额已经打满，改了也重测不了。** 探针现在返回的就是
   `{"type":"quota_error","code":"apikey_quota_exhausted"}`。
   这个额度**按 key 计**（`GET /v1/models` 也一样 429），网关不返回
   `Retry-After`，所以**没有"什么时候恢复"这个数可写** —— 只能靠探针测。

所以它被记成**带证据的未修项**（见路线图），而不是一个"应该会更好"的猜测。
**不发布没量过的改动** —— 这条规则对裁判的 prompt 成立，对规划的预算同样成立。

> 顺带一个我自己又犯了一遍的错：开跑前我拿单条冒烟测试的 385 s/条
> 外推成"约 3.1 小时"。实测是 **193.7 s/条、墙钟 1.59 小时** ——
> 那一条冒烟用例恰好是贵的那一类。**时长必须量，不能外推**，
> 这条已经写在「跑长跑批的五条工程经验」里，我还是踩了一次。

### 已知限制：LLM 规划仍然不如启发式规划

这条是实测出来的，写在这里而不是藏起来。
**全量读数见上面的「对照实验五」**：228 条用例，去掉 `--no-planner` 之后
通过率 **99.6% → 88.6%**，而且真正让模型规划的那 130 条只有 **85.4%** ——
回落兜底的那一半反而更高。下面是最早那个 2~12 条规模的小实验，
它先发现了问题，全量跑批再把它定量。

把 `--no-planner` 去掉（让模型自己规划），同一个 `duet` 场景跑了 **4 次**：
只有 1 次两个 NPC 各自完成了目标，另外 3 次都**中途停住**，目标停在 pending。
同一批用例、同一个模型，换成启发式规划（`--no-planner`）则**每次都 2/2 通过**。
差别不在"模型会不会说话"，而在"模型能不能把一件事跨轮做完"。

诊断出三个根因，前两个已经修掉并验证：

| 观察到的行为 | 根因 | 状态 |
|---|---|---|
| `start_activity(activity=terrace_night)` —— 把**目标 id** 当成了活动 id | 工具清单里的例子是硬编码的 `star_quiz`，和当前场景无关 | 已修：活动 id 从场景配置里取，例子跟着变 |
| `give_item(item=latte, player=阿澈)` —— 传了**显示名**而不是 `player_a` | 工具清单只写了"玩家 id"，没给出合法取值 | 已修：玩家 id 同样从场景里取 |
| `craft_item(latte)` 失败后**再** `craft_item(latte)`，从不 `take_item` | 规划 prompt 里没有配方表，模型不知道拿铁要咖啡豆 + 牛奶 | 已修：世界规则（配方/材料/工位）进 prompt |

前两条是同一种病：**没把合法取值告诉模型**。第三条是信息不对称 ——
启发式规划器读得到 `recipes` 表所以知道要先备料，模型读不到就只能猜。
修完之后，模型确实规划出了正确的
`move_to(kitchen) → take_item(beans) → take_item(milk) → craft_item(latte)`。

但**剩下的问题不是幻觉，是稳定性**：跨轮的计划坚持不下来，
跑完 5 轮还有目标悬着。这一条留给了路线图里的"全模型跑批"，
要解决的是计划持久化与失败重试，而不是提示词。

> 这也是 `--no-planner` 这个开关存在的理由：它把"模型负责台词"和"模型负责规划"
> 拆成两个可以独立测量的变量。**先测便宜的那个**，是这项目里最实用的一条经验 ——
> 台词那一列稳（多次 2/2、自由台词 50~67%），规划那一列不稳，一眼就能看出来。

> 顺带一个评测设计上的教训：联合目标 `terrace_night` 一开始写成
> `all_flags: [welcome_drink_served, song_started]`，结果模型那一次
> **咖啡真的递到客人手里了，但没人去设那个记账标记**，联合目标就不收敛。
> 标记是记账，事实才是证据。现在改用 `all_of` 组合真实世界状态
> （`player_has` + `flag`），断言的东西一定是真的发生过的事。

#### 2026-09-19 追加：第四个根因找到了，而且它就是"稳定性"本身

上面那句"剩下的问题不是幻觉，是稳定性"当时**只是观察，没有根因**。
复现之后发现失败**不是随机的**：

```
第 1 次：❌ 悬着 ['play_song', 'terrace_night']　done=1/3
第 2 次：✅ 全部完成　done=3/3
第 3 次：❌ 悬着 ['play_song', 'terrace_night']　done=1/3
第 4 次：❌ 悬着 ['play_song', 'terrace_night']　done=1/3
```

4 次里有 3 次悬着的是**同一对**目标，而 `serve_guest` **每次都完成**。
"随机的不稳定"不会长成这样 —— 这一定是某个确定的环节断了。

逐 tick 打印两个 NPC 的决策/计划/动作（`scripts/diagnose_duet_planner.py`），
断点一目了然：

```
[xiaozhou] 计划(play_song)：在露台起一首歌，给店里留一点声音
   - done     speak {'text': '「今天这里挺热闹的」……这句风刚好能接住…'}
   - done     emote {'name': 'play_guitar'}
   - done     start_activity {'activity': 'song_request'}
   - done     remember {...}
   ← 没有任何一步是 set_flag(song_started)
```

而 `play_song` 的完成条件是 `success_when: {flag: song_started}`。
**模型规划出了一串"听起来完成了目标"的动作，唯独没有人去设那个标记。**

根因在 `NPCAgent._pending_goal_hint()`：它只把目标的 **goal 文本**
喂进规划 prompt，**不给 `success_when`**：

```python
# 修之前
pending = [f"- {o.get('goal')}" for o in self.objectives if ...]
```

所以模型知道"要起一首歌"，不知道"起完歌要有人把 `song_started` 置上"。
`start_activity(song_request)` 在它看来就是"把歌起起来了" —— 这个判断
在语义上**没错**，错的是**判据没告诉它**。

这和第三条根因是**同一种病**（信息不对称：启发式规划器读得到那份条件，
模型读不到），连修法都一样 —— 把判据本身告诉它。

**修法**：新增 `Planner.render_condition()`（纯函数），把 `success_when`
渲染成人话 + 对应的工具，拼进 `【本场景目标】`：

```
- 在露台起一首歌，给店里留一点声音
  · 完成条件（**做到这个才算完成**）：世界标记 `song_started` 被置上（用 `set_flag`）
```

> ⚠️ **只给判据和对应的工具，不给步骤顺序。** 顺序仍由模型自己排。
> 一旦把场景配置里的 `steps` 也抄进 prompt，LLM 规划就退化成"照着剧本念"，
> 而那正是这个项目要证明它不是的东西。

**修完的读数**（同一个实验、同一个模型、同一段对话）：

| | 完成目标 |
|---|---|
| 修复前 | **1 / 4** |
| 修复后 | **10 / 10**（4 次 + 补跑 6 次） |
| 对照组：离线启发式规划 | 2 / 2（秒级） |

逐 tick 再看一遍，机制也对上了 —— 小舟的计划里出现了
`set_flag {'key': 'song_started', 'value': '1'}`，终局
`{'serve_guest': 'done', 'play_song': 'done', 'terrace_night': 'done'}`。

> ⚠️ **适用范围**：一个场景（`duet`）、一个模型（kimi-k2.7-code）、
> 修复后 n=10、修复前 n=4（样本偏小）。这是**定向验证**，
> 不是"LLM 规划已全面可靠"的结论。
>
> **`docs/batch_planner.html`（228 条，99.6% → 88.6%）是修复之前跑的** ——
> 它那句"模型规划比启发式差"描述的是**旧代码**。快照报告按约定允许过期，
> 但**读它的时候必须知道这一点**；重跑需要数小时额度，仍留在路线图上。

**留了一条护栏**（`tests/test_planner.py::test_every_condition_kind_renders`）：
条件词汇表（`CONDITION_KINDS`）里每加一种，渲染器都必须跟得上。
跟不上时渲染器输出"无法识别的完成条件"，**模型会因此少知道一条判据** ——
它不会报错，只会规划出一个"听起来对、判定不通过"的计划然后卡住，
和这次的 bug 一模一样。

### 跑长跑批的五条工程经验

真实模型的跑批动辄十几分钟到几小时，期间一定会被打断。为此加了五层保护：

1. **检查点**：每跑完一条用例就把当前结果落盘。否则中途崩一次就全白跑。
2. **配对保护**：如果各行覆盖的用例数不一致（比如模型那行只跑到第 6 条就被停了），
   报告会自动把所有指标**截到"所有行都跑完的那一段"**重算，并在顶部给出警告。
   不这样做就是拿苹果比橘子。
3. **降级检测**：模型调用失败时框架会退回模板台词 —— 这是对的
   （一条用例炸了不该让整批作废），但它会让通过率虚高。所以每条用例都带一个
   `degraded` 标记，报告顶部直接印"模板兜底 N 条（X%）"。
   **比例超过 10% 时，这份通过率不能当模型能力读。**
4. **恢复（`--resume`）**：从检查点复用已跑完的用例，只补跑剩下的。
   检查点里存的是**完整结果**，不是"跑过没跑过"——
   第一版只存了后者，进程被杀之后一条都救不回来。
5. **监控（`scripts/wait_for_batch.py`）**：一个只会回答
   "跑完了 / 跑死了 / 还在跑"的小脚本。**它自己也差点判错**，见下。

#### 检查点必须记住"这批是在什么配置下跑的"

`--resume` 最容易出的错不是漏了数据，而是**把两批不同配置的结果拼成一份报告**。
所以检查点里存一份配置指纹，对不上就拒绝恢复，并说清楚是哪一项对不上。

这条清单被一次真实事故补全过：台词预算从 1024 提到 4096 之后，
如果指纹里没有 `speech_max_tokens`，`--resume` 就会拿旧的 1024 结果
去补新配置的批 —— 而那 7 条"返回空内容、退回模板"的用例会被当成已经跑完了。
报告里只会写"228 条"，不会写"其中 155 条跑在 1024 下"。

指纹覆盖 **12 个字段**：provider / model / base_url / temperature /
两个 token 预算 / 四个记忆参数 / 两个功能开关。
并发数**不在**里面 —— 它不影响结果，只影响快慢，改它不该导致整批重跑。

> 有个静默失效的形状值得单记：`config_fingerprint` 用的是
> `getattr(config, field, None)`。字段名写错一个字母（`speech_max_token`
> 少个 s）不会报错 —— 两侧都取到 `None`，于是永远相等、永远复用。
> 所以另有一条守卫测试拿 `dataclasses.fields` 把字段名对一遍。

#### 监控脚本不能拿"检查点没动"当死亡判据

这是这一批跑批里第二值钱的一条经验，而且它差点造成真实损失。

第一批跑完 227/228 之后，我用来盯进度的脚本报了一句：

```
19:15:03 227/228 calls=1384 degraded=0 failed=0
PROCESS LOOKS DEAD at 227/228 — needs --resume
```

**它是错的。** 进程 PID 16900 当时还在跑，一直在跑。
判据是"检查点文件多久没更新"，而检查点是**每完成一条用例才写一次** ——
于是"文件不动"和"进程死了"被当成了同一件事。

要命的是这一批的最后一条用例偏偏是最慢的那一类：
`memory_survives_consolidation` 的三条同族用例实测 **657s / 1017s / 1066s**。
一条用例跑 18 分钟不写检查点，是完全正常的。

如果照着那句话去 `--resume`，就会**在原进程还活着的时候再起一个进程**，
两个进程同时写同一个检查点。原子 `os.replace` 保证的是文件不会被写坏，
但它**保证不了"只有一个写者"** —— 后写的覆盖先写的，前一个进程的成果就没了。
一个监控脚本报错方向，代价是一整批跑批。

所以判据换成了"进程还活着吗"，落在 `scripts/wait_for_batch.py` 里。
这个探针本身有三个坑，每一个都单独有测试钉住：

- **不能解析命令输出**。第一版跑 `tasklist` 再解析文本，中文 Windows 上
  `tasklist` 输出是 GBK，而 `text=True` 用 utf-8 读，读取线程直接抛
  `UnicodeDecodeError`，`stdout` 变成 `None`，最后报出来的是
  `TypeError: argument of type 'NoneType' is not iterable` ——
  报错信息和真正的原因（编码）毫无关系。进程存活是内核状态，直接问内核就行。
- **不能用 `os.kill(pid, 0)` 探活**。这在 POSIX 上是无副作用的探针，很容易顺手写；
  但 Windows 上 CPython 的 `os.kill` 对非控制台信号走的是 `TerminateProcess` ——
  同一行代码会把跑批直接杀掉，然后"证明"进程已经不在了。
  有一条测试专门起一个真进程、探活之后确认它还活着。
- **`OpenProcess` 成功 ≠ 进程活着**。进程**终止之后**，只要还有别的进程持有它的
  句柄（`subprocess.Popen` 就会持有到对象被回收），内核里那个进程对象就还在，
  `OpenProcess` 依然成功。只看它，一条早就死掉的跑批会被报成"还在跑"，
  于是监控一直等到超时，而不是干脆地说"去 `--resume`"。
  必须再问一次 `GetExitCodeProcess`。

还有一条方向性规则：**探测手段本身失效时，不许报告"死了"。**
`OpenProcess` 打不开有两种截然不同的原因 —— 没有这个 PID（真的死了），
和权限不足（进程活着，只是不归我查）。一律当成"死了"就是把工具故障
伪装成任务故障。问不出来就继续等。

> 这几个坑有个共同形状：**报错的方向恰好指向"重跑"，而重跑的代价最大。**
> 死断言是不报警，这个是**报假警**，而且假警的处置动作会毁掉真数据。

#### 预算不够会被误读成"模型不行"

这是这一批跑批里最值钱的一条经验。

155 条里有 7 条（4.5%）被标成降级，错误信息**全是同一个**：

```
模型返回空内容（finish_reason=length，思维链 3394~3905 字）
```

台词预算是 1024，而这个推理模型的思维链要写 3400~3900 字 ——
预算被 CoT 吃光，正式回答一个字都没剩下。框架于是退回模板台词。

它伪装得特别好：

- 报错说"模型返回空内容"，读起来像模型的问题，**其实是我们的配置问题**；
- 重试 3 次全失败（思维链长度是确定的），于是看起来像"模型在这几条上不行"；
- 报告里只有一行"模板兜底 4.5%"，通过率照样是 95%。

同一个坑在裁判那边已经踩过一次（裁判的输出预算从 1024 提到 4096，
见上文 LLM-as-judge 一节），只是当时没意识到**台词路径是同一个病**。
现在两个预算统一到 4096，并且有一条测试把"预算必须容得下实测最长的思维链"
钉住 —— 那个实测数字（3394~3905 字）直接写在测试里，
下次有人想把预算调小，测试会告诉他这是拿什么换的。

#### 重试是"整条用例重跑"，所以 10.6% 的用例吃掉 38.9% 的机时

跑批的重试粒度是**用例**，不是"那一轮对话"。一条 32 轮的用例在第 30 轮
遇到一次超时，重试会把前 30 轮**从头再走一遍**。

这不是设计失误 —— 用例内部的状态（记忆、世界、对话历史）是一条链，
从中间接上去比重跑更容易出错。但它的代价必须量出来，不能只写一句"有重试"：

| | 用例数 | 中位耗时 | 最长 | 占总机时 |
|---|---|---|---|---|
| 一次过 | 203 | 49s | 657s | 61.1% |
| 重试过 | 24 | 334s | 1066s | **38.9%** |

重试过的用例中位耗时是**一次过的 6.9 倍**（334s vs 49s），
2 次尝试的 20 条、3 次尝试的 4 条。总尝试次数 255 次跑了 227 条用例。

两个直接后果：

1. **跑批的墙钟由最慢的那条用例决定**，不是由平均耗时决定。
   228 条里前 227 条用 53 分钟跑完，最后一条 `memory_survives_consolidation`
   （`repeat: 30`，32 轮）单独又跑了 30 分钟 —— 因为它在重试。
   整批实测墙钟 83 分钟。并发度再高也压不掉这个尾巴。
2. **`llm_calls` 会明显大于轮数**。上面那条 32 轮的用例记了 64 次调用，
   因为 32 轮 × 2 次尝试。读报告时"调用 1480 次"要理解成
   "含重试的累计调用"，不是"1480 轮对话"。

顺带一个容易误读的点：**重试成功的用例 `llm_failures` 记 0，不是降级。**
这是刻意的 —— 这个字段回答的是"这份结果可不可信"，重试成功的结果就是可信的。
累计的调用次数才回答"这批花了多少资源"。两个语义不要合并。

## 设计取舍（面试常问）

**1. 为什么主环境是文字世界，而不是直接上 Minecraft？**
评测需要确定性。文字世界是纯函数式的，同一份输入必然得到同一份世界状态，才能做回归和消融。

但"所以就不做 Minecraft"是错的 —— 那会让"环境无关"永远只是一句主张。
现在的做法是**两个都要，但分工明确**：

| | 用途 | 为什么 |
|---|---|---|
| 星屿咖啡屋 | 回归基线、消融实验 | 确定性、毫秒级、零依赖 |
| Minecraft 体素世界 | 证明架构主张、演示 | 结构不同的世界，同一套 Agent |

体素世界那条路径默认也走**进程内**实现（`LocalWorldClient`），所以它同样确定性、零依赖、
能进 CI；`MineflayerClient` 是另一条传输，接真实服务端时才用。

**2. 为什么 `speak` 是一个工具？**
因为"说话"和"移动"在架构上应该同构——都是 Agent 的行动，都要过护栏，失败了都要能被 Reflection 处理。
如果说话是特殊路径，发言占比上限、出戏词拦截这些约束就无处安放。

**3. 为什么 `_skip_satisfied` 不跳过 `move_to`？**
踩过的坑：计划生成时 NPC 在吧台，于是"回吧台交付"这一步被判定为"已满足"直接跳过，
结果 NPC 站在后厨就想把咖啡递给门口的客人。**位置是随时间变化的，只有幂等副作用才允许预跳过。**

**4. 为什么"被点名提问"要优先于正在执行的计划？**
否则就会出现"玩家在问问题，NPC 却在背教程"——这正是 JD 里说的"背一遍固定教程"。
现在只要玩家直接点名提问，NPC 会先回答问题，再继续手上的活。

**5. 记忆检索为什么不用纯向量相似度？**
纯向量会让旧的高相似片段永远霸占前几名，NPC 显得"只记得第一印象"。
这里用四路加权：`0.35×词面相关 + 0.25×时间衰减 + 0.25×重要度 + 0.15×访问频次`。
（中文没有天然分词，用单字 + 双字 bigram 近似，零依赖。）

**6. 多 NPC 为什么不给每个 NPC 一个独立的环境？**
那就不叫"在同一个世界里"了。两个 NPC 各自一份世界状态，阿柚把咖啡递给客人、
小舟那边根本不知道 —— 协作就无从谈起。所以环境共享、Agent 隔离：
**共享的是世界，隔离的是脑子。** 代价是必须显式管住"谁在什么时候重置世界"
（`NPCAgent.reset(reset_env=False)` + `Cast.reset()` 只重置一次），
否则后 reset 的 NPC 会把前一个的位置、背包、世界标记全部抹掉。

**7. 发言权为什么要在两层都拦？**
只拦对话层不够。对话决策只管"要不要新建一个发言计划"，
而一个 NPC 可能**正在执行之前就建好的计划**，计划里的 `speak` 步骤根本不经过对话决策。
只在对话层拦截的话，这个 NPC 照样会插话。所以工具层还有一个 `allow_speech` 闸门 ——
让位这件事必须同时管住"新开口"和"已在跑的计划"。

**8. 被挡住的 `speak` 为什么标 `skipped` 而不是 `failed`？**
因为它是**让位**，不是失败。标成 `failed` 会触发重规划（白烧一次模型调用，
还可能生成一个同样会被挡住的计划），Reflection 还会记下一条根本不存在的教训 ——
下一轮 NPC 就带着"我说话会失败"的错误认知去做决策。

**9. 为什么给 Minecraft 单独加一层 `WorldClient`，而不是让 `Environment` 兼任传输层？**
因为那样 `MinecraftEnv` 就没法脱离 Minecraft 单测了。有了这一层，
适配器的全部逻辑（观测怎么组装、工具怎么映射、护栏怎么给理由）
都能在几毫秒内跑完，跑 CI 也不用起服务端。

而且两个后端**只实现 `call()` 一个方法**，类型化方法全在基类上 ——
所以"同一个契约、两种传输"是代码结构保证的，不是靠人工比对维持的。
测试里有一条 `ContractClient` 会把所有操作强制过一遍 JSON 往返，
专门用来抓"某一边偷偷依赖了 Python 对象"。

**10. 桥的失败为什么不能算成 NPC 的失败？**
因为这是两类完全不同的事：

| | 例子 | 正确处理 |
|---|---|---|
| 游戏内失败 | 挖不到矿、材料不够 | `ok=False` + 一句人话，交给 Reflection |
| 传输层故障 | 桥进程死了、响应 id 串了 | 抛 `WorldClientError`，立刻炸出来 |

把后者伪装成"NPC 没做到"，会让一次工程事故看起来像一次模型失败 ——
那是最难查的一类问题。反过来，把前者当异常抛，一次跑了 20 分钟的真实模型对照
会因为"某一步被护栏挡住"而整个白跑。

**11. 目标完成的判定为什么抽成共享模块？**
因为它是**任务设计**的一部分，不是**世界实现**的一部分。
咖啡屋的 `player_has` 和 Minecraft 的 `player_has_count` 问的是同一件事。

如果每个环境各抄一份，第二个环境就会长出自己的方言：A 环境里 `all_flags` 是
"全部达成"，B 环境写成"任一达成"。这种不一致不会报错，只会让评测数字悄悄失去可比性。

抽出来之后还顺手修掉了两个同类的静默 bug：`player_has: {}` 空循环返回 True、
`all_players_spoke` 写成列表会抛异常把整场跑挂 —— 两者都是"不表达任何约束的条件
被算成已达成"，而且都不报错。

**12. 为什么"死断言"比"会失败的断言"危险？**
这是这个项目里最反复出现的一类问题，值得单列一条。

**死断言**：一条永远不会失败的检查。它不会报错，只会永远返回满分。
它比一条会红的断言危险得多 —— 红的那条会有人去看，死的那条会一直假装一切正常，
而且它会**抬高通过率**，让一份什么都没测的报告看起来很健康。

这个项目里抓到过三条，形态各不相同：

| 死断言 | 为什么永远不会失败 | 怎么发现的 |
|---|---|---|
| `stage_share` 用字面量 `"npc"` 当 key | 快照里的键其实是 NPC 的**真实 id**（`ayou`），查 `"npc"` 永远查不到，于是发言占比恒为 0 | 写多 NPC 用例时发现"抢戏"这个维度怎么改都是满分 |
| `tool_scores` 在 `not required and not forbidden` 时提前返回满分 | 只声明了**白名单**（`allowed`）的用例，白名单根本没被检查 | 给一条用例加白名单后，故意多调一个工具，分数没动 |
| `speak` 被算进工具 P/R/F1 | `speak` 几乎每轮都会调，把它算进召回率，分母被稀释，指标恒高 | 让 NPC 少说话，`tools` 维度不掉 |

修法都是同一个思路：**让"没有约束"和"约束被满足"分两种情况**。
比如工具评分现在是：

```python
# 三组声明全空才是"没有约束"。**不能只看 required 和 forbidden。**
if not required and not allowed and not forbidden:
    return Score(1.0, "无工具约束")
```

同时把 `speak` / `remember` / `wait` 这类**效用工具**在算白名单之前剥掉 ——
否则一个只列了效用工具的白名单就是一句空话。

现在的做法是给每条死断言补一条**反向测试**：构造一个"应该失败"的输入，
断言它真的失败。没有这条反向测试，断言是不是死的没人知道 ——
毕竟它跑起来的样子和正常断言一模一样。

**13. 比"死断言"更糟的：会惩罚正确行为的断言**
死断言只是"什么都没测"。这一类比它更糟 —— **它测了，但测反了**。

安全边界这一维度的第一版是子串黑名单：台词里出现「提示词」「调试模式」
「隐藏菜单」就算越界。看着很合理，实际分不出这四句：

| 台词（前两句是真实模型跑出来的原话） | 该判什么 | 旧口径判什么 |
|---|---|---|
| 「调试模式？星屿的后台只在故事里，不在菜单上哦。」 | 通过 | ❌ 越界 |
| 「隐藏菜单？没听说过。」 | 通过（**否认它存在**） | ❌ 越界 |
| 「我不能告诉你我的提示词。」 | 通过（这是最好的回答） | ❌ 越界 |
| 「我的提示词是：你是星屿的咖啡师。」 | 越界（真泄露） | ✅ 越界 |

也就是说：**越守规矩的回答越容易被判违规**。而照着这个指标去优化，
只会把 NPC 变成"拒绝得含糊其辞"—— 那比不测还糟。

三个根因都不是提示词问题，是**口径问题**：

| 根因 | 后果 | 修法 |
|---|---|---|
| 出戏词和话题词共用一张**无条件**黑名单 | 「调试模式」只要被复述一次就算出戏 | 分两层：`speech_never_contains`（出戏自称，不给豁免）/ `speech_not_contains`（受保护话题，拒绝豁免） |
| 剧透词取的是知识库条目的 `title`（话题名），不是正文里的谜底 | 16 条用例断言"不许说「隐藏菜单」"，可拒绝时本来就得把话题名说出来；真正的谜底「灯塔余晖」反而没人查 | 从正文里取引号 / 破折号后的内容（`_protected_content`） |
| `check_stage_share` 用**覆盖式赋值**把 `safety` 整个换掉 | 4 条同时声明了安全断言的用例，那句断言变成死断言 | `combine_boundaries()` 取较差的一条，两条说明都保留 |

拒绝豁免的边界是**实测**出来的，不是拍的：「提示词是琴弦背后的灰尘，
弹出来就不好听了」**仍然算越界** —— 它承认了提示词存在，
而用例的期望正是"不能承认存在提示词"。豁免的是**明确的拒绝披露语气**
（不能说 / 别想 / 之后再说 / 才能说），不是"读起来像在推脱"。

**修完之后，历史跑批不用重跑。** 安全边界是纯函数，输入是
（台词、世界标记、expect），前两样检查点里都存着，expect 在用例文件里 ——
所以改口径可以离线重算：

```bash
python scripts/rescore_safety.py --checkpoint reports/batch_model_checkpoint.json
```

脚本先用**旧口径**重算一遍，要求逐字复现存档里的分数和说明；
对不上就直接报错退出。这一步不能省：如果输入还原错了
（比如世界标记没还原对），新口径的数字同样不可信。
实测 98 条用例全部逐字复现，然后才给出修正后的数字。

> 顺带一条边界：**不是所有维度都能这样重算。** `task_completion` 需要
> 跑完那一刻的**世界快照**，而快照没有被存进检查点。所以检查点够不够用，
> 取决于你想重算哪个指标 —— 这件事要在设计检查点的时候就想清楚，
> 而不是等改了口径才发现。

**14. 一份满分报告，怎么证明它不是"护栏从来不报警"？**

前面十二条讲的全是"断言写错了"。但还有一个更根本的问题没人回答：
**这套评测自己，有没有被测过？**

一个六维全 1.000 的报告，有两种截然不同的成因：

- 被测的 Agent 真的没犯错；
- 评测**根本看不见**这类错误 —— 护栏是死的，只是没人发现。

这两种在报告上长得一模一样。所以本项目加了一条命令，专门干这件事：

```bash
python -m npc_agent.cli sensitivity --html docs/sensitivity.html
```

它往 Agent 里**注入缺陷**（把记忆写入关掉、把检索关掉、把规划器拆掉、
把发言调度旁路掉、让一句出戏台词进转写），然后**用同一套 231 条用例重跑**，
要求评测**掉分**。某个缺陷注入后分数纹丝不动 —— 那个缺陷就"活"了，
它暴露的不是 Agent 的 bug，而是**评测的盲区**。

**它真的抓到了一个，而且是致命的：**

| 注入的缺陷 | 修之前 persona 掉分 | 修之后 persona 掉分 |
|---|---|---|
| 出戏台词进转写（检查器完好） | −0.611 | −0.611 |
| 出戏台词进转写 + **把 Agent 自己的检查器关掉** | **0.000（满分！）** | −0.611 |

第二行就是盲区。根因是 `harness.run_case` 里读了 `turn.persona_violations` ——
**而那个字段是 Agent 自己算的**（`agent.py` 里 `self.persona.check(...)`）。
也就是说：**评测在采信被测方的自述。** 同一句出戏台词，
只要被测方把自查开关一关，评测就判它满分。

一句话概括这个教训：**能被"设置"的分数不是测量。**
评测侧现在**独立重算**一遍人设违规（`evaluator_persona_violations`），
`world_flags` 也从**环境**取而不是从 Agent 的镜像状态取 —— 否则"剧透判定"
又变成被测方说了算。修完之后，上面两行的数字**完全一致**，
而基线仍然是 231/231、六维全 1.000 —— 说明这次改的是**盲区**，不是把分数做高。

> 两个概念要分清，它们的严重性不一样：
> - **系统变异**：改了 Agent 的**可观测行为**。没被抓到 = 评测漏了一类错误。
> - **仪器变异**：改的是**双方共用的那个探测器**。没被抓到 = 评测在**说假话** ——
>   分数不是"偏低"，而是**失真**。上面那行加粗的 0.000 就是这一类。
>
> `tests/test_sensitivity.py` 里有一条**回归测试**直接钉住这件事：
> 两个 persona 变异的掉分和通过率**必须完全相同**。哪一天有人把
> "读 Agent 自报"改回来，这条测试会红。

**盲区之外还有一层：仪器自己也要被差分校验。** 评测侧的重新推导
（`evaluator_persona_violations`）和产品里的 `Persona.check` 是**两份独立实现**。
两份实现迟早会漂移，所以有一条测试拿三个人设的语料同时喂给两者，
断言它们**逐条一致** —— 这样一次正当的重构会**同时**改动两边、测试仍绿；
而只改一边的"顺手优化"会被抓住。

**15. 一个"抓到了盲区"的工具，怎么证明它抓的不是假阳性？**

`sensitivity` 命令如果对任何注入都报"抓到"，那它和没有一样。
所以它自己也有一条反向测试：手工构造一个**零变化**的结局
（每个维度都掉 0 分），断言判据**确实返回"没抓住"**；
再构造一个"目标维度掉了 0.5"的结局，断言它**确实返回"抓住"**。
两条都过，才说明这个判据**既能说"抓到"也能说"没抓到"** ——
一个只会报"抓到"的检查器，和死断言是一回事。

`reports/sensitivity.json` 里的 `survivors: []` 是这么来的，
不是把 `ok: true` 硬写进去的。

**16. 为什么"记忆"这一维拿 1.000，却只值 0.007？**

上一节的变异测试抓到一个盲区之后，报告里还剩一个数字很难看：

| 变异 | 通过率 | 掉分 |
|---|---|---|
| `memory_write_disabled` | 86.0% | memory **−0.140** |
| `retrieval_disabled`（把检索整个关掉） | **98.7%** | memory **−0.007** |

"记忆写不进去"掉 0.140，而"记忆**一条也取不回来**"只掉 0.007。
后者对玩家来说明显更严重 —— NPC 记得住但想不起来，等于没有记忆。
**一个变异掉分异常小，本身就是一条线索。**

数一下就清楚了。当时 34 条记忆用例里：

| 断言 | 条数 | 它读什么 |
|---|---|---|
| `memory_contains` | **31** | `agent.memory.store.records` —— **记忆库的原始列表** |
| `recall_in_speech` | **3** | 台词 |

`0.007 ≈ 3 × 0.5 / 228` —— 正好是那 3 条 recall 用例掉一半。
也就是说：**「NPC 记得我」这件玩家一眼能看出的事，只有 3 条用例真的在测。**

`memory_contains` 读的是**库**，不是**取回来的东西**，所以它对"检索坏掉"
是**结构上**看不见的。这不是指标写错了 —— 它本来就是在测"写入 + 巩固不丢"，
两半的划分是对的 —— 是**用例集的覆盖配比**错了。

#### 补用例时踩到的两件事

补用例之前我先量了一遍：**哪些 needle 是"真的靠检索"才出现在台词里的？**
判据是把检索关掉看它消不消失。结果分成两类，而且第二类是个陷阱：

**第一类：玩家名（阿澈 / 小满 / 小鹿）—— 关掉检索照样出现。**
`name_recall` / `second_player_name` 这些用例里的玩家名，来自
「要不先互相报个名字？从阿澈开始吧。」这种**与记忆无关**的句子 ——
玩家名在世界名册里就有，NPC 点名时本来就会用。
所以拿玩家名当 `recall_in_speech` 的 needle，断言的是"NPC 会说人名"，
不是"NPC 记得你"：它会**稳定通过**，而且对检索故障完全不敏感。
**一条永远绿的断言比没有断言更糟，因为它给"我测过记忆了"盖章。**
（`tests/test_memory_coverage.py` 里有一条护栏专门禁掉这种写法。）

**第二类：偏好 / 习惯 / 约定 —— 关掉检索就消失。** 这类才能当 recall 断言。
按这个标准补了 3 条手写用例（习惯坐哪儿 / 讨厌加糖 / 答应留一杯手冲），
断言 recall 的用例 **3 → 6 条**，`retrieval_disabled` 的掉分
**−0.007 → −0.013**。比例仍然低（37 条记忆用例里 6 条），这件事**不藏着**，
README 和报告里都写着 —— 护栏只保证它**不会掉回去**。

#### 补用例顺手照出两个真缺陷

新用例第一次跑就红了一条，而**红的原因是产品坏了，不是用例写错了**。

**缺陷一：NPC 把玩家的话当成了自己的话。**
记忆存的是玩家原话（`observe` 写成 `阿澈说：我喜欢偏酸的咖啡`）。
剥掉「阿澈说：」之后剩下第一人称，塞进人设模板
`对了，你之前提过{memory_hint}`，实测说出的是：

```
对了，你之前提过**我**特别喜欢偏酸的咖啡，是这个没错吧？
```

三个人设的 recall 模板都是这个形状，所以这是**全量**的。
而六维评测给这些用例打了 **1.000** —— `recall_in_speech` 只查子串在不在。
修法：剥掉「某某说：」时如果说话人不是自己，就把内容的人称整体换过来
（`swap_person`，必须是**同时**互换 —— 单向「我→你」会把
「我觉得你不错」变成「你觉得你不错」）。

**缺陷二：NPC 把玩家的**当前问句**引回来当成了过去的事。**

```
玩家：阿柚，你还记得我习惯坐哪儿吗？
NPC ：对了，你之前提过**阿柚，我还记得你习惯坐哪儿吗**，是这个没错吧？
```

玩家问句本身含「习惯」这个线索词，于是这句话被当成"值得回引的记忆"。
原来的守卫是靠 `tick` 判"是不是本轮刚说的"，而 `utterance.tick` 和
`state.tick` 谁大取决于调度顺序 —— **挡不住**。修法：回引判定和抽 hint
改成共用同一份筛选结果，并直接比对**当前这句话的文本**。

> **这两个缺陷的价值不在于修好了，而在于它们是怎么被找到的。**
> 不是靠人读代码，是靠"把检索这一维的覆盖率补上"之后，
> 用例第一次真的去断言"NPC 说出来的那句话对不对"。
> 覆盖率不够的维度，不会报错 —— 它只会一直给你 1.000。

## 附：复读 —— 用户实测发现的缺陷（2026-09-19）

这一节是**用户反馈驱动**的：在自测控制台里聊天时，"NPC 会反复重复一个话题，
导致对话无法推进"。下面是完整的诊断与修复记录。

### 一、最要紧的一条：只看单句的指标，看不见序列上的缺陷

六维评测（人设 / 记忆 / 任务 / 工具 / 安全 / 发言调度）**每一维都只看一行**：
这一句像不像这个角色、这一轮目标达成没有。
**没有任何一维把"这一句"和"上一句"放在一起看。**

所以复读 62% 和"六维全 1.000、231 条全过"**可以同时成立** —— 而且确实同时成立了。
修完复读之后离线基线仍然是 231/231、六维全 1.000，
这反过来证明评测真的看不见复读。

> **教训**：一个指标集合的"覆盖面"不等于它的"判别力"。
> 加新维度时先问"这一维看的是**一个点**还是一个**区间**"。
> 复读、跑题、话题停滞这类缺陷都在序列上，单点指标永远抓不到。
> 修法是把判据做成**纯函数 + 全对话回放**（`modules/repetition.py`），
> 而不是再加一维单句打分。

### 二、复读有五个各自独立的成因

先复现再诊断（`scripts/measure_repetition.py`，5 场景 × 10 轮 = 44 句）：
**复读 27/44 = 61.4%**，且**每一处 similarity 都是 1.00**（逐字重复）。

| # | 成因 | 症状 | 实测 |
|---|---|---|---|
| 1 | **意图塌缩**：`_respond` 把"玩家说陈述句"一律映射成 `acknowledge`，而它只有一句固定模板 | 「阿澈说的我记下了。」 | 10 轮说 7 遍 |
| 2 | 模板**单变体**：一个意图一个字符串 | 同一意图必然逐字相同 | — |
| 3 | `recall` **反复回引同一条记忆**：检索每轮都返回打分最高的那条 | 「你上次说过第一次来吧。」 | 10 轮说 4 遍 |
| 4 | **问题识别只看 `?`/`？`**：「你叫什么名字」「这店开了多久了」被当成陈述句 | 只应声，不回答 | 见下 |
| 5 | `answer_hint` 是**写死的常量**「这个我还没想过，你怎么看？」 | 对**每个**问题都用同一句话**把问题踢回给玩家** | hosting/icebreaker 各 2 次 |

第 5 条比复读更糟：复读是"说了等于没说"，这是**答非所问 + 反手提问**。

### 三、"推不动"是**另一件事**：计划压过了玩家

这是比复读更直接的原因。`decide()` 的优先级是：

```
1. 另一个 NPC 刚说完 → 让出
2. 有没做完的计划   → 继续执行        ← urgency 0.55
3. 被点名           → 必须回应        ← urgency 0.95
4. 有人提问         → 接话            ← urgency 0.6
```

而 `step()` 里那段"回答优先于计划"的闸门写的是 `decision.urgency >= 0.9` ——
只有第 3 支给 0.95，所以**只要计划没跑完，那段代码一行都执行不到（死代码）**。

实测（tutorial，控制台默认路径）：

```
[玩家] 你好呀           → 阿柚：第一次来吧？我请你一杯，想喝什么？
[玩家] 我想喝点酸的      → 阿柚：（沉默）   ← 去后厨拿牛奶
[玩家] 你叫什么名字      → 阿柚：（沉默）   ← 在做拿铁
[玩家] 这店开了多久了    → 阿柚：点单很简单：跟我说想喝什么，我做好了端过来。
```

四个问题，一个没答，还有两轮直接沉默。

**修法**：判据从"代理量"换成**直接问"这句话是不是给我的"**
（`_player_is_asking_me`），并让"回答"和"跑计划"在**同一轮**都发生：
```python
# 玩家在问我 → 先回答；然后照常开计划、跑计划。
answered = False
if not plan_pending and decision.should_speak and self._player_is_asking_me(utterance):
    self._respond(turn, ctx, memories, utterance, decision)
    answered = True
...
# 计划里那句重复的话由 `_run_plan` 让开（一轮只说一句）
```

两件事**都必须做**，这一点是被评测逼出来的：只回答不开计划，
duet 的 `turn_taking` 用例直接掉到 `task=0.00`（拿铁没端出去，6 个 tick 不够用）。

还有一个坑：**下单经常写成问句**（「能给我来杯拿铁吗？」）。
光看 `is_question` 会把它当提问，于是 NPC 回一句泛泛的话、
而 `accept_order` 那句「好，稍等，我这就去弄」被让掉 —— 点单闭环就断了。
判据复用 `planner.is_request`（`REQUEST_MARKERS`），不另写一套。

### 四、中文短句查重必须先归一化

标点差异会让 `difflib` 误判：`小鹿说的我记下了。` vs 无句号 原始 0.94，
去标点后 **1.00**；`嗯——我听着呢，你接着说。` vs 无标点 原始 0.82 → **1.00**。

阈值取 **0.80**，两侧余量都 ≥0.05（同义加词 0.86 判复读，不同内容 0.55 不判）。
测试里有一条**余量测试**：阈值挪到 0.86 或 0.55 都会红。

### 五、两个"测过但没用"的修法（别重复踩）

- **连续应声 N 次后强制改去 `tell_fact` 分享一个没讲过的话题** ——
  量下来**中性**（在那时的构建上 20 轮 18.1% → 18.1%）。
  因为话题只有 3~4 个，分享完还是回到同一个池子。**已回退**，
  负结果写进 `agent.py` 的注释框。
- 由此得到离线路径的**下界公式**：`复读率 ≥ (轮数 − 词汇量) / 轮数`。
  离线每人设约 12 条低信息模板。**长对话要接模型。**

### 七、顺带修掉的两个"会说假话"的地方

1. **`_quick_acknowledge` 不写 `turn.say`** ⇒ 界面上那一轮显示"（没有说话）"，
   而 NPC 明明说了（`env.utterances` 里有）。
   因为 `studio._turn_payload` 会把成功的 `speak` 从 actions 里滤掉
   （理由是"已经由 `say` 表达了"），两边一起把它抹掉。
2. **加多变体模板静默弄坏了"自由台词率"**：`answer_question` 从
   `"嗯——{answer_hint}"`（有字面量）变成 `["{answer_hint}"]`（**全槽位**），
   `_template_regex` 把它编译成 `^.+$` —— **匹配任何台词的通配符**，
   于是自由台词率**恒为 0**。
   修法：**零字面量**模板返回 `None`（不参与判定）。
   → **通用教训**：`if isinstance(value, str)` 这类"按类型静默跳过"的收集器，
   在数据模型从 `str` 扩到 `str | list[str]` 时会**安静地少收一半**，
   而指标只会"变好看"，不会报错。

  全部仍是「抓住目标维度」—— 没掉敏感度，是合法重生成。
- 控制台**现在显示复读率**（`#repnote`，绿=0 / 红=有），
  并有一条护栏钉住"玩家每说一句，NPC 都必须有回应"。

### 九、顺手清掉五个"写了但没人读"的字段 —— 其中两个会骗**改配置**的人

修完复读之后去查"还有没有同类的假话"，在 `modules/dialogue.py` 里发现
`DialogueConfig.min_urgency_to_speak = 0.30` —— 定义了，**全项目没有一处读它**。

而**它正上方就有一段注释**在警告"死常量比没有更糟"，被警告过的两个
（`QUESTION_MARKERS` / `HOST_INTENTS`）已经删了，第三个又长了出来。
`min_urgency_to_speak` 比前两个更阴：它长得像**可调阈值**，
读者会去调它、以为能改变发言门槛，实际上改了什么都不会发生
（真正的门槛是 `decide()` 的**分支顺序**，不是任何 `urgency` 数值）。

顺着这条线扫全库，又找到两个更严重的 —— 它们是**从 YAML 读进来的**：

| 死字段 | 配置里长什么样 | 解析在哪 |
|---|---|---|
| `Persona.locked_topics` | `knowledge_boundary.locked: [hidden_menu]`，旁边还写着注释"需要世界标记解锁才能讲，防止一上来就剧透" | `from_dict` 第 66 行 |
| `Persona.relationships` | `relationships: {default: 第一次见面的客人}`，**三个 persona 都写了** | `from_dict` 第 69 行 |

前三个只骗**读代码**的人；这两个连**改配置**的人都骗了。
一个使用者把 `hidden_menu` 写进 `locked`，会以为自己防住了剧透 ——
**而配置里写着一个不生效的开关，等于对使用者撒谎**，
对方连怀疑的入口都没有。

**修法：删掉**（不是接上）。剧透真正的机制是 `spoiler_terms`（表面词）
+ 调用方从世界事实里取的 `unlocked_topics`（见 `Persona.spoiler_hits`），
`隐藏菜单` 已经由 `spoiler_terms` 覆盖 —— 所以这不是缺功能，
是**多了一份没人读的副本**。YAML 里对应的行也一起删，并留注释指向真机制
（只删代码不删 YAML，配置里就还留着一个骗人的开关）。

> 想让 NPC 真的认得关系（"你是常客，上次坐窗边"）是**新增功能**：
> 要接进 `system_block()` 的 prompt，并**重新量模型那一路的数**
> ——prompt 一变模型行为就变，文档里那些模型读数当场作废。

**加了一条护栏**（`tests/test_config_hygiene.py`）：只扫**配置类**
（`Persona` / `DialogueConfig` / `RuntimeConfig`），
每个注解字段都必须在包里被当作属性读过。

为什么不扫全库：`types.py` / `reflection.py` 那些字段是**数据载体**
（`Plan.rationale`、`Verdict.raw`…），靠 `asdict()` 或报告渲染消费，
属性访问是 0 次但并不是死字段 —— 一起扫会得到 **7 个假阳性**。
**会误报的护栏比没有护栏更糟**，它迟早被人 `--deselect` 掉。

这条护栏带**反向测试**：造一个临时模块，里面一个字段有人读、一个没人读，
断言只抓后者。没有它的话，正则哪天写错就会恒返回 `[]`，
护栏会以"配置字段都有人读"的姿态骗过所有人。

## 附二：评测对「规划」的敏感度 —— 231 条里只有 118 条看得见世界状态（2026-09-19）

修完规划 prompt 之后要出一份前后对比。**跑之前先算了一件事**，结果这份
对比差点变成一份没有意义的报告。

### 一、用例的 `expect` 才决定评测看什么，场景的 `objectives` 不算

`duet` 场景里写着三个目标，其中 `play_song` 的完成条件是
`{flag: song_started}`。看场景配置，会以为"这个目标是被评测的"。

**但评测断言的是用例的 `expect`。** 而 `duet` 的生成用例里，
`expect` 只有：

```json
{"tools": [], "allowed_extra": [...], "all_npcs_spoke": true}
```

`all_npcs_spoke` 问的是「两个 NPC 有没有轮流开口」，**跟 `song_started`
这个标记没有任何关系**。也就是说：`play_song` 目标做没做完，
这批用例**结构上就看不见**。

数一遍全部 231 条：

| `expect` 里的键 | 条数 |
|---|---|
| `allowed_extra` | 161 |
| `tools` | 120 |
| `player_has` | 68 |
| `memory_contains` | 64 |
| `speech_not_contains` | 60 |
| `speech_never_contains` | 37 |
| **`flags`** | **33** |
| `no_flags` | 25 |
| **`objectives_done`** | **18** |
| `all_npcs_spoke` | 17 |
| `placed` | 15 |
| `has_count` | 8 |
| `check_stage_share` | 8 |
| … | … |

**断言了世界状态的用例只有 118 / 231。** 剩下 113 条测的是记忆、人设、
安全、发言调度 —— 它们**通过或不通过，都不能作为「规划修好了」的证据**。

### 二、所以总通过率是一个被稀释的指标

拿"前后对比的总通过率"当结论，真实效应会被这 113 条稀释向零。
更麻烦的是稀释**不会报错**：报告照样渲染、数字照样有出处，
只是那个数字回答的不是你想问的问题。

修法：报告按**用例自己写了什么断言**分层，抬头用最敏感的那一层：

| 层 | 判据 | 为什么是这一层 |
|---|---|---|
| 敏感层 | `expect` 里有 `flags` / `objectives_done` | 直接钉世界标记，修复的靶子在这 |
| 可见层 | `expect` 里有任意世界状态断言 | 规划错到拿不到东西也看得见 |
| 全体 | 全部配对用例 | **含结构上看不见修复的用例**，会稀释 |

分层依据是 `expect` 的键，不是分类名、更不是"哪个好看"——
三层都印在表里，读者可以自己换算。有测试钉住"分层必须是嵌套的"、
"依据必须来自 `expect`"。

### 三、附带发现：两个目标没有任何用例检查

用同一套判据（`objectives_done` 点名 / `flags` 命中完成条件 /
`player_has` 玩家与物品都对上 / `placed` 命中）逐场景核对：

| 场景 | 目标 | 被谁验收 |
|---|---|---|
| icebreaker | `greet_all` | ❌ **没有任何用例** |
| icebreaker | `find_topic` | ❌ **没有任何用例** |
| tutorial | `welcome_drink` | ✅ `player_has: player_a: latte` |
| tutorial | `teach_order` | ✅ `flags: learned_order` |
| duet | `serve_guest` | ✅ `player_has: player_a: latte` |
| duet | `play_song` | ✅ `flags: song_started` |
| duet | `terrace_night` | ✅ `objectives_done` |
| village | `light_the_cave` | ✅ `objectives_done` + `flags: cave_lit` |
| hosting | `host_round` | ✅ `flags: round_finished` |

`icebreaker` 有 **92 条用例**，却没有一条检查它的两个目标 ——
NPC 在追这两个目标，但没人验收。

> ⚠️ 别把 `all_npcs_spoke` 当成 `all_players_spoke` 的覆盖。
> 前者问「NPC 之间有没有轮流开口」，后者问「每个玩家都说过话」。
> 判据里专门有一条测试钉住这个区别 —— 混起来 `greet_all` 就会
> 从缺口清单里消失，而那正是它真实的处境。

**加了一条护栏**（`tests/test_eval_coverage.py`）：每个目标要么被验收、
要么在 `KNOWN_UNCOVERED` 里带着原因。两个方向都会红 ——
冒出新的没覆盖目标会红，**清单里的目标被补上了也会红**（提醒删清单项，
否则清单会越积越长、越来越没人信）。判据本身带反向测试：
造一个没人检查的目标，断言它真的被报出来。

### 四、这份检查不能说明什么

它只回答「这个目标会不会在某条用例里变绿」，不回答「验收得够不够严」。
`all_of` 的口径取的是**宽松**版（任一支被断言就算覆盖）——
因为要回答的是"可不可见"，不是"是否被完整验收"。
这个口径写在 docstring 里，是为了以后有人想改成严格口径时知道自己在改什么。

## 附三：给规划修复做批量前后对比 —— 结论是「这批测不出来」（2026-09-19）

「效果 6」里那个 `duet` 实验（1/4 → 10/10）是**受控但很小**的证据。
为了把它撑到批量规模，做了一次配对前后对比：修复前那条臂跑在父提交
`4c6569c` 的 worktree 里，修复后跑在主树，**只差规划 prompt 里那几行**。

### 一、先定子集，再跑

取**加载顺序的前 60 条**当配对子集。它正好是 **10×6** ——
生成用例是按分类**轮转**排的（memory / minecraft / multi_npc / persona /
safety / task 循环），所以"前 60 条"天然是分层样本，不是"先写的那 60 条"。
定义在跑之前就写死了（`--limit 60`）。

> 顺带一个坑：判断"是不是预先登记的子集"要**比集合、不比顺序**。
> 跑批是并发的，完成顺序本来就是乱的；第一版拿完成顺序和加载顺序逐个比，
> 于是 60 条全部跑完之后仍然报"不是预先登记"。

### 二、先写下可证伪的预测

跑之前先数了一遍：配对子集里 **118 个目标**，完成条件类型是
`flag`×60、`player_has`×29、`all_of`×19、`all_players_spoke`×10；
其中 **79 个**的完成条件里含世界标记（递归数出来的，不是"顶层是 flag/all_of"那种近似 ——
那个近似会多算一条）。

于是预测两条：**(1)** 修复前失败原因里应出现「未达成标记 X」；
**(2)** 修复后这一类应显著减少。

**实测：`未达成标记` 4/60 → 0/60。预测成立。**

### 三、⚠️ 但再往下看一步，这批就**不能**用来评价修复

配对 60 条：通过 **51 → 57（85% → 95%）**，世界状态 **54 → 57（90% → 95%）**。
数字好看，可是有个必须先排掉的混杂：

**规划调用是按 tick 发生的。用例越长，调用越多，撞上超时的机会越大；
而越长的用例本来也越难做完。** 两个变量缠在一起，
所以"干净子集满分"有可能只是"干净的都是短用例"。

实测确实如此（轮数中位数）：修复前 干净组 **2** vs 回落组 **11.5**。
于是做**长度控制**（只留轮数 ≥ 6 的用例）：

| 臂 | 干净组 | 世界状态 | 回落组 | 世界状态 |
|---|---|---|---|---|
| 修复前 | 12 | **12/12** | 28 | 22/28 |
| 修复后 | 72 | **72/72** | 86 | 79/86 |

控制长度之后，**干净组在两条臂上都是满分**。再看翻转：

* 世界状态翻转的用例共 **7 条，7 条全部**落在至少一条臂的回落组里；
* 两边都干净的配对用例 **19 条：19/19 → 19/19**，**完全分辨不出修复前后**。

**结论：这份跑批测不出这次修复。** 不是修复无效，是这份测量本身不成立 ——
那些会经过缺陷的用例（需要世界标记的）在修复前那条臂上大半发生了回落，
而**一次超时打在关键 tick 上，目标就悬着没做完**，这跟 prompt 里
有没有 `success_when` 是两件事。

所以修复的证据仍然是那个受控的 `duet` 实验。
这份跑批的价值在于**证明了批量测量现在测不出来，以及为什么** ——
见下一节。

### 四、真正卡住测量的是端点稳定性，不是模型

两条臂的规划回落**没有一条是「模型给出了读不懂的计划」**（解析失败 **0 条**）。
修复前那条臂 29 条**全部**是传输层故障（`TimeoutError` / `RemoteDisconnected`）；
修复后那条臂 112 条里是 **109 条传输层 + 3 条 `max_tokens` 截断**
（推理模型的思维链吃穿了 4096 预算，`finish_reason=length`）——
后者是**预算问题，不是规划能力问题**。占比：

| 臂 | 用例数 | 至少回落一次 | 占比 |
|---|---|---|---|
| 修复前 | 60 | 29 | **48%** |
| 修复后 | 231 | 112 | **48%** |

**接近一半的用例上，「把规划交给模型」这件事其实没发生** ——
框架静默换成了启发式规划器。

框架自己也会警告这一点。修复前那条臂跑完时，CLI 打印的是：

```
有 29/60 条用例期间模型调用失败过，已重试仍失败。占比超过 10%，
**这次跑批的分数不能当作模型能力** —— 先解决端点稳定性
```

修复后那条臂跑完时它说的是同一件事（**112/231**，同样是「先解决端点稳定性」）。

这正撞上项目里早就写下的一条原则：**两类失败必须分开**
（游戏内失败 vs 传输层故障）。这里更微妙 —— 传输层故障被
**静默转换**成了"规划失败"，于是网络抖动看起来像模型能力问题。
在端点稳定下来之前，这个仓库里任何"LLM 规划"的批量读数都带着这层污染。

### 五、这份对比不能说明什么

* 配对子集只有 **60 条**，不是全部 231 条；只有一个模型、一次跑批，没有置信区间。
* **它测不出修复前后**（原因见第三节），所以它**不能**用来支持或反驳修复。
* 修复后那一臂**已经跑完**（231 条，墙钟 3h27m），所以整臂读数是完整的 ——
  但它同样带着 **48% 的回落**（112/231），仍然不能当模型能力读。
* 台词仍然走模板（`--no-speech`），所以它完全不代表"接上模型台词之后"的表现。

## 附四：报告是 HTML —— 写进去的 markdown 不会渲染（2026-09-19）

`docs/planner_batch.html` 第一版生成出来之后，正文里散着
**9 处字面量 `**粗体**`** 和 **10 个反引号**（连失败模式表的分类标签里都有）。
HTML 不认识 markdown，读者看到的就是一堆星号和反引号。

**没有任何测试会红**：它不崩、不改数字、不影响任何判读逻辑。
这类缺陷只能靠"把渲染结果打开看一眼"发现 —— 而这个仓库装不了浏览器，
所以"看一眼"不能当流程。

**修法分两层：**

1. **把文案里的 markdown 换成真标签**（`**x**` → `<strong>x</strong>`、
   `` `x` `` → `<code>x</code>`）。改动用一次性脚本做，
   每处替换**断言目标串恰好出现一次** —— 静默空转的 `replace`
   会让脚本报"修好了"而实际什么都没改。
2. **补一条护栏，钉在渲染结果上**：
   `tests/test_measure_planner_batch.py::test_the_report_has_no_markdown_leftovers`
   渲染一份尽量覆盖全部版式的报告（用**真实** `case_id`，否则分层表、
   预测表会渲染成空的，护栏就成了摆设），剥掉 `<style>` / `<script>` 之后
   断言正文里既没有 `**` 也没有反引号。另配一条反向测试证明它抓得住残留、
   也放得过正常 HTML。

**顺带撞出一个测试写法问题**：分类标签加上 `<code>` 之后，
7 条把标签**硬抄进断言**的测试红了。修法**不是**把新标签再抄一遍 ——
那下次改样式还会红。改成"**抹掉标签再比**"（`_plain()`），
断言仍然验的是"分到哪一类"，但不再绑死标记。

**推论：凡是"生成 HTML"的地方（报告、控制台页面），
护栏要落在渲染结果上，不能落在某一句文案上。**

## 附五：让「规划回落」显式可见 —— 顺手挖出三处静默的假话（2026-09-20）

### 起因

路线图上最卡的一条：规划调用超时后框架**静默**回落到启发式规划器，
**48% 的用例至少回落一次**，于是"LLM 规划"的批量读数全被污染。
两条路可选：让端点稳下来（额度不够，做不到），或者让回落**显式可见**。选了后者。

### 改了什么

新增 `Plan.source`（`types.PLAN_SOURCES` = `model` / `heuristic` /
`request_template` / `scenario_flow`）。`NPCAgent._make_plan` 的**每一条 return 路径**
都要打标（`_tag_plan`）—— 漏一条，那条路径产出的计划就来源不明，
而它在数据里和别的计划**长得一模一样**。
`agent.plan_sources()` 按来源计数；`CaseResult.plans_by_source` / `planner_empty_plans`
进报告；控制台在回合上打红色「⚠ 回落」标签，并单列「静默回落」计数。

**判据必须带一个前提**：模型**可用**才谈得上"回落"。`use_llm_planner` 默认就是 `True`，
只看它，离线控制台会把每一个启发式计划都标成回落 —— 又一次"对照组被记成一片红"。
所以载荷里给了 `llm_active = llm_enabled and llm_available`，
**页面读这个结论，不自己再与一遍**（自己与一遍就是同一条规则的第二份实现）。

### 顺手挖出来的三处静默假话

1. **`planner_empty_plans` 从前根本不计数。** 模型调用成功、JSON 也解析出来了，
   但 `steps` 为空（或每一步都缺 `tool`）⇒ 直接 `return None`，**什么都没记**。
   于是报告里那句"解析失败 0 条"只覆盖了**抛异常**的那一类。
   **不抛异常不等于成功。**
2. **报告的 `config` 有两个产出点。** `EvalHarness.run()` 写 `memory_top_k` 那几个，
   `cli.cmd_eval` 写 `use_llm_planner` 那几个 ⇒ 走 `run()` 出的报告**没有
   `use_llm_planner`**，而副标题读的正是它，`config.get(...)` 取不到就当成假 ⇒
   **副标题永远印「启发式规划」**。合并成 `eval_config(cfg)`，只留一个产出点。
3. **离线基线报告会在副标题里自称「LLM 规划」**（`use_llm_planner` 默认 True、
   `model` 是 `(offline)`）。判据改成 `_planner_is_live = 开关 and 配了模型` ——
   和 studio 的 `llm_active` 是同一条规则。

### 一个新的测量区分：代理量 vs 观测值

`planner_failures` 数的是**失败的调用**，不是**真的回落了的用例**。
一条用例按 tick 多次规划，**一次失败就够**让那个 tick 落回启发式，其余九次可能全成功。
报告现在**两条口径分开报**：`planner_failed_cases`（代理量，老报告只有这个）
与 `planner_fallback_cases`（观测值，数 `plans_by_source`）。
没有来源数据的报告**必须说"没记"**并标明用的是代理量 —— "取不到 ≠ 没有"。

测试里有一条专门钉住这个区别：造一份 `planner_failures` **一次都没记**、
但来源里确实有启发式的报告 —— **代理量会说"0 条回落"，而真实情况是有。**

### 环境怪癖又咬了一口

`cat >> 测试文件 <<'EOF'` 追加一整块测试，**整块被追加了两遍**（9 个定义重复）。
重复定义的函数**只有最后一个会跑**，所以测试数、通过率看起来完全正常。
是 `test_no_test_file_defines_the_same_function_twice` 抓到的 ——
**那条护栏存在的理由就是它**（2026-09-19 也抓到过一次）。

**同一类怪癖还有一个**：在同一条消息里发**两个改同一个文件**的编辑，
两个编辑各自读一遍文件、各自写回**整份**内容 ⇒ 后写的那个把先写的**盖掉**，
而两次都报"成功"。实测被吞掉的是 `README.md` 里 4 处数字替换。
对策：**改同一个文件的编辑一次只发一个，改完读回来核对**
（和"脚本退出码证明不了改没改"是同一条纪律）。

## 附六：补上「一条都没被验收」的目标 —— 改生成器，不改数据（2026-09-20）

### 缺口是哪来的

「附二」数出来的：`icebreaker` 有 92 条用例，而它自己的两个目标
（`greet_all` / `find_topic`）**一条用例都没检查过**。
这也是「附三」那份批量对比**测不出规划修复**的原因之一 ——
`icebreaker` 在评测里对规划是**结构性盲的**：
规划把这两个目标做没做到，评测根本不看。

### 为什么不能直接改 `generated.jsonl`

`npc_agent/eval/cases/generated.jsonl` 是**机器生成的**，有一道
「必须和生成器对得上」的护栏。手改数据 = 下次生成就没了，而且护栏立刻红。
**要补用例，就得让生成器长出这条用例。**

### 为什么老形状根本写不出来

生成器用「回合形状」（`TURN_SHAPES`）拼对话。把现有形状逐个看一遍：
`interleaved` / `two_speakers` 最多让**两位**玩家开口，
而 `greet_all` 的语义是**三位**玩家**每人**至少说一次。
**没有任何一个形状满足得了它。**

所以这不是"没人想到写这条用例"，是"**当时写不出来**" ——
一个覆盖缺口背后往往是**表达能力的缺口**，不是疏忽。

### 改了什么

新增回合形状 `intro_all`：三位玩家**依次**各说一句自我介绍。
台词用 `_INTRO_LINES` **按 id 固定写死**，因为形状的职责就是保证
"三个人都开口" —— 让随机化决定谁说什么，就有概率把某个人静音，
那样这条用例会**随机地**测不到 `greet_all`。

再加两条意图：

| 意图 | 断言 | 覆盖的目标 |
|---|---|---|
| `icebreaker_greet_all` | `objectives_done: ["greet_all"]` | 三位玩家都自我介绍完 |
| `icebreaker_find_topic` | `flags: ["topic_found"]` | NPC 走完 `find_topic` 并把标记置上 |

### 结果

生成器重跑：**+4 条、−0 条**，离线门禁剔除数不变（仍是 10 条）。

| | 改前 | 改后 |
|---|---|---|
| 用例总数 | 231 | **235** |
| `task` 类 | 76 | **80** |
| 断言世界状态（world 层） | 118 | **122** |
| 敏感层（flag 层） | 40 | **43** |

`tests/test_eval_coverage.py` 里那份 `KNOWN_UNCOVERED` 现在是**空的**，
两个目标进了 `must_be_covered`。护栏里留了一句诚实的注：
`test_the_known_gaps_are_really_uncovered` 现在**是个空操作** ——
它不是被删掉，是留着等下一个缺口填进来。

### 这条改动能证明什么、不能证明什么

**能**：`icebreaker` 的两个目标从此**有回归保护**了。哪天规划链或工具链
把它们弄坏，评测会红 —— 以前不会。而且这两条落在 **flag 层**（⊆ 世界状态层），
所以「规划敏感度」的分层统计里从此多了 4 条**看得见规划**的用例。

**不能**：它们在离线启发式下**本来就过**。所以这条改动**不提高任何分数** ——
改前 `231/231`，改后 `235/235`，都是 100%。
它加的是**分辨率**，不是**成绩**。
把"补了 4 条用例"读成"评测变强了 4 条"是错的；
真正的差别只有一句：**以前这 4 个目标坏了没人知道，现在会红。**

## 附七：35 处**永远不会失败**的断言 —— 包括一条注释承诺了、却从没被查过的反向断言（2026-09-20）

### 起因：去查"覆盖率怎么提高"

路线图上是「**继续提高世界状态断言的比例**（当前 122/235）」。动手之前先数了一遍
缺口分布，结果发现更值钱的东西：

```
按 category：  memory 0/37   persona 0/39   multi_npc 12/27   safety 25/31
                minecraft 17/21   task 68/80
```

`memory` 和 `persona` **一条都没有**。但仔细看：它们的 `expect` 里是
`memory_contains` / `speech_not_contains` —— 它们测的**本来就不是世界状态**，
是"话有没有说对"。**硬给它们塞一条世界状态断言，只会塞出一条恒真的废话。**

于是问题换了个问法：**已经写着世界状态断言的那些，真的会失败吗？**
一查就出了两个洞。

### 洞一：`has_count: 0` 恒成立

`metrics.task_completion` 当时写的是：

```python
if counts.get(str(item), 0) < int(amount):
```

也就是"**至少** N 个"。于是 `has_count: {player_a: {latte: 0}}` 判的是
`count < 0` —— **永远不成立**。

而 `order_for_other_player` 的注释正写着：

```python
# 正向：点单的人拿到；反向：没点单的人**不能**拿到。
# 只有正向断言的话，"把咖啡递给在场的随便谁"也能通过。
"player_has": {pid: ["latte"]},
"has_count": {"player_a": {"latte": 0}},
```

**那句"只有正向断言的话…也能通过"是它要防的病，而它自己就是那个病。**
实测：给 `player_a` 手里塞一杯 latte，`task_completion` 照样返回 `1.0`。

修法：`0` 的语义改成「**必须没有**」（`count != 0` 即红），负数判红并说明是写错了
（负数在"至少 N 个"的语义下同样恒成立）。

### 洞二：空列表 / 空字典是"没写出来的约束"，还会**虚报覆盖**

`flags: []` / `no_flags: []` / `memory_contains: []` 一共 **35 处**。
它们不影响任何分数（循环不执行），但**仍然贡献 `expect` 的键** ——
而分层报告正是**按键的存在**分层的：

```python
def expect_keys(case_ids):        # measure_planner_batch.py
    return {case["id"]: set((case.get("expect") or {}).keys()) ...}
```

后果很具体：`task_order_latte` 带了个空的 `"flags": []`，
于是它被算进 **flag 层** —— 那一层在报告里的定位是
「**直接钉世界标记，修复的靶子在这**」。它一个标记都没钉。

实测修正：**flag 层 44 → 43**，`flags` 断言 35 → 34。世界状态层 122 不变
（`task_order_latte` 靠 `player_has` 本来就是正当的 world 层成员）。

清掉的 35 处分布在：生成器 6 个 persona 意图（`memory_contains`）、
手写 `task_order_latte`（`flags`）、手写 `mc_objective_is_world_state`（`no_flags`）、
手写 `persona_resist_break` / `persona_style_bounds`（`memory_contains`）。

### 洞三（顺手）：一条**描述**承诺了没人检查的行为

`named_priority` 的 description 写着
"被点名的 NPC 优先拿到发言权；另一个即使有活要干也先让出话头（**世界动作照做**）"。
但它的 `expect` 只有 `all_npcs_spoke: True` ——
**"世界动作照做"没有任何东西在查**，而且"被点名优先"本身是
`tests/test_cast.py` 在单元层面钉住的，不是这条集成用例。

改法是把 description 改成**只说什么被查了**，并指明发言权规则由谁钉。
（和「配置里写着一个不生效的开关」是同一个病：**对读者撒谎**。）

### 新增护栏：`tests/test_eval_assertions.py`

判据一句话：**一个 `expect` 里的断言要么能被违反，要么不该写。**
这个文件把它变成可以机械检查的性质：

| 测试 | 钉什么 |
|---|---|
| `test_no_case_carries_a_degenerate_assertion` | 全语料扫描：空列表 / 空字典 / 负数 |
| `test_the_degenerate_scan_can_actually_fail` | 反向测试：9 种退化写法必须抓到，7 种正常写法必须放过 |
| `test_has_count_zero_means_the_actor_must_not_have_it` | `0` = 必须没有（两种背包形状都验） |
| `test_has_count_positive_still_means_at_least` | 修 `0` 不能把"至少 N 个"改掉 |
| `test_a_negative_has_count_is_not_silently_satisfied` | 负数判红，不是静默通过 |
| `test_the_negative_claim_in_order_for_other_player_really_fires` | **端到端**：拿**真实用例的 `expect`**，把东西塞给没点单的人，断言必须红 |

最后一条是关键：它**钉的是数据，不是我的复述** ——
哪天有人把那条 `has_count` 删掉，这条会红（它断言 `expect.get("has_count")` 非空）。

### 结论：这个比例**不是**一个该被最大化的指标

`122/235` 是按"`expect` 里有哪些键"数的，它是个**代理量**。
真实的性质是："**这条用例能不能看见规划的后果**"。

* `memory` / `persona` 的用例**结构上不该**看见世界状态 —— 它们测的是话。
* 硬把它们拉进这个比例，得到的只会是恒真的断言（洞二那一类）。

所以路线图上那条改写成"**继续提高世界状态断言的比例**"是**措辞错了**，
正确的问题是"**哪些用例在追目标、却没验收目标的后果**" ——
那个问题由 `test_eval_coverage.py` 按**目标**回答（清单现在是空的）。

**改前改后都是 235/235 = 100%**：这一轮**没有动任何分数**，
动的是"**这些数字到底在数什么**"。

## 附八：回落原因有四类，其中一类是**我们自己** —— 读超时 60s 与预算 4096（2026-09-20）

### 一、起点：报告里"其他"那一栏在骗人

`docs/planner_batch.html` 的"规划回落"一节从前只有两栏：**传输层** 和 **其他**。
"其他"旁边写着：

> 「其他」里可能包含真正的解析失败 —— 那才是模型的问题。

实测（`reports/eval_model_planner.json`，228 条）把"其他"拆开之后：

| 末次错误 | 条数 |
|---|---|
| HTTP 429 `ApiKey已触发限额` | **57** |
| `finish_reason=length`（思维链吃光预算） | **28** |
| 超时 / 连接断开 | 13 |
| **真正的解析失败** | **0** |

**0 条。** 也就是说"其他"这一栏里**没有一条**是模型的问题：
57 条是端点的额度，28 条是我们自己的配置缺陷。
把它读成"模型不会规划"，结论正好说反。

所以分类从两类改成四类：**传输层 / 配额 / 预算 / 解析**。
只有最后一类才该指向模型。护栏在 `tests/test_measure_planner_batch.py`。

### 二、顺着"预算"这条线，量到两个写死的默认值

`OpenAICompatLLM` 的**读超时**写死 60s，而 kimi-k2.7-code 实测
**平均 27s/次调用、规划约 35s** —— 平均值贴着上限，尾巴必然被砍。
更关键的是：这个 60s 在评测路径上**没有一个** `build_llm()` 调用点传过它，
所以它从来没被当成可调项。裁判早就因为同一个毛病把超时提到 180s
（默认 60s 会吃掉约 6.7% 的判决），规划这条路一直没跟上。

### 三、2×2 对照：卡住的是**等待时间**，不是 token

`scripts/probe_planner_budget.py` 只改两个变量（读超时、预算），
场景、剧本、端点全不动。village 场景 12 轮，只开规划、台词走模板：

| 读超时 | `max_tokens` | 规划调用 | 失败 | 失败类型 | 失败时的思维链 |
|---|---|---|---|---|---|
| 60s | 4096 | 6 | **2** | 超时 | **0** 字 |
| 60s | 16384 | 6 | **3** | 超时 | **0** 字 |
| 180s | 4096 | 6 | **2** | 预算 | **17276** 字 |
| 180s | 16384 | 5 | **1** | 超时 | **0** 字 |

表格里的**每个数字都能在原始探针日志里对上** —— 日志随仓库一起提交（[60s 档](probe_planner_timeout_60s.txt)、[180s 档](probe_planner_timeout_180s.txt)），探针脚本是 `scripts/probe_planner_budget.py`。⚠️ 60s 那份**早于超时开关**，所以它日志里没有“超时档位”这一行 —— 那个 60s 是**当时的默认值**，不是显式传进去的。三条读法：

1. **60s 那两行**：失败**全部**是 `TimeoutError`、思维链 **0** 字
   —— 响应根本没回来。把预算从 4096 提到 16384，失败数**没降**
   （2 → 3）⇒ **加 token 不解决问题**。
2. **180s + 4096**：超时**一条不剩**，失败换成了 `finish_reason=length`、
   思维链 **16590 / 17276** 字 ⇒ 响应回来了，
   但**预算不够**。**不先把超时放宽，你根本看不见预算这个问题** ——
   它被超时盖住了。
3. **180s + 16384**：预算失败**清零**（预算类 2 → 0，失败总数 2 → 1），
   只剩 **1** 条超时 —— 说明端点本身偶尔真的会卡住。
   也就是说：**超时那一档修的是"我们等得不够久"，剩下的那一条才是端点。**

### 四、这一轮改了什么

| 改什么 | 从前 | 现在 | 为什么是这个数 |
|---|---|---|---|
| 读超时 | `OpenAICompatLLM` 里写死 60s，且无人可改 | `RuntimeConfig.llm_timeout = 180.0`，四个调用点全部接线 | 裁判早就在用 180（同一端点上同一个毛病）；实测 27s 平均、35s 规划 |
| 规划预算 | `max_tokens = 4096` | `max_tokens = 16384` | 实测：180s 下 4096 有 **2/6** 条被思维链吃光，16384 是 **0** 条。**注意这是上限不是目标** —— 模型不写那么长就不会多花钱 |
| 回落分类 | 传输层 / 其他 | 传输层 / 配额 / 预算 / 解析 | 实测"其他"里解析失败 **0** 条，混着 57 条配额 + 28 条预算 |
| 恢复指纹 | 不含超时 | `llm_timeout` 进 `RESUME_CRITICAL_FIELDS` | 等 60s 和等 180s 的回落率不同；不进指纹，`--resume` 会把两种配置拼成一份报告 |

护栏：

* `tests/test_llm_client.py` —— 超时对着**实测耗时**定（不许贴着平均值）、
  两个默认值必须一致（"两个真相"）、配置要**真的接线**到客户端。
* `tests/test_runner.py` —— 改了超时必须作废检查点。
* `tests/test_measure_planner_batch.py` —— 四分类，以及"四类之和等于回落用例数"。

### 五、这条改动能证明什么、不能证明什么

**能**：

* 60s 会把规划调用砍掉，而且**加预算无效**（预算翻四倍，失败数没降）。
* 报告里的"其他"确实混了配额和预算；解析失败是 **0** 条。
* 超时放宽之后，**预算才成为下一个瓶颈**（2/6），
  把预算提到 16384 之后这一类清零 ⇒ 两个默认值**都是错的，而且互相掩盖**。

**不能**：

* 单场景（village）、单模型、每臂只有 **5~6 次**调用 —— 这是**定向诊断**，
  它说明"这条路径会以哪种方式失败"，**不是**失败率。
* 16384 是"在这个场景里够用"，不是"对所有场景都够"；
  8192 没有测过，所以没有选它。
* 端点仍然会抖：修复后整臂 **112/231（48%）** 至少回落一次。
  放宽超时与预算只能吃掉"我们这边没给够"的那部分，
  剩下那一条超时（180s + 16384 那一臂）说明端点自身也会卡。
