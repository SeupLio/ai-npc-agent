# 技术文档

> 这份文档写给**要改这个仓库的人**：模块怎么划分、关键取舍为什么是那样、
> 每个数字是怎么量出来的、哪些地方踩过坑。
>
> README 面向读者（项目是什么、能做什么、怎么跑），这里面向维护者。

---

## 一、范围与非目标

**做**：一套环境无关、模型可选、可评测的 NPC 智能体框架。核心是"边界可控"——
该不该说话、什么不能说、失败了怎么归因、两个 NPC 怎么接话。

**不做**：

- 不做通用 Agent 框架。通用框架的优化目标是"任务成功率"，这里的目标是
  "体验不崩"，两者的取舍经常相反（例如这里会**主动让 NPC 闭嘴**）。
- 不做模型训练/微调。模型是可插拔的上层，不是前提。
- 不做渲染、动画、语音。这些在引擎侧，框架只产出"说了什么 + 做了什么"。

## 二、一轮的完整链路

```
observe          从环境取观测（谁在场、我在哪、世界标记）
  ↓
state.update     刷新现场状态（谁刚说话、冷场多久、发言占比）
  ↓
dialogue.decide  该不该我说话？对谁说？—— 含"同伴点了我"这一支
  ↓
memory.retrieve  检索相关记忆（混合打分：相关度 + 时间衰减 + 重要度）
  ↓
planning         分解任务 / 继续未完成的计划 / 失败后重规划
  ↓
tool use         统一执行（speak / remember / 世界动作）
  │              人设闸门（出戏词 / 剧透词 / 句数上限）
  │              环境护栏（位置 / 材料 / 白名单 / 知识解锁）
  ↓
reflection       失败归因 → 写成教训 → 下次重规划时插入补救动作
```

链路是**闭合**的：世界状态的变化会回到记忆与反思里，下一轮决策看得见
"我上次做了什么、结果如何"。

多 NPC 场景在这条链之外还套了一层**导演**（`Cast`）：

```
玩家发言 ──▶ 导演：这一轮谁先开口（被点名的优先，其余轮转）
              │
              ├─ NPC A 行动 ──▶ 说了一句给 B 的话
              │                  │
              │                  ├─ 记进对话板（谁对谁说的）
              │                  └─ 开一条"接话义务"（B 下一轮必须接）
              │
              └─ NPC B 行动 ──▶ 下一轮把 A 那句话当成输入喂给 B
```

## 四、NPC 之间怎么对话

### 4.1 问题：那条边根本不存在

修复前的实测（`scripts/probe_npc_dialogue.py`，duet，8 轮离线）：

```
NPC 台词        5 句
其中对 NPC 说的  0 句
被点名后接话     0 次（0%）
```

根因不是"接得不好"，是**结构上不存在**：

1. 导演只把**玩家**的发言当成输入。同伴说的话只被 `observe_utterance`
   记进记忆 —— "听见"和"要回答"被混成了一件事。
2. 对话决策里没有任何一支承认"同伴在跟我说话"。`decide()` 的六条分支
   全部以玩家发言为前提。
3. 发言权规则是"另一个 NPC 刚发言 → 我不打断"。它在玩家轮里是对的
   （防止抢话），但同伴轮里同样生效，于是被点名的人永远不说话。

三处都在，缺一不可：只补第一处，第二处会把话截住；只补第二处，第一处
根本不会把话送过来。

### 4.2 接话义务（ReplyObligation）

由导演开、由导演销，一个时刻只有一个人被欠一句话。

```
A 说了一句"要回应"的话，且收件人是 B
  → board.open(target=B, ...)
下一轮：board.take(B) 成功 → 把 A 那句话包成 Utterance(role="npc") 喂给 B
        没接住 → board.expire()（过期是对话的一部分）
玩家开口 → board.player_turn()（清空义务、链长归零）
```

两个关键判据：

- **"要回应"由产出方声明**（`Utterance.expects_reply`），不由接收方猜。
  按"说了给谁"就要求回应，会陷入「……听见了」→「我记下了」→「嗯」的礼貌死循环
  （实测 10 轮里 4 轮是这种回声）。
- **收件人必须是显式声明或点名的**。曾经有一条"两个 NPC + 问句 ⇒ 问的就是另一个"
  的兜底规则，它把阿柚对**全场**说的开场白「第一次来吧？想喝什么？」
  判成了问小舟 —— 小舟回一句「……还行。」，她自己的目标永远没开工。
  这条兜底现在**只在同伴轮内**生效。

### 4.3 话题账本（TopicLedger）

逐字查重（`modules/repetition.py`）只能抓"同一句话说两遍"。
账本抓的是"同一件事说两遍"—— 换个说法也拦得住。

内容点由**产出方声明**（`ContentPoint(topic, detail)`），不由消费者猜：

| 意图 | 内容点 |
|---|---|
| `recall` / `heard_from` | `("recall", 记忆 id)` |
| `tell_fact` | `("fact", 话题 id)` |
| `ask_peer` / `delegate` | `("ask_peer"/"delegate", 同伴 id)` |

账本是**跨 NPC 共享**的（挂在对话板上），这是它相对 `agent.said` 的唯一增量：
"我刚讲完店史，他也讲一遍"这种事，私有判据管不到。

### 4.4 话语类型（classify_utterance）

回应由**话语类型**决定，不由"哪个模板先匹配上"决定。

| 类型 | 例子 | 正确反应 |
|---|---|---|
| `delegate` | 阿柚，你让小舟弹一首呗？ | 转达给同伴（**不是**回答玩家） |
| `group_question` | 你们俩平时都聊些什么？ | 用"同伴事实"回答 |
| `peer_turn` | （同伴）小舟，还有豆子吗？ | 接话 |
| `question` | 这店开了多久了？ | 回答，答不上才老实说不知道 |
| `statement` | 今天挺热闹。 | 应一声 / 追问 |

修复前的问题是**意图从模板池里按优先级挑**：`delegate` 找不到模板，
落到 `unknown`，NPC 回「这个我不太清楚」—— 它不知道的是"该转达"，
不是"这件事"。

### 4.5 连聊上限

`max_peer_exchanges` 默认 3。这不是"怕模型话多"，是产品判断：
玩家看两个 NPC 聊十轮，不会觉得世界很活，只会觉得自己被晾着。

到顶之后不再开新义务，计数记在 `board.truncated` 上 ——
它是"机制在工作"的证据，不是失败率，也不进任何分母。

### 4.6 冷场时 NPC 会主动搭话

目标都做完了、也没有新知识可分享时，NPC 会跟同伴搭一句
（`ask_peer`，每个同伴只问一次）。这是"世界自己在转"最便宜的证据：
玩家什么都不说，场上仍然有人在说话，而且是**对另一个人**说的。

## 五、印象怎么在角色之间流动

### 5.1 为什么不能传原话

所有 NPC 都听得见玩家说话（`observe_utterance` 是广播），
所以"把原话再传一遍"没有信息量 —— 接收方早就听过，记忆里还会出现
「小舟说：…」和「听小舟说，…」两条重复。

真正只属于某个 NPC 的东西是**它的判断**：「阿柚注意到阿澈口味偏酸」。

### 5.2 链路

```
玩家：我喜欢偏酸的豆子
  → 阿柚应答成功 → preference_clause() 取出「我喜欢偏酸的豆子」
  → to_third_person() → 「阿澈喜欢偏酸的豆子」
  → gossip.publish(SharedFact(fact_id="pref:player_a:...", source=阿柚))
  → 一轮结束时投递给小舟 → 记忆里写入「听阿柚说，阿澈喜欢偏酸的豆子」
     （tags: gossip, source:阿柚；entities: 阿柚 + 阿澈）
  → 另一个玩家问「你还记得阿澈喜欢什么吗」
  → 小舟：阿柚说过，阿澈喜欢偏酸的豆子。
```

### 5.3 三个必须有的细节

1. **来源写成 tag，不写进 content**。按文案猜来源，上游一改措辞就失效
   （这个项目在这条坑里摔过好几次）。
2. **只传一跳**。两跳之后"谁说的"和"还是不是原话"都没法保证，
   而一条传错三次的传闻比没有传闻更伤。
3. **检索要放行**。`_recallable` 有一条"必须关于当前说话人"的规则
   （防止把 A 的偏好回引给 B）。传闻是第三人称、自带归属，不该被这条挡住 ——
   但也不能全放行，所以条件是"这句话里提到了传闻的主角"。

### 5.4 关掉它

`gossip_enabled=False` 真的会关掉（有测试），不是装饰性配置。

## 六、成本与循环管控

三个开关，对应同一次事故的三个侧面（几十个 Agent 跑十几小时、没有上限）。

| 开关 | 参数 | 拦什么 |
|---|---|---|
| 单轮调用上限 | `max_llm_calls_per_turn=2` | 一轮里狂调模型 |
| 会话预算 | `max_session_tokens=200_000` | 一轮一轮地慢慢烧 |
| 循环检测 | `loop_guard_repeats=3` | 原地打转 |
| 上下文裁剪 | `context_max_chars=2000` | 每轮把全部记忆塞进提示词 |

### 6.1 循环检测的判据（踩过一次）

第一版写的是"同一个动作在窗口里出现 3 次"。它把一条正常的做单计划判成了
死循环：`move_to(吧台)` 在一次做单里本来就出现 3 次（去后厨、回吧台、
再回吧台递东西），中间夹着别的动作。计划被拦腰砍断，`give_item` 永远执行不到 ——
离线 235 条掉到 233。

现在的判据是**末尾出现重复的周期块**（周期 1~3，重复 3 次）：

```
A A A                周期 1
A B A B A B          周期 2
A B C A B C A B C    周期 3
```

"重复"和"反复经过同一个地方"是两件事。

### 6.2 token 是估算

仓库里没有 tokenizer（那会引入依赖，破坏"clone 下来就能跑"）。
估算口径是字符数，只用来兜底，**不能用来做成本核算**。
报告里凡引用它都写明是估算。

## 七、评测体系

四层，各自回答不同的问题：

| 层 | 规模 | 回答什么 |
|---|---|---|
| 六维回归 | 235 条 | 改了代码，框架逻辑有没有被弄坏 |
| 多 NPC 对话基准 | 18 条 | NPC 之间能不能聊起来 |
| 敏感性 | 注入 6 个缺陷 | 满分是不是"护栏从不报警" |
| 分辨率 | 剂量-反应曲线 | 退化多少，评测才开始掉分 |

### 7.1 为什么对话基准要单独一套

六维评测对"两个 NPC 之间"**结构上盲**：`turn_taking` 只看
"一个 tick 里是不是只有一个人开口"，两个 NPC 全程不说话它也满分。

所以对话基准的六维是另外六个：

```
peer_turn     同伴点了我，我接不接
delegation    玩家让我叫同伴，我转不达得到
grounding     问"你们俩"、问"你是谁"，答不答得上来
novelty       复不复读、会不会两个 NPC 抢着说同一件事
memory_flow   印象传不传到另一个 NPC 那里
turn_taking   一个 tick 一个人、链长有上限、被点名的优先
```

**判据只断言可观测的行为**（世界里的发言记录），不看内部变量：
内部变量可以为了通过测试而设成某个值，发言记录不能 —— 玩家听到的就是它。

### 7.2 敏感性：满分必须能被证伪

| 注入的缺陷 | 通过 | 掉分的维度 |
|---|---|---|
| 关掉 NPC 对聊（`max_peer_exchanges=0`） | 14/18 | 同伴接话、转达 |
| 关掉传闻（`gossip_enabled=False`） | 16/18 | 印象流动 |

**预期是事先写死的**，不是事后看到哪个掉了就记哪个 ——
否则判据会自己解释自己。

一个反直觉的读数：关掉对聊之后 `turn_taking` 仍然是 3/3。
因为它测的是"别抢话"，不是"会不会聊"。把它当成"对话能力"的证据是误读。

这条还抓出过一次**假通过**：`peer_chain_alternates` 的第一版只检查
"两个人都开过口、相邻两句不是同一人"，于是关掉对聊之后它照样通过 ——
因为小舟会自己找话讲，两个人的名字都会出现在记录里。
现在的判据要求：至少有一句是**对另一个 NPC** 说的，而且对方下一轮接了。

## 八、关键取舍

### 8.1 边界放在工具层，不放在提示词里

出戏词、剧透词、句数上限、发言权，全部在 `ToolRegistry` 执行前判定。
理由：提示词是**请求**，工具层是**约束** —— 只有后者能被测试钉住。

### 8.2 离线路径是地基，不是降级

`llm_provider` 默认 `null`。这不是"没配好时的兜底"，是**可复现评测的前提**：
只有确定性路径才能当回归基线。真实模型是可插拔的上层。

### 8.3 发言权由导演统一收放

多 NPC 场景里，`cast.py` 是唯一决定"这个时刻谁能开口"的地方。
自己管自己的话，两个 NPC 都会觉得自己该说话 —— 多 Agent 最典型的翻车。

### 8.4 让出 ≠ 失败

`ActionResult.outcome` 区分 `failed`（真的没做成）和 `declined`（按策略让出）。
不区分的话，反思会把"守规矩"记成"有毛病"，而这条假教训会以高重要度
进记忆、被规划提示词取走 —— 模型会被告知自己有个毛病，而那个"毛病"是它守规矩。

### 8.5 判据由产出方声明，不由消费方猜

`Utterance.expects_reply`、`ActionResult.outcome`、`ContentPoint` 都是这个原则。
按文案猜意图，上游一改措辞就静默失效，而这类失效不会报错。

### 8.6 环境无关

Agent 只面对 `observe()` 和 `dispatch()`，不知道自己在咖啡屋还是 Minecraft。
这句话有两个结构完全不同的世界可以对照验证。

## 十、世界设定、关系、动机、注意力

这四个模块补的是"世界本身像不像活的"。它们的共同点是：
**都要有一个可观测的出口** —— 只写进配置、不改变任何可见行为的机制，
等于没有（这个仓库里最忌讳的那类死代码）。

### 10.1 世界观一致性（`modules/lore.py`）

**问题**：出戏词有词表、剧透有解锁状态，但"这家店在山顶"这种**事实错误**
没有任何护栏。它语法通顺、语气对、没出戏、没剧透，只是和世界不符。

**判据**：同一句话里**同时**出现主体（"这家店"的某个叫法）和矛盾说法。
只查矛盾词会误伤闲聊（「山顶的风景不错」）；只查主体会误伤正常陈述。
保守，会漏（换了说法的矛盾抓不到），但不会冤枉 —— 在这个位置上，
冤枉的代价更高：玩家看不出那是护栏的错，只会觉得这 NPC 怪。

**两个出口**：
- `ToolRegistry._speak` 拦截（和出戏词、剧透同一个位置，是**约束**）；
- `canon_block()` 拼进台词提示词（是**请求**，让模型少犯错）。

**为什么设定写在场景 YAML 而不是人设卡**：设定属于世界，不属于角色。
同一个人设配到另一个世界里，店的位置就变了。

### 10.2 关系与称号（`modules/relationship.py`）

**问题**：环境早就在算好感（递饮品 +4、答对题 +6），但**没有任何决策读它**。
一个会动、没人用的数字，比没有更糟 —— 调参的人会以为自己能改变体验。

**做法**：好感是环境的（它知道发生了什么），阶段和称号是这个模块派生的。
两边各存一份必然漂移，所以这里只做"读环境 + 派生"。

**阈值是量出来的**：初始好感 50。第一版阈值从 30 起，于是**第一次见面的人
一进门就是「面熟」**，还会当场领称号（实测小舟第一轮就说
「记住这个：熟面孔。阿澈。」）—— 比没有关系系统更糟，因为它一眼假。
现在 56 才到「面熟」，两次有效互动才跨过去。

**称号必须说出口**：只存进数据库的称号玩家看不见。解锁时攒一条待播报事件，
下一次跟这个人说话时优先说出来，说完就清掉（说两次就是复读）。
玩家在问问题时**不播报** —— 先回答问题，否则是答非所问。

### 10.3 动机与涌现事件（`modules/motives.py`）

**"涌现"最少需要三步**：各有动机 → 争夺同一个资源 → 冲突有结果且改变世界。
少了第三步，"动机"只是配置里的两行字。

**强度是产品判断**：谁让步写在配置里（40 vs 70），不是模拟出来的。
这一点在文档里必须说清楚，否则会被读成"NPC 有自主意识"。

**事件只发生一次**：`resolved` 记已经裁定过的**资源**（不是冲突对）。
不记的话每轮重新裁定，NPC 会反复说"行，那就依你"—— 那是复读，不是涌现。
按资源记还有第二个理由：三个人抢同一件事时，按冲突对枚举会产生三条事件；
按资源分组才是"一件事裁定一次，赢家一个，其余人让步"。

**让步优先于计划**：阿柚的计划有 8 步，不让它插队的话，实测 8 轮都没说出
那句让步，事件等于没发生。所以让步和"回答玩家"同级：插队说一句，
计划里排到的 `speak` 自动让开（一轮只说一句）。

### 10.4 一对多注意力（`modules/attention.py`）

**两种"一对多"**：同时有多人想说话；有人问了但没答。

第二种是重点：玩家问了一句没被答上，NPC 转头去分享店史，
玩家会觉得"它根本没在听"。而它其实听见了 —— 只是没有一个地方
记着"我欠他一个回答"。

**判据**：被点名 +100、问句 +40、等待 +5/轮（封顶 +30）、好感 ±10。
权重是产品判断，写在一处、能被测试钉住，比散落在分支里好。

**补答时先试着真答**：把欠着的那句话还原成 `Utterance`，走同一条
`_direct_answer` 路径。另写一条字符串路径必然和主路径漂移。

**账目会被清掉**：玩家换了话题，旧账作废（`state.note_utterance` 里
`pending_question` 跟着更新）。人也是这样。

### 10.5 跨会话记忆（`modules/persistence.py`）

**问题**：前面所有记忆能力都有一个隐含前提 —— 同一个进程里连续玩。
关掉窗口再进来，好感清零、称号清零、"我喜欢偏酸的"也不知道了。
对一个养成玩法，这是致命的：玩家花两小时把关系养到「常客」，第二天归零。

**存什么**：每个 NPC 的记忆、关系档案、欠着的回答、**环境里的好感**
（玩家 + 同伴）；世界的事件编年史（含全部让步方）；时钟。
**不存什么**：这一局的转写、传闻网络、发言权状态。判据是
"玩家下次回来，这件事还成立吗" —— 好感成立，"刚才小舟说了句什么"不成立。

**环境好感必须存**：关系账本看起来保存了分数，但每轮 `sync` 都会从环境重读；
不存 `Actor.affinity` 的话，读档后下一步分数就被打回 50，而阶段还停在旧值 ——
两个字段自相矛盾，且不报错。

**三个必须处理的坑**：

1. **tick 要接上**。检索里有硬条件 `record.tick < now`；tick 从 0 重来，
   所有记忆都会被判成"未来的事"而过滤掉 —— 静默失忆，不报错。
2. **编年史是引用**。`Cast.reset` 把 `self.events` 交给每个 NPC；
   读档时若**重新赋值** `cast.events`，NPC 手里还是旧 list，
   于是"上次那事"答不上来。必须 `[:] =` 原地替换。
3. **`resolved` 要一起恢复**。只恢复事件、不恢复"这对冲突已经裁定过"，
   下一轮 `poll` 会再裁定一次，让步方把同一句话说第二遍（实测踩到）。

**版本不兼容就报错**，不做"尽量兼容"：半读进来的存档比读不进来更危险。

### 10.6 三人同场与同伴好感

**为什么需要第三个人**：两人时很多规则"看起来对"，只是被"只有一个人可挑"
掩盖了。第三个人一进场，两个默认假设就现形：

1. 冷场搭话按字典序挑人 → 第三个人永远不被搭话；
2. 动机按冲突对裁定 → 三个人抢同一件事产出三条事件。

**同伴好感不是社交模拟**，它只给"挑谁搭话"一个非任意的依据：
`env.observe()` 交出所有非自身角色的好感，`StateTracker` 按 kind 分流到
`players` / `peers`，`Cast` 在点名/转达/听传闻时调整，`_ask_peer` 按好感
（同好感按 id 稳定排序）挑最近的同伴。

**基准**：活世界基准的「多 NPC 同场」2 条 ——
三个人都得开口；一处资源只产生一条事件、两个让步方、代表只说一次。
故障注入是"只调度前两个 NPC"，两条都会红。

### 10.7 跨 NPC 回引冷却

**问题**：读档后的第二次进店，阿柚说"你之前提过你口味偏酸"，
下一轮小舟又说同一件事。两人各有一条记忆（亲耳听 / 听同伴说），
按记录 id 去重拦不住。

**做法**：`TopicLedger.is_recent(point, now, window)` 是时间窗冷却，
和 `is_spent`（一局一次）并存。`RECALL_COOLDOWN = 4`：太短挡不住轮流复读，
太长会让"记得你"整段只发生一次。冷却从真的说出口开始计时。

## 十一、已知局限

1. 多 NPC 场景支持到 3 个，但仍是全场轮转：没有分组、私聊、并行对话；
   四人以上没实现也没量过。
2. 传闻只做一跳，不做多跳扩散。
3. 离线启发式词汇量有限，20 轮以上复读率会爬到 20%~40%。
4. 对话基准衡量"链路通不通"，不衡量"聊得好不好"——后者要真人玩家。
5. LLM 规划仍不稳定（把规划交给模型时通过率掉到 88.6%）。
6. 裁判判决不可复现（约 22% 的重复判定会翻转），只能当参考信号。

完整证据单见 [`BOUNDARY.md`](BOUNDARY.md)，工程踩坑记录见 [`ENGINEERING.md`](ENGINEERING.md)。
