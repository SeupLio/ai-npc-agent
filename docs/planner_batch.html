模型自己规划：修复前 vs 修复后

把规划交给模型之后，NPC 到底能不能把一件事做完。共 60 条用例的配对前后对比，只差规划 prompt 里那几行（success_when）。
敏感层 16 条（断言世界标记的用例）：世界状态达成 11/16 → 15/16，总通过 11/16 → 15/16。
全体配对子集 60 条：通过 85.0% → 95.0%（其中只有 29 条断言了世界状态，其余结构上看不见这次修复）。
修复后那一臂总共跑了 231 条，通过 221 条（95.7%）—— 但其中 112 条（48%）期间规划调用回落过（末次错误传输层 109 条、配额 0 条、预算 3 条、解析 0 条），所以这个数也不能当模型能力读。
没法确认这是一个预先登记的子集。修复前那条臂跑了 60 条，其中只有 57 条落在加载顺序的前 60 条里 —— 所以它的用例集不是加载顺序的前缀。两种可能：(1) 跑批还没跑完（并发完成的顺序本来就是乱的），跑完之后这条警告会自己消失；(2) 这个子集是事后挑的。跑完之后如果它还在，那就是第二种，引用这些数字时要把这句话一起带上。
两条臂只差一个变量。同一条用例集、同一个模型、同样的 --no-speech（模型只负责规划，台词走模板）。修复前那条臂跑在父提交 4c6569c 的 worktree 里，修复后是 HEAD。所以这里的差可以归到规划 prompt 上，而不是「模型今天心情好」。

事先说好的预测（跑批之前定的）

配对子集里一共 118 个目标，它们的完成条件类型是：all_of×19、all_players_spoke×10、flag×60、player_has×29。其中 79 个的完成条件里含世界标记（标记可能嵌在 all_of 里，所以这个数是递归数出来的）。

为什么要单独列这一栏。框架在规划解析失败时会静默回落到启发式规划器。回落不等于失败 —— 启发式规划器也能完成任务，只是那不是模型的功劳。如果两条臂的回落次数差很多，直接比总通过率就会把「这一次请求没回来」记成「规划质量变差」。所以干净子集那一行才是保守读数：它只算两边都真的让模型规划成功的用例。

这份报告不能说明什么

  • 配对子集只有 60 条，不是全部 231 条。它够看出一个大的效应，不够给小数点后一位的结论。
  • 只有一个模型（kimi-k2.7-code）和一次跑批。模型采样有方差，这份报告没有重复跑，所以没有置信区间。
  • 这是规划这一条路径的读数。台词仍然走模板（--no-speech），所以它完全不代表「接上模型台词之后」的表现。
  • 它量的是目标有没有做完，不是对话好不好。复读、语气、趣味性不在这一列。
  • 旧的那份全量报告 docs/batch_planner.html 描述的是修复前的代码，两份报告的数字不可混用。
